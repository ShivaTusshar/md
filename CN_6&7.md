# CHAPTER 6: The Link Layer and LANs

## 6.1 Introduction to the Link Layer

### Terminology

- **Node:** any device that runs a link-layer (layer 2) protocol: hosts, routers, switches and WiFi access points.
- **Link:** a communication channel that connects two **adjacent** nodes along the path.
- **Frame:** the link-layer packet. A transmitting node **encapsulates the datagram in a frame** and sends the frame over one link.

A datagram going from a wireless host to a server crosses **several different links**, each possibly using a **different link-layer protocol.** The book's example path has six links: WiFi (host to access point), Ethernet (AP to switch), switch to router, router to router, Ethernet (router to switch), Ethernet (switch to server).

### The transportation analogy

A travel agent plans Princeton to Lausanne: limousine to JFK, plane to Geneva, train to Lausanne. Each segment is run by a different company using a different "transport mode."

| Analogy | Networking |
|---|---|
| The tourist | A datagram |
| Each transportation segment | A link |
| The transportation mode (limo, plane, train) | A link-layer protocol |
| The travel agent | A routing protocol |

### Two kinds of links

- **Point-to-point link:** one sender at one end, one receiver at the other (for example, between two routers, or between a PC and its switch). Link access is simple; the sender can send whenever the link is idle. (Protocols: PPP, HDLC.)
- **Broadcast link:** **many senders and receivers share one channel**; when one node transmits, **every** other node receives a copy. (Ethernet bus, WiFi, cable access, satellite.) This needs a **multiple access protocol.**

### 6.1.1 Services provided by the link layer

| Service | What it means |
|---|---|
| **Framing** | Wrap each datagram in a frame (data field + header, sometimes a trailer). MAC addresses in the header identify source and destination (different from IP addresses). |
| **Link access (MAC)** | Rules for putting a frame onto the link. Trivial on point-to-point links; the interesting case is the **multiple access problem** on shared links. |
| **Reliable delivery** | Move each datagram across the link **without error**, using acknowledgments and retransmissions (as in Section 3.4). Used on **error-prone links such as wireless**, to fix errors locally. It is **unnecessary overhead on low-error links** (fiber, coax, most twisted pair), so most wired protocols skip it. |
| **Flow control** (slides) | Pacing between adjacent sending and receiving nodes. |
| **Error detection** | Bit errors come from signal attenuation and electromagnetic noise. The sender adds error-detection bits; the receiver checks them and drops the frame (or asks for retransmission). More sophisticated than the Internet checksum and done **in hardware.** |
| **Error correction** | The receiver finds out **where** the errors are and **fixes them without a retransmission.** |
| **Half-duplex / full-duplex** (slides) | Half duplex: both ends can transmit, but **not at the same time.** Full duplex: both at once. |

**Slide question: why both link-level and end-to-end reliability?** Link-level reliability **corrects an error where it happens** (cheaply, over one hop) instead of forcing a long end-to-end retransmission; this matters most on lossy wireless links. End-to-end reliability (TCP) is **still needed**, because losses can also happen elsewhere (for example, router buffer overflow), which no single link can repair. This is the end-to-end argument from Chapter 4.

### 6.1.2 Where is the link layer implemented?

- In **every host**, mostly on a chip called the **network adapter** (also **NIC**, network interface controller). The Ethernet or WiFi chip implements **framing, link access, error detection** and so on **in hardware.**
- **Sending side:** the controller takes a datagram from host memory, builds the frame, fills in the fields and transmits it following the link-access protocol.
- **Receiving side:** the controller receives the **entire** frame, checks errors and extracts the datagram.
- A part of the link layer is **software on the host CPU** (assembling addressing information, handling controller interrupts, passing the datagram up). So the link layer is **"where software meets hardware"**: a combination of hardware, software and firmware.

## 6.2 Error-Detection and Error-Correction Techniques

### The setting

At the sender, the data **D** is augmented with **EDC** (error-detection and -correction bits). D plus EDC go in the frame. The receiver gets **D′ and EDC′** (which may differ from the originals because of bit flips) and must decide: **was an error detected?**

**Important wording:** the question is "is an error *detected*", not "has an error *occurred*." Even with EDC bits, some errors **go undetected**, and the receiver may deliver a corrupted datagram. More powerful schemes cost **more overhead** (more computation and more EDC bits).

The book covers three techniques: **parity**, **checksumming**, **CRC.**

### 6.2.1 Parity checks

**Single-bit parity.** The sender adds **one parity bit** so that the **total number of 1s in the d + 1 bits is even** (even parity) or odd (odd parity).

- **Example (book):** data `0111000110101011` has nine 1s (odd), so the even-parity bit is **1**, making ten 1s.
- **Receiver:** count the 1s. If the count is odd under even parity, an error occurred. More precisely, **an odd number of bit errors** occurred.
- **Weakness:** an **even** number of flipped bits goes **undetected.** Real errors come in **bursts**, so single-bit parity can miss up to about **50%** of errors.

**Two-dimensional parity.** Arrange the d bits in **i rows and j columns.** Compute a parity bit for **each row and each column** (so i + j + 1 parity bits).

- A **single flipped bit** causes **one row parity error and one column parity error.** Their intersection **pinpoints the bad bit**, so the receiver can **correct** it.
- It also detects (but cannot correct) **any two errors** in a packet.
- A single error in a parity bit itself is detectable and correctable too.

**Forward Error Correction (FEC):** the ability of the receiver to **both detect and correct** errors. Benefits: fewer sender retransmissions, and **immediate correction** without waiting a round trip (valuable for real-time applications and for long-delay links such as deep space). Used in audio CDs, and in networks alone or combined with link-layer ARQ.

### 6.2.2 Checksumming methods

- Treat the data as a sequence of **k-bit integers** and sum them. The **Internet checksum** treats bytes as **16-bit integers**, sums them, and takes the **1s complement** of the sum.
- The receiver sums everything **including the checksum** and takes the complement; if the result is **all 0s**, no error is indicated.
- In TCP and UDP the checksum covers **header and data**; in IP it covers **only the IP header.**
- **Low overhead (16 bits) but weak protection** compared with CRC.

**Why checksum at the transport layer but CRC at the link layer?** The transport layer is **software in the operating system**, so it needs something simple and fast. The link layer is **dedicated hardware in the adapter**, which can compute the heavier CRC quickly.

### 6.2.3 Cyclic Redundancy Check (CRC)

CRC codes are also called **polynomial codes** (the bit string is viewed as a polynomial with 0/1 coefficients).

**Setup:**
- **D** = the d data bits.
- **G** = a **generator**, an **r + 1 bit** pattern that sender and receiver agree on. Its leftmost bit must be **1.**
- The sender appends **r extra bits, R**, so that the d + r bit pattern is **exactly divisible by G** using **modulo-2 arithmetic.**
- The receiver divides the received d + r bits by G. **Nonzero remainder means an error**; zero remainder means accepted.

**Modulo-2 arithmetic:** no carries or borrows. Addition and subtraction are both the **XOR.** Examples: `1011 XOR 0101 = 1110`, `1001 XOR 1101 = 0100`.

**How R is computed.** The transmitted pattern is `D · 2^r XOR R` (shift D left by r places, then fill in R). We want it to equal `n · G` for some n. XORing R to both sides gives `D · 2^r = nG XOR R`, so:

> **R = remainder of ( D · 2^r ÷ G )**

**Worked example (book and slide):** D = `101110` (d = 6), G = `1001` (r = 3).
1. Append r = 3 zeros: `101110000`.
2. Divide by `1001` with XOR long division.

Long division, step by step: take `1011` XOR `1001` = `0010`; bring down bits and subtract whenever the leading bit is 1: the successive remainders are `010` → `011` → `101` → `011`.

3. The remainder is **R = 011.**
4. Transmitted bits: `101110 011` (nine bits).

(Check: the receiver divides `101110011` by `1001` and gets remainder 0.)

**Strength of CRC:**
- Detects **all burst errors of r or fewer bits** (any burst shorter than r + 1 bits).
- A longer burst is detected with probability **1 − 0.5^r.**
- Detects **any odd number of bit errors.**
- Standards exist for **8-, 12-, 16- and 32-bit** generators. **CRC-32** is used in many IEEE link protocols, including **Ethernet and 802.11.**

## 6.3 Multiple Access Links and Protocols

### The multiple access problem

On a **broadcast channel**, if two or more nodes transmit at the same time, their signals **collide** at every receiver; **all the frames involved are lost** and the channel is wasted. A **multiple access protocol** decides **who may transmit and when.**

**Analogy (cocktail party / classroom):** many people share one medium (the air). Humans have rules: "give everyone a chance", "don't interrupt", "don't monopolize."

**The four wishes for an ideal protocol on a channel of rate R bps** (book and slide 14):
1. If **one** node wants to send, it gets **R** bps.
2. If **M** nodes want to send, each gets about **R/M** bps (on average).
3. **Fully decentralized:** no master node (no single point of failure), no clock or slot synchronization needed.
4. **Simple** and cheap.

**Three classes of protocols (taxonomy):**

| Class | Idea |
|---|---|
| **Channel partitioning** | Divide the channel into pieces (time slots, frequencies, codes) and give each node exclusive use of a piece |
| **Random access** | Don't divide the channel; allow collisions and **recover** from them |
| **Taking turns** | Nodes take turns; nodes with more to send can take longer turns |

### 6.3.1 Channel partitioning protocols

**TDM (time-division multiplexing).** Time is split into **frames**, each frame into **N slots**, one per node. Each node sends only in its own slot (usually long enough for one packet).
- Eliminates collisions and is perfectly **fair** (R/N each).
- **Drawbacks:** a node is **limited to R/N even when it is the only active node**, and it **always waits for its turn.**

**FDM (frequency-division multiplexing).** The R bps channel is split into **N frequency bands**, each R/N bps, one per node. Same advantages and **same drawbacks** as TDM.

**CDMA (code division multiple access).** Each node gets a different **code** to encode its bits. If the codes are chosen carefully, **different nodes can transmit simultaneously** and each receiver can still recover its sender's bits. Used in military systems (anti-jamming) and widely in **cellular telephony.** (Details are in Chapter 7, Section 7.2.1 below.)

### 6.3.2 Random access protocols

In random access, a transmitting node **always transmits at the full channel rate R.** After a collision, each node involved **waits a random delay** before retransmitting. Because the delays are independently chosen, one node may pick a short enough delay to "sneak through."

#### Slotted ALOHA

**Assumptions:** all frames have exactly **L bits**; time is divided into **slots of L/R seconds** (one frame time); nodes start transmitting **only at the beginning of a slot**; nodes are **synchronized**; if two or more frames collide in a slot, every node **detects the collision before the slot ends.**

**Operation (p is a probability):**
1. With a fresh frame, wait for the next slot and transmit the whole frame.
2. If no collision: done.
3. If there is a collision: retransmit the frame in **each following slot with probability p** until it gets through (like tossing a biased coin).

**Pros:** a lone node can use the full rate R; highly decentralized (but needs slot synchronization); very simple.
**Cons:** some slots are **wasted by collisions**, others are **empty** (everyone happened not to transmit); only slots with **exactly one** transmitter are **successful.**

**Efficiency** = the long-run fraction of successful slots when many nodes always have frames to send.

Derivation (N nodes, each transmits in a slot with probability p):
- Probability a given node succeeds = p(1 − p)^(N−1)
- Probability **some** node succeeds = **N · p · (1 − p)^(N−1)**
- Maximize over p (the best p is about 1/N), then let N → infinity:

> **Maximum efficiency of slotted ALOHA = 1/e ≈ 0.37 (37%)**

So at best **37%** of slots are successful, about **37% are empty** and about **26% have collisions.** A 100 Mbps slotted-ALOHA channel delivers **under 37 Mbps** in the long run.

#### Pure (unslotted) ALOHA

No slots and no synchronization: a frame is transmitted **immediately** when it arrives. A frame sent at time t0 collides with any other frame sent in **[t0 − 1, t0 + 1]** (the vulnerable period is **two** frame times: it can overlap the start of or the end of another frame).

- P(success) = p · (1 − p)^(N−1) · (1 − p)^(N−1) = **p(1 − p)^(2(N−1))**
- **Maximum efficiency = 1/(2e) ≈ 0.18 (18%)**, exactly **half** of slotted ALOHA. That is the price of being fully decentralized.

*(History: ALOHAnet by Norm Abramson at the University of Hawaii (1970) was the first radio packet network, and it inspired Bob Metcalfe to invent Ethernet.)*

#### CSMA (carrier sense multiple access)

ALOHA ignores what other nodes are doing. CSMA adds two polite rules:
1. **Listen before speaking (carrier sensing):** if the channel is busy, wait until it is idle.
2. **If someone else starts talking at the same time, stop (collision detection):** the CD part.

**Why do collisions still happen if everyone listens first?** **Propagation delay.** A signal takes a non-zero time to travel along the medium, so node D may sense the channel idle even though node B has already started transmitting (B's bits just have not reached D yet). The **longer the propagation delay, the more likely** such a collision. (Book: space-time diagram with nodes A, B, C, D.)

#### CSMA/CD (with collision detection)

A node keeps listening **while** it transmits. On detecting another transmission, it **aborts immediately** (instead of sending a damaged frame in full), which **saves channel time.** Collision detection is **easy in wired** networks but **hard in wireless.**

**The Ethernet CSMA/CD algorithm:**
1. The adapter gets a datagram, builds a frame, and puts it in its buffer.
2. If the channel is **idle**, start transmitting; if **busy**, wait until idle, then transmit.
3. If the **whole frame** goes out with no collision detected, done.
4. If another transmission is detected while sending, **abort** (and send a short **jam signal**, per the slides, so everyone notices the collision).
5. After aborting, wait a random time (**binary exponential backoff**), then return to step 2.

**Binary exponential backoff.** After the **m-th collision** of a frame, the node picks K at random from **{0, 1, 2, ..., 2^m − 1}** and waits **K × 512 bit times** (m is capped at **10**).
- Why random? If everyone waited the same fixed time they would collide forever.
- Why exponential? The interval should be **short when few nodes collide** and **long when many do.**
- Example: after 1st collision K ∈ {0,1}; after 2nd K ∈ {0,1,2,3}; after 3rd K ∈ {0,...,7}; after 10 or more K ∈ {0,...,1023}.
- 512 bit times = **5.12 µs on 100 Mbps Ethernet** (51.2 µs on 10 Mbps).
- Each **new** frame starts the algorithm fresh, so a node with a new frame may sneak in while others are backing off.

**CSMA/CD efficiency** (approximation, with d_prop = max propagation delay between any two adapters and d_trans = time to transmit a maximum-size frame):

> **Efficiency = 1 / (1 + 5 · d_prop / d_trans)**

- As d_prop → 0, efficiency → 1 (colliding nodes abort immediately).
- As d_trans → very large, efficiency → 1 (a frame that grabs the channel keeps it a long time).
- *Illustrative numbers (mine):* if d_prop = 20 µs and d_trans = 1.2 ms, then 5 × 20/1200 = 0.083 and efficiency = 1/1.083 ≈ **0.92.**
- It is **far better than ALOHA**, and simple, cheap and decentralized.

### 6.3.3 Taking-turns protocols

ALOHA and CSMA satisfy wish 1 (one node gets R) but **not wish 2** (M nodes get R/M). Taking-turns protocols aim for both.

**Polling.** A designated **master node** invites each node in turn ("you may send up to some maximum number of frames"), round-robin. It can tell a node is finished by seeing the channel go quiet.
- **Pros:** no collisions, no empty slots, higher efficiency.
- **Cons:** **polling delay** (a lone active node still gets polled around the idle nodes, so it sends below R); and the **master is a single point of failure.** Typically used with "dumb" devices. **Bluetooth** is a polling example.

**Token passing.** No master. A small special frame, the **token**, circulates in a fixed order. A node holding the token sends up to a maximum number of frames, then passes the token on (or passes it immediately if it has nothing to send).
- **Pros:** decentralized and highly efficient.
- **Cons:** token overhead and latency; **one node failing can crash the whole channel**; a node that forgets to release the token needs a **recovery procedure.** Examples: **FDDI** and IEEE 802.5 **token ring.**

### 6.3.4 DOCSIS: the link layer of cable Internet access

A great case study because it uses **all three classes** of protocols.

- Several thousand cable modems connect to a **CMTS** (cable modem termination system) at the **cable headend.**
- **FDM:** the downstream (CMTS to modems) and upstream (modems to CMTS) are each divided into **multiple frequency channels.** Downstream channels are **24 to 192 MHz** wide (about **1.6 Gbps** per channel); upstream channels are **6.4 to 96 MHz** wide (about **1 Gbps**).
- **Downstream:** only the CMTS transmits, so there is **no multiple access problem.**
- **Upstream (TDM-like):** each upstream channel is divided into time intervals containing **mini-slots.** The CMTS sends a **MAP message** downstream saying **which modem may transmit in which mini-slot**, so those transmissions **cannot collide.**
- **How does the CMTS know who has data?** Modems send **mini-slot request frames** in special mini-slots, in **random access** fashion, so these **may collide.** A cable modem **can neither sense the channel nor detect collisions**; it **infers** a collision when it gets no answer in the next MAP, and then uses **binary exponential backoff** before trying again.
- When traffic is light, a modem may even send **data** in slots meant for requests.

So the cable network combines **FDM + TDM + random access + centrally allocated slots.**

### Summary of MAC protocols (slide 33)

| Class | Examples | Notes |
|---|---|---|
| Channel partitioning | TDM, FDM, CDMA | By time, frequency or code |
| Random access | ALOHA, slotted ALOHA, CSMA, CSMA/CD | Carrier sensing is easy on a wire and hard on wireless. **CSMA/CD = Ethernet; CSMA/CA = 802.11** |
| Taking turns | Polling, token passing | Bluetooth, FDDI, token ring |

## 6.4 Switched Local Area Networks

A **switched LAN** connects hosts through **link-layer switches.** Switches forward **frames** using **MAC addresses**; they don't understand IP addresses and don't run routing algorithms such as OSPF.

### 6.4.1 Link-layer addressing and ARP

#### MAC addresses

- It is the **adapter (interface)**, not the host, that has a link-layer address. A device with several interfaces has several MAC addresses (and several IP addresses).
- **Link-layer switches do not have MAC addresses on their ports**, because a switch is **transparent**: hosts never address a frame to the switch.
- Also called **LAN address, physical address, MAC address.** For Ethernet and 802.11 it is **6 bytes (48 bits)**, written in hexadecimal, e.g. `1A-23-F9-CD-06-9B`, giving 2^48 addresses.
- **Uniqueness:** the **IEEE** manages the space. A manufacturer buys a block of **2^24 addresses** (the first 24 bits are fixed, the company chooses the last 24).
- **Flat structure and portable:** a MAC address does not change when the adapter moves. (An IP address is hierarchical and must change when a host changes subnet.)

| | MAC address | IP address |
|---|---|---|
| Layer | Link (2) | Network (3) |
| Size | 48 bits | 32 bits (IPv4) |
| Structure | **Flat** | **Hierarchical** (network + host part) |
| Analogy | **Social security number** (stays with you) | **Postal address** (changes when you move) |
| Used for | Getting a frame to the **next** interface on the same LAN | End-to-end forwarding across networks |

**Receiving a frame:** an adapter checks whether the frame's **destination MAC matches its own** (or is the broadcast address); if yes it passes the datagram up, otherwise it **discards** the frame. The **MAC broadcast address** is **FF-FF-FF-FF-FF-FF** (48 ones).

**Why have both kinds of address?** (Book sidebar "Keeping the layers independent"):
1. LANs support **arbitrary network-layer protocols**, not just IP, so adapters use "neutral" MAC addresses.
2. If adapters used IP addresses, they would have to be **reconfigured whenever they move or power up.**
3. With no adapter addresses at all, **every frame would interrupt the host's CPU**, even frames meant for others.

So each layer has its own addressing: **host names (application), IP addresses (network), MAC addresses (link).**

#### ARP (Address Resolution Protocol)

**Problem:** the sender knows the destination's **IP** address but needs its **MAC** address to build the frame. **ARP translates IP address to MAC address.**

- Like DNS, but with a big difference: **DNS resolves names for hosts anywhere; ARP resolves only for interfaces on the same subnet.** (A node in California cannot use ARP for a node in Mississippi.)
- Each host and router keeps an **ARP table**: **<IP address, MAC address, TTL>.** A typical TTL is **about 20 minutes.** It does not have entries for every node.

**How it works (A wants B's MAC, not in its table):**
1. A builds an **ARP query packet** containing the target IP address and puts it in a frame addressed to the **MAC broadcast address FF-FF-FF-FF-FF-FF.**
2. **Every** adapter on the subnet receives it and passes it to its ARP module.
3. Only the node whose IP address **matches** replies with an ARP response containing its MAC address.
4. A stores the mapping in its table and sends the datagram.

**Things to notice:**
- The **query is broadcast**, but the **response is a normal (unicast) frame**, because the query already carried the sender's MAC address, so the target can reply directly.
- ARP is **plug-and-play**: tables build themselves, and stale entries expire.
- Is ARP link layer or network layer? It is **carried inside a frame** (so above the link layer) but contains **link-layer addresses** and **network-layer addresses**, so it **straddles the boundary** between the two layers.

#### Sending a datagram off the subnet (the classic exam example)

Two subnets joined by a router R (book Figure 6.19, slides 41 to 46):
- Subnet 1 = `111.111.111/24`, Subnet 2 = `222.222.222/24`.
- Host A: IP `111.111.111.111`, MAC `74-29-9C-E8-FF-55`.
- Router interface on Subnet 1: IP `111.111.111.110`, MAC `E6-E9-00-17-BB-4B`.
- Router interface on Subnet 2: IP `222.222.222.220`, MAC `1A-23-F9-CD-06-9B`.
- Host B: IP `222.222.222.222`, MAC `49-BD-D2-C7-56-2A`.

A (on Subnet 1) sends a datagram to B (on Subnet 2):

| Hop | IP source to IP destination | MAC source to MAC destination |
|---|---|---|
| **A to R** | 111.111.111.111 to 222.222.222.222 | 74-29-9C-E8-FF-55 to **E6-E9-00-17-BB-4B** (the router, **not B**) |
| **R to B** | 111.111.111.111 to 222.222.222.222 | 1A-23-F9-CD-06-9B to **49-BD-D2-C7-56-2A** (now B's MAC) |

**Key lessons:**
- The **IP addresses stay the same** end to end; the **MAC addresses change at every hop.**
- If A used B's MAC address on Subnet 1, **no adapter would accept the frame** and the datagram would die.
- A learns the **router's MAC via ARP**; the router learns **B's MAC via ARP** on Subnet 2. A knows the first-hop router's IP from **DHCP** (the default gateway).
- Each router interface has its own IP address, its own ARP module and its own adapter.

### 6.4.2 Ethernet

**Ethernet** has taken over the wired LAN market. Reasons for its success: it was the **first widely deployed high-speed LAN**; token ring, FDDI and ATM were **more complex and expensive**; Ethernet **kept getting faster** and introduced **switched Ethernet** in the early 1990s; and the hardware is a **cheap commodity.** It was invented in the mid-1970s by **Bob Metcalfe and David Boggs** (original speed 2.94 Mbps).

**Topology evolution:**

| Era | Topology | Behavior |
|---|---|---|
| 1980s to mid-1990s | **Bus** of coaxial cable | **Broadcast LAN**; all frames reach all adapters; CSMA/CD handles collisions |
| Late 1990s | **Hub-based star** | A **hub** is a **physical-layer** device that works on **bits**: it re-creates each bit, boosts its energy and sends it out all other ports. Still a broadcast LAN; frames from two ports at once **collide** |
| Early 2000s onward | **Switch-based star** | The switch is **collision-less**, a real **store-and-forward** device, operating through **layer 2** only |

#### Ethernet frame structure

```
| Preamble | Dest. address | Source address | Type | Data (payload) | CRC |
|  8 bytes |    6 bytes    |    6 bytes     | 2 B  |  46-1500 bytes | 4 B |
```

- **Preamble (8 bytes):** the first 7 bytes are `10101010` and the last is `10101011`. They **wake up the receiver and synchronize its clock** with the sender's (clocks drift a little). The last two 1s signal that the "important stuff" is coming.
- **Destination address (6 bytes):** if the adapter sees its own MAC or the broadcast address, it passes the data up; otherwise it discards the frame.
- **Source address (6 bytes).**
- **Type (2 bytes):** says which **network-layer protocol** the payload belongs to (**demultiplexing**, like the protocol field in IP or port numbers in TCP/UDP). For example ARP has type **0806** hex.
- **Data (46 to 1500 bytes):** the datagram. **MTU = 1500 bytes** (larger datagrams must be fragmented). If it is shorter than **46 bytes**, it is **stuffed** with padding up to 46; the IP **length field** lets the receiver strip the padding.
- **CRC (4 bytes):** lets the receiver detect bit errors.
- *(Derived: the minimum frame is 6 + 6 + 2 + 46 + 4 = **64 bytes** and the maximum 6 + 6 + 2 + 1500 + 4 = 1518 bytes, not counting the preamble.)*

#### Ethernet service model

- **Connectionless:** no handshake between sending and receiving adapters.
- **Unreliable:** the receiver runs the CRC but sends **no ACK or NAK**; a bad frame is simply **dropped.** The sender never knows. So the datagram stream can have **gaps.** With **UDP**, the application sees the gaps; with **TCP**, the missing data is **retransmitted** by TCP (Ethernet does not know whether it carries new or old data).
- MAC protocol: **unslotted CSMA/CD with binary backoff** (needed only on shared media; on a switched Ethernet there are no collisions).

#### Ethernet technologies (the naming)

`10BASE-T`, `100BASE-T`, `1000BASE-LX`, `10GBASE-T` ...
- First part = **speed** (10 Mbps, 100 Mbps, 1000 Mbps (Gigabit), 10G, 40G).
- **BASE** = **baseband** (the medium carries only Ethernet traffic).
- Last part = **physical medium.** **T** means **twisted-pair copper**; others are coax or fiber (e.g. 100BASE-FX).
- Early 10BASE-2 and 10BASE-5 ran over two kinds of **coax**, about 500 m max, extended with **repeaters** (physical-layer devices that regenerate the signal).
- **100 Mbps Ethernet:** same MAC protocol and frame format, new physical layers. Limit: **100 m over twisted pair**, several km over fiber.
- **Gigabit Ethernet (802.3z):** keeps the **standard frame format** (backward compatible), supports **point-to-point links (with switches)** and shared channels (with hubs, called **buffered distributors**), uses CSMA/CD on shared channels (so distances must be limited), and allows **full-duplex** operation on point-to-point links. Now also runs over category 5 UTP (1000BASE-T, 10GBASE-T).

**The enduring constant:** speeds grew by three orders of magnitude, media changed, switches replaced hubs and even the MAC protocol is often unnecessary, yet the **Ethernet frame format** has stayed the same.

### 6.4.3 Link-layer switches

The switch receives incoming frames and forwards them onto outgoing links. It is **transparent** to hosts and routers (they never address frames to it), and its output interfaces have **buffers** (like router output ports).

**Two functions:**
- **Filtering:** deciding whether a frame should be forwarded or **dropped.**
- **Forwarding:** deciding to which interface(s) a frame should go, and moving it there.

Both use the **switch table**: entries of **(MAC address, interface leading toward that MAC, time)** for *some* hosts.

**Frame arrives on interface x with destination MAC D. Three cases:**

| Case | Action |
|---|---|
| **No entry for D** | **Flood:** forward a copy to **all interfaces except x** |
| **Entry says D is on interface x** | **Filter:** **drop** the frame (the destination is on the segment it came from, so it already got it) |
| **Entry says D is on interface y ≠ x** | **Forward** the frame to interface y only |

(The slide gives the same logic as an algorithm: record the incoming link and sender's MAC; look up the destination; if found and on the same segment drop, else forward; if not found **flood.**)

**Self-learning (plug-and-play):**
1. The switch table starts **empty.**
2. For **every incoming frame**, the switch records the frame's **source MAC address, the interface it arrived on, and the current time.**
3. An entry is **deleted after an aging time** with no frames from that source (so a replaced PC eventually disappears).

*Example (book):* at 9:39 a frame with source `01-12-23-34-45-56` arrives on interface 2, so the switch adds that entry. If the aging time is 60 minutes and no frame from `62-FE-F7-11-89-A3` arrives between 9:32 and 10:32, that entry is removed at 10:32.

A switch is **plug-and-play** (no configuration needed) and **full-duplex** (each interface can send and receive at the same time).

#### Properties and advantages of switching

- **No collisions:** a switch buffers frames and never puts more than one frame on a segment at a time. Each link is its own **collision domain**, and A-to-A′ and B-to-B′ can transmit **simultaneously.** The aggregate throughput of a switch is the **sum of all its interface rates.**
- **Heterogeneous links:** different links can have **different speeds and media** (e.g., 1 Gbps copper and 100 Mbps fiber on one switch).
- **Management:** the switch can disconnect a **jabbering adapter** (one that keeps sending frames), a cable cut only affects one host, and it gathers **traffic statistics.**

**Security note (switch poisoning):** on a switched LAN, host C normally **cannot sniff** the A-to-B frame (the switch sends it only to B). But the switch **floods frames with unknown destinations**, and everyone sees **broadcast frames.** In **switch poisoning**, an attacker sends many frames with **bogus source MAC addresses** to **fill the switch table**, so the switch floods most traffic and the sniffer can see it. Switches are still **less vulnerable to sniffing than hubs and wireless LANs.**

#### Switches versus routers

Both are **store-and-forward** and both have **forwarding tables**, but:

| | **Switch** | **Router** |
|---|---|---|
| Layer | **Link (2)**; examines frame headers | **Network (3)**; examines IP headers |
| Addresses used | **MAC (flat)** | **IP (hierarchical)** |
| How the table is built | **Self-learning** (flooding and learning) | **Routing algorithms** (OSPF, BGP, etc.) |
| Plug and play | **Yes** | **No** (needs IP addresses configured) |
| Processing speed | Usually **faster** (only up to layer 2) | Larger per-packet processing |
| Topology | Limited to a **spanning tree** (to stop broadcast frames from cycling) | Rich topologies with the **best path**; no spanning-tree restriction |
| Broadcast storms | **Susceptible** (a host sending endless broadcast frames can collapse the network) | Provide a **firewall** against layer-2 broadcast storms |
| ARP load | Large switched networks need **large ARP tables** and generate lots of ARP traffic | Better isolation |

**Table 6.1 (typical features):**

| | Hubs | Routers | Switches |
|---|---|---|---|
| Traffic isolation | No | Yes | Yes |
| Plug and play | Yes | No | Yes |
| Optimal routing | No | Yes | No |

**When to use which:** small networks (a few hundred hosts) use **switches** (no IP configuration, localizes traffic); larger networks (thousands of hosts) add **routers** for robust isolation, broadcast control and smarter routes.

### 6.4.4 Virtual LANs (VLANs)

**Three problems of a plain hierarchical switched LAN:**
1. **Lack of traffic isolation:** broadcast traffic (ARP, DHCP, unknown-destination frames) must cross the **entire** institutional network. This hurts performance, security and privacy (e.g., executives vs. employees running sniffers).
2. **Inefficient use of switches:** 10 small groups would need 10 switches, although one big switch could hold everyone (but then there is no isolation).
3. **Managing users:** moving an employee to another group means **re-cabling.**

**A VLAN-capable switch** lets you define **several virtual LANs on one physical LAN infrastructure.** Hosts in a VLAN communicate **as if they were the only ones connected to the switch.**

**Port-based VLAN:** the manager groups the switch's **ports**; each group is a VLAN and a **broadcast domain.** *Book example (Figure 6.25):* a 16-port switch with **ports 2 to 8 = EE VLAN** and **ports 9 to 15 = CS VLAN**, ports 1 and 16 unassigned. (The slide labels EE as ports 1 to 8.) If the user on port 8 joins CS, the operator just reconfigures that port to the CS VLAN. The switch keeps a **port-to-VLAN table** and delivers frames only between ports of the same VLAN.

**Traffic between VLANs** must go through a **router** (a switch port belonging to both VLANs, connected to a router; in practice one device contains the VLAN switch plus router). An EE-to-CS datagram crosses the EE VLAN to the router, which forwards it onto the CS VLAN.

**VLANs across multiple switches:**
- **One cable per VLAN** between the two switches: **does not scale** (N VLANs need N ports on each switch).
- **VLAN trunking:** a special **trunk port** on each switch belongs to **all VLANs** and carries frames of all VLANs over one link. The receiving switch must know which VLAN a frame belongs to, so frames on a trunk use the **802.1Q** format.

**802.1Q frame:** the standard Ethernet frame plus a **4-byte VLAN tag** inserted in the header:
- **TPID (Tag Protocol Identifier):** 2 bytes, fixed value **0x8100** (written 81-00).
- **TCI (Tag Control Information):** 2 bytes, including a **12-bit VLAN identifier** and a **3-bit priority** field (similar to the IP TOS field).
- The **CRC is recomputed** because the frame changed.
- The sending switch **adds** the tag; the receiving switch **removes** it.

Other VLAN types: **MAC-based** (membership by MAC address), based on **network-layer protocol**, and VLANs can even be **extended across IP routers** to span the globe.

## 6.5 Link Virtualization: A Network as a Link Layer

Our idea of a "link" has evolved: a **physical wire**, then a **shared channel** (cable, radio), then a **complex switched LAN or VLAN.** A host is **unaware** of how complex the link below it is.

The Internet also **virtualizes** other networks: a **dial-up modem connection** across the **telephone network** is just a "wire" to IP hosts. (Similarly, an **overlay network** treats the Internet as a link, as in Chapter 2.)

### 6.5.1 MPLS (Multiprotocol Label Switching)

**What it is:** a **packet-switched, virtual-circuit-style** network that the Internet treats as a **link-layer technology** connecting IP devices. It grew out of mid/late-1990s efforts to **speed up IP forwarding** by borrowing the **fixed-length label** idea from virtual-circuit networks. The goal was **not** to abandon IP forwarding but to **augment** it: selectively label datagrams and forward on **labels** when possible. It works **hand-in-hand with IP** (RFC 3031, 3032).

**MPLS header:** inserted **between the link-layer header (e.g., Ethernet) and the IP header.** Fields: **Label** (20 bits), **Exp** (3 bits, experimental), **S** (1 bit, marks the bottom of a stack of labels) and **TTL** (8 bits). *(The slide text shows a different number for TTL; the header is 32 bits in total, so 20 + 3 + 1 + 8.)*

**Label-switched routers:** an MPLS-capable router forwards a frame by **looking up the label** in its table and sending it to the output interface, **without examining the IP destination address** or doing a longest-prefix match. MPLS frames can only go between routers that are **both MPLS capable.**

**Example (Figure 6.29):** R1 to R4 are MPLS-capable; R5 and R6 are ordinary IP routers.
- R1 tells R2 and R3: "label **6** goes toward destination **A**."
- R2 maps incoming label **8** to outgoing label 6 (toward A).
- R3 maps incoming label **10** to outgoing 6 (toward A), and incoming label **12** to outgoing 9 (toward D).
- **R4 now has two MPLS paths to A:** via **interface 0 with label 10** (through R3) and via **interface 1 with label 8** (through R2).

**Why that is the real value of MPLS:** IP routing (OSPF/BGP) would give a **single least-cost path** to A. MPLS can forward some traffic on **one path** and the rest on **another**: **traffic engineering.** Other uses:
- **Fast restoration:** reroute over a precomputed backup path after a link failure.
- **VPNs (virtual private networks):** isolate a customer's addressing and resources inside the ISP's MPLS network.

**Signaling and paths:** labels are distributed with an extension of **RSVP (RSVP-TE)**, and OSPF is extended to flood link-state information to MPLS routers. The path computation algorithms are **not standardized** (vendor-specific). MPLS appeared **before SDN**; many of its traffic-engineering functions can now also be done with SDN and generalized forwarding.

## 6.6 Data Center Networking

Companies such as Google, Microsoft, Amazon and Alibaba run data centers with **tens to hundreds of thousands of hosts.** Data centers serve three purposes: **deliver content** (web, search, email, video), **massively parallel computing** (e.g., search index computation), and **cloud computing** for other companies.

### 6.6.1 Data center architecture

- **Cost (2009, 100,000-host data center, over $12 million/month):** about **45% hosts**, **25% infrastructure** (power, cooling), **15% electricity**, **15% networking.** Networking is not the biggest cost, but **networking innovation is the key to cutting total cost and maximizing performance.**
- **Hosts** are called **blades** ("pizza boxes"), stacked in **racks of 20 to 40 blades.** At the top of each rack is a **Top-of-Rack (TOR) switch.** Hosts connect to the TOR at **40 or 100 Gbps**, and each has an internal IP address.
- **Two kinds of traffic:** external clients to internal hosts, and internal host to internal host. **Border routers** connect the data center to the Internet.

**Load balancing.** Each application has a **public IP address.** Requests first reach a **load balancer**, which spreads them across hosts based on their load.
- Sometimes called a **"layer-4 switch"**, because it decides using the **destination port number** as well as the destination IP.
- It also does a **NAT-like translation** (public IP to the chosen host's internal IP and back), which **hides the internal network** from clients (a security benefit).

**Hierarchical architecture** (Figure 6.30): border router, then **access routers**, then **tier-1 switches**, then **tier-2 switches**, then **TOR (tier-3) switches**, then servers. Links are Ethernet (copper and fiber). There is redundancy for high availability (e.g., each TOR connects to two tier-2 switches). The hosts under each access router form one **subnet**, which is partitioned into smaller **VLANs** of a few hundred hosts to **localize ARP broadcasts.**

**The limited host-to-host capacity problem.** Example: hosts connect at **10 Gbps**; switch-to-switch links are **100 Gbps.** Hosts in the **same rack** talk at the full 10 Gbps. But if **40 flows** (10 flows from each of racks 1 to 4 to racks 5 to 8) all cross a single **100 Gbps** link, each gets **100/40 = 2.5 Gbps**, far below 10 Gbps. Solutions:
1. **Faster switches and routers** (very expensive).
2. **Co-locate** related services and data (limited, because placement flexibility is needed).
3. **More connectivity between tiers** (Figure 6.31): each TOR connects to **several tier-2 switches**, which connect to several tier-1 switches. This gives **more capacity and more reliability** (path diversity). (Facebook: each TOR connects to **4** tier-2 switches, each tier-2 switch to **4 of the 48** tier-1 switches in its plane, with **4 planes.**)

**Multipath routing.** With many paths, flows are **multipath by default.** A simple scheme is **ECMP (Equal Cost Multi-Path)**, which does a **randomized next-hop choice** per flow. More advanced schemes balance more finely, or even spread **individual packets** of a flow over multiple paths.

### 6.6.2 Trends in data center networking

| Trend | Details |
|---|---|
| **Cost reduction / tiered networks** | A hierarchy of many **small commodity switches** acts like one huge **crossbar** switch but with multiple paths and better reliability. Such multistage networks are called **Clos networks.** Switches are often built from **merchant silicon.** (Google's Jupiter: TOR has 48 links to servers and 8 up to tier-2; a tier-2 switch connects 256 TORs and 16 tier-1 switches.) |
| **Centralized SDN control** | One organization manages the whole data center, so many adopt **SDN-like logically centralized control**, with simple commodity data-plane switches and a software control plane. |
| **Virtualization** | **VMs** can migrate between servers in different racks, but standard Ethernet/IP struggles to keep connections alive. Solution: treat the whole data center as **one flat layer-2 network** and replace ARP broadcast with a **DNS-style directory query** that maps a VM's IP to its current switch. |
| **Physical constraints** | Very high capacity (40/100 Gbps) and **microsecond delays**, so buffers are small and standard TCP congestion control does not scale well. Needs fast reactions in **very low loss** regimes: data-center TCP variants, **RDMA** on Ethernet, etc. |
| **Hardware modularity and customization** | **Shipping-container modular data centers (MDCs)**: a 12-meter container holds a "mini data center" (up to a few thousand hosts), and is replaced when too many components have failed (**graceful degradation**). Providers build or customize adapters, switches, TORs and protocols. **Availability zones:** replicate data centers in nearby buildings (a few km apart) for fault tolerance. |

## 6.7 A Day in the Life of a Web Page Request

Bob connects his laptop to the school's Ethernet switch and loads `www.google.com`. This brings together nearly every protocol so far. Setting: school network `68.85.2.0/24`; Comcast provides DNS; the **DHCP server runs inside the router.**

| Phase | What happens |
|---|---|
| **1. DHCP, UDP, IP, Ethernet** (steps 1 to 7) | Bob has no IP address. His laptop builds a **DHCP request**, in a **UDP** segment (dest port **67**, source port **68**), in an **IP** datagram (source `0.0.0.0`, dest `255.255.255.255`), in an **Ethernet** frame to `FF:FF:FF:FF:FF:FF` (source = Bob's MAC `00:16:D3:23:68:8A`). The **switch floods** it; the router (MAC `00:22:6B:45:1F:1B`) receives it and the DHCP server replies with a **DHCP ACK**: IP **68.85.2.101**, DNS server **68.87.71.226**, default gateway **68.85.2.1**, subnet **68.85.2.0/24.** The reply is **unicast** because the **self-learning switch** already knows Bob's port. Bob installs the gateway in his forwarding table. (Only the **last two** DHCP steps are really needed here.) |
| **2. DNS and ARP** (steps 8 to 13) | The browser needs Google's IP. The laptop builds a **DNS query** (UDP, dest port **53**) addressed to **68.87.71.226.** To send it to the gateway, it needs the gateway's **MAC**, so it sends an **ARP query** (broadcast frame) for 68.85.2.1; the router answers with its MAC `00:22:6B:45:1F:1B`. Now the DNS frame goes out with **destination MAC = gateway**, while the **IP destination = DNS server.** |
| **3. Intra-domain routing to the DNS server** (steps 14 to 17) | The school router, then the Comcast routers forward the datagram using tables built by **RIP/OSPF/IS-IS** and **BGP.** The DNS server finds the cached record and replies with **64.233.169.105.** |
| **4. TCP and HTTP** (steps 18 to 24) | Bob's laptop opens a **TCP socket** to port **80**: **SYN**, **SYNACK**, **ACK** (3-way handshake), forwarded through the school, Comcast and Google networks (inter-domain links are governed by **BGP**). Google's server makes a connection socket. Bob's browser sends the **HTTP GET**; the server replies with the HTML in an **HTTP response**; the browser displays the page. |

**What to notice:** the **MAC addresses change at every hop** while the **IP addresses stay put**; broadcast is used when **no address is known yet** (DHCP, ARP); the switch **learns** where Bob is from his first frame.

## 6.8 Chapter 6: Key Takeaways

- The link layer moves a datagram across **one link** inside a **frame**; services: **framing, link access, reliable delivery, flow control, error detection and correction.** It lives mostly in the **adapter (NIC)**, in hardware.
- **Parity** detects odd numbers of errors (2D parity corrects one); the **Internet checksum** is weak but fast (software); **CRC** (modulo-2 division, R = remainder of D·2^r ÷ G) is strong and used in hardware (Ethernet, 802.11).
- **Multiple access:** **channel partitioning** (TDM, FDM, CDMA), **random access** (slotted ALOHA max **37%**, pure ALOHA max **18%**, CSMA, **CSMA/CD** with **binary exponential backoff**), **taking turns** (polling, token passing). **Cable (DOCSIS)** uses all of them.
- **MAC addresses** are **48-bit, flat, portable**; **ARP** maps **IP to MAC** on **one subnet** using a **broadcast query** and a **unicast reply.** Across subnets, **IP stays the same and MACs change each hop.**
- **Ethernet:** connectionless and unreliable; frame = preamble, dest, source, type, data (46 to 1500), CRC; evolved from **bus to hub to switch.**
- **Switches** are **self-learning** (learn source MACs, **flood** unknown destinations, **filter** same-segment frames), plug-and-play and collision-free. **Routers** are layer-3, not plug-and-play, but isolate broadcasts and use the best path.
- **VLANs** split one physical switch into several broadcast domains; **trunk ports** carry **802.1Q** frames (4-byte tag, 12-bit VLAN ID).
- **MPLS** forwards on **fixed-length labels** and enables **traffic engineering**, fast restoration and VPNs.
- **Data centers** use tiered **Clos-style** topologies of many small switches, **load balancers**, **ECMP**, SDN control and virtualization.
- A web request touches **DHCP, UDP, IP, Ethernet, ARP, DNS, routing (OSPF/BGP), TCP and HTTP.**
