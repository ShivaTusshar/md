# Concurrency: An Introduction — Complete Concept Guide

This is the start of the **second pillar** of the course. Your earlier guides (Virtual Memory, Syscall Entry/Exit, Page Faults) were all about **one process at a time**, protected in isolation. Concurrency is the opposite problem: **multiple independent flows of execution that deliberately share state**, and the surprising, often broken things that happen when their timing isn't controlled. Nothing here depends on Sv39, PTEs, or traps — it's a fresh, self-contained topic, though it will eventually reuse the trap/scheduling machinery from earlier parts of the course (a thread still needs the OS to context-switch it, same as a process).

## PART 0 — The Peach Analogy (Setting Up the Whole Problem)

The dialogue chapter builds the entire concurrency problem from a physical scenario before ever mentioning code, and it's worth carrying the analogy forward because every later technical term maps onto it directly:

> Many peaches on a table, many people who want to eat one.

**Naive approach**: each person looks at a peach, then reaches for it.
**Problem**: two people can look at the *same* peach, and only one of them actually gets it — the other reaches and finds nothing. The looking (checking availability) and the grabbing (acting on it) are two separate steps, and something can happen **in between** them that invalidates what you saw.

**Fix #1 — a line (strict serialization)**: everyone goes one at a time. This is **correct** — no more clashes — but now **only one person can act at a time**, even though nothing stops multiple people from safely grabbing *different* peaches simultaneously. This is **correct but slow**.

**The real goal, stated by the student and confirmed by the professor as "everything you need to know about concurrency":**
> We want something that is **both fast and correct** — not just one or the other.

### Mapping the analogy directly onto threads
| Peach scenario | Concurrency term |
|---|---|
| A peach on the table | A location in shared memory |
| Looking, then reaching (two separate steps) | A **critical section** — code that touches shared state in more than one step |
| Two people going for the same peach | A **race condition** |
| Whoever's timing happens to win gets the peach | An **indeterminate** outcome |
| Forming a line so only one person acts at a time | **Mutual exclusion** |
| Wanting both correctness *and* speed | The entire remaining goal of every synchronization primitive this section of the course builds |

Two more things the dialogue is careful to establish, briefly but pointedly:
- **Why this belongs in an OS course, not just "application programming":** two separate reasons. First, the **OS must provide the primitives** (locks, condition variables — coming in later chapters) that multi-threaded applications use to solve this problem themselves. Second, and just as importantly: **the OS itself was the very first concurrent program** — it must access its own internal memory (page tables, process lists, free lists — all the structures from your earlier VM guides) very carefully, or "many strange and terrible things will happen."

## PART 1 — What a Thread Actually Is

### 1.1 A thread vs. a process
A process, as covered in your earlier guides, has a single point of execution: one program counter, one register set, one address space. A **thread** is *almost* a separate process, except for one crucial difference:

> **Each thread is very much like a separate process, except for one difference: they share the same address space and thus can access the same data.**

A **multi-threaded process** therefore has **multiple points of execution simultaneously** — multiple PCs, each independently fetching and executing instructions — all operating inside the *same* address space.

### 1.2 What state is per-thread, and what's shared
This distinction is the single most important thing to get right about threads, since it directly explains why the "shared data" problem (Part 2) exists at all:

| Per-thread (private) | Shared across all threads in the process |
|---|---|
| Program counter (PC) | Code |
| Register set | Heap |
| Stack | Global/static variables |
| **TCB** (thread control block) | The page table / address space itself |

### 1.3 The context switch, compared to processes
Switching from one thread to another looks almost identical to a process context switch (register state of the outgoing thread saved, register state of the incoming thread restored) — with **one major difference**:

> **The address space remains the same** — there is no need to switch which page table is in use.

This is directly connected to your earlier VM guide's Part 5.5: switching page tables means writing `satp` and issuing `sfence.vma`. **A thread-to-thread context switch skips both of those steps entirely**, because both threads already share the exact same page table. This is one concrete reason threads are often described as "cheaper" than processes to switch between.

Per-process bookkeeping used a **PCB** (process control block); per-thread bookkeeping needs its own analogous structure — a **TCB** (thread control block) — since a process with multiple threads now has multiple independent register/PC states to save and restore, not just one.

### 1.4 The other major difference: the stack
In a classic single-threaded process (your earlier VM guide's Part 1.3), there's exactly one stack, conventionally at one end of the address space, growing toward the heap at the other end.

```
Single-threaded                  Multi-threaded (2 threads)
┌──────────────┐  0KB            ┌──────────────┐  0KB
│ Program Code  │                │ Program Code  │
├──────────────┤  1KB            ├──────────────┤  1KB
│ Heap          │                │ Heap          │
├──────────────┤  2KB            ├──────────────┤  2KB
│               │                │ (free)        │
│  (free)       │                ├──────────────┤
│               │                │ Stack (2)     │
│               │                ├──────────────┤
│               │                │  (free)       │
├──────────────┤ 15KB            ├──────────────┤
│ Stack         │                │ Stack (1)     │
└──────────────┘ 16KB            └──────────────┘  16KB
```

**A multi-threaded process needs one stack per thread**, not one shared stack — since each thread independently calls into routines, needs its own local variables, its own return addresses, and its own call chain, entirely separate from what any other thread is doing. Stack-allocated data (locals, parameters, return values) for a given thread therefore lives in what's called **thread-local storage** — the specific stack belonging to that specific thread.

**Consequence worth noting explicitly**: this "ruins" the clean single-threaded layout where heap and stack could each grow freely into one shared gap (recall the earlier VM guide's discussion of heap-grows-up/stack-grows-down). With multiple stacks squeezed into the same address space, they can't all have unlimited room to grow — but this is usually fine in practice, since stacks don't normally need to be very large (the flagged exception: **programs that make heavy use of recursion**, which can run a stack out of its allotted room).

## PART 2 — Why Use Threads At All? (Two Genuine Reasons)

### 2.1 Reason 1: Parallelism
If you're operating on a large array (e.g., adding two arrays together, or incrementing every element), a single processor must do this one operation at a time. But on a system with **multiple physical processors**, you can split the work — one thread per CPU, each handling a portion — and get real speedup. This transformation (single-threaded → multi-CPU-exploiting) is called **parallelization**, and one-thread-per-CPU is the natural, typical way to achieve it on modern hardware.

### 2.2 Reason 2: Avoiding I/O-related blocking
This is described as "a bit more subtle." Consider a program that does various kinds of I/O — waiting to send/receive a network message, waiting for a disk operation to finish, or even (implicitly) **waiting for a page fault to complete** — a direct callback to your earlier Page Faults guide, where a fault genuinely does require the CPU to wait while the kernel does work (allocate, read from disk/file, map). Rather than the whole program sitting idle during that wait, it can use a **separate thread** to do something else useful — more computation, or issuing further I/O requests — while the first thread blocks. **The CPU scheduler switches to other ready threads whenever one blocks**, letting I/O and computation overlap within a single program, much the way multiprogramming (from your earlier VM guide's Part 1.1) overlapped I/O and computation *across* different programs. This is exactly why server-based software — web servers, database systems — makes heavy use of threads.

### 2.3 Why threads and not just multiple processes?
Both of the above *could* technically be done with separate processes instead of threads. The deciding factor: **threads share an address space, so sharing data between them is trivial** (just read/write the same variable) — making threads the natural choice whenever the concurrent tasks genuinely need to cooperate closely on shared data structures. **Processes** remain the better choice for logically separate tasks that need little or no memory sharing (which is exactly the isolation goal your earlier VM guide built an entire virtual-memory system to enforce).

## PART 3 — Thread Creation, and Why Ordering Is Unpredictable

### 3.1 The example program
```c
void *mythread(void *arg) {
    printf("%s\n", (char *) arg);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p1, p2;
    printf("main: begin\n");
    Pthread_create(&p1, NULL, mythread, "A");
    Pthread_create(&p2, NULL, mythread, "B");
    Pthread_join(p1, NULL);   // wait for T1 to finish
    Pthread_join(p2, NULL);   // wait for T2 to finish
    printf("main: end\n");
    return 0;
}
```
`main` creates two threads (call them **T1** and **T2**), each running `mythread()` with a different argument, then calls `pthread_join()` **twice** — once per thread — which blocks until that specific thread has finished. Only after *both* joins return does `main` print "main: end". **Three threads total participate**: the main thread, T1, and T2.

### 3.2 Thread creation is like a function call, with a twist
> "It is a bit like making a function call; however, instead of first executing the function and then returning to the caller, the system instead creates a new thread of execution for the routine being called, and it runs independently of the caller — perhaps before returning from the create, but perhaps much later."

The key word is **independently**. Once `pthread_create()` returns, there's no guarantee about *when* the new thread actually starts running relative to the calling code that continues after the create call — that's entirely up to the OS scheduler.

### 3.3 Three different, all-legal execution orderings
The whole point of walking through multiple traces here is to demonstrate that **there is no single "the" execution order** — the scheduler could legitimately produce any of these:

**Trace 1 — main waits, then each thread runs fully in turn:**
```
main: starts, prints "main: begin", creates T1, creates T2, waits for T1
                                              T1 runs, prints "A", returns
main: waits for T2
                                                            T2 runs, prints "B", returns
main: prints "main: end"
```

**Trace 2 — each thread runs immediately upon creation, before the next create even happens:**
```
main: starts, prints "main: begin", creates T1
                                              T1 runs, prints "A", returns
main: creates T2
                                                            T2 runs, prints "B", returns
main: waits for T1 → returns immediately, T1 already done
main: waits for T2 → returns immediately, T2 already done
main: prints "main: end"
```

**Trace 3 — T2 runs before T1, even though T1 was created first:**
```
main: starts, prints "main: begin", creates T1, creates T2
                                                            T2 runs, prints "B", returns
main: waits for T1
                                              T1 runs, prints "A", returns
main: waits for T2 → returns immediately, T2 already done
main: prints "main: end"
```

**The lesson, stated directly**: *"there is no reason to assume that a thread that is created first will run first."* Creation order and execution order are entirely independent facts, decided by the scheduler, not by the program.

### 3.4 The foreshadowing line
> "As you might also be able to tell from this example, threads make life complicated: it is already hard to tell what will run when! Computers are hard enough to understand without concurrency. Unfortunately, with concurrency, it simply gets worse. Much worse."

This is deliberately setting up Part 4 — and note that this example (Part 3) has **no shared mutable data being updated** at all; each thread only prints its own private string argument. The ordering is unpredictable, but the *outcome* (both letters get printed, exactly once each) is still always correct regardless of interleaving. Part 4 is where unpredictable ordering starts actually **breaking correctness**.

## PART 4 — Why It Gets Worse: Shared Data

### 4.1 The example
```c
static volatile int counter = 0;

void *mythread(void *arg) {
    printf("%s: begin\n", (char *) arg);
    int i;
    for (i = 0; i < 1e7; i++) {
        counter = counter + 1;
    }
    printf("%s: done\n", (char *) arg);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p1, p2;
    printf("main: begin (counter = %d)\n", counter);
    Pthread_create(&p1, NULL, mythread, "A");
    Pthread_create(&p2, NULL, mythread, "B");
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("main: done with both (counter = %d)\n", counter);
    return 0;
}
```
Two threads, each incrementing a **single shared global variable** 10 million times. **Expected final result: 20,000,000** (10 million + 10 million).

### 4.2 What actually happens
Sometimes, the expected result appears:
```
main: done with both (counter = 20000000)
```
But other runs — on the **exact same compiled binary, on the same machine** — give:
```
main: done with both (counter = 19345221)
main: done with both (counter = 19221041)
```
**Different every time.** This directly violates the intuitive expectation that "computers produce deterministic results" — and the chapter poses this pointedly as the central mystery to resolve: *why does this happen, and why is it different each time?*

## PART 5 — The Heart of the Problem: Uncontrolled Scheduling

### 5.1 What "one line of C" actually compiles to
`counter = counter + 1;` is not a single hardware operation — it compiles (in this x86 example) into **three separate instructions**:
```asm
mov 0x8049a1c, %eax   ; load counter's current value into register eax
add $0x1, %eax        ; increment the register (not memory!) by 1
mov %eax, 0x8049a1c   ; store the register's new value back into counter
```
**This is the entire root cause.** The "single conceptual step" of incrementing a shared variable is, at the hardware level, a **read**, then a **modify**, then a **write** — three distinct steps, with a window in between each one where the CPU could be interrupted and switched to a different thread.

### 5.2 The failure, traced step by step
Assume `counter` starts at 50.

1. **T1** runs `mov` → T1's `eax = 50`.
2. **T1** runs `add` → T1's `eax = 51`. (Note: `counter` in memory is *still* 50 — only T1's private register has changed so far.)
3. **Timer interrupt fires.** The OS saves T1's full state (PC, registers including `eax=51`) into T1's TCB.
4. **T2 is scheduled to run.** It enters the *same* code. Its own private `eax` starts fresh: T2 runs `mov` → T2's `eax = 50` (still reading the same, unmodified `counter = 50` from memory, since T1 never wrote its result back).
5. T2 runs `add` → T2's `eax = 51`. T2 runs the final `mov` → **`counter` in memory becomes 51.**
6. **Another context switch — T1 resumes.** T1 had already executed its `mov` and `add`; it was paused right before its own final `mov`. T1's saved `eax` is restored as `51` (from its TCB). T1 now executes its final `mov` → **`counter` in memory is set to 51 again** (overwriting T2's already-correct update with the *same* stale value T1 computed earlier).

**Net result: the increment code ran twice, `counter` started at 50, and ended at 51 — one entire increment was silently lost.** A correct execution should have produced 52.

### 5.3 The detailed instruction/register/memory trace
Assuming the code sits at addresses 100 (mov, 5 bytes on x86), 105 (add, 3 bytes), 108 (final mov):

| OS event | Thread 1 | Thread 2 | PC | eax | counter |
|---|---|---|---|---|---|
| | (before critical section) | | 100 | 0 | 50 |
| | `mov 8049a1c,%eax` | | 105 | 50 | 50 |
| | `add $0x1,%eax` | | 108 | 51 | 50 |
| interrupt: save T1, restore T2 | | | 100 | 0 | 50 |
| | | `mov 8049a1c,%eax` | 105 | 50 | 50 |
| | | `add $0x1,%eax` | 108 | 51 | 50 |
| | | `mov %eax,8049a1c` | 113 | 51 | **51** |
| interrupt: save T2, restore T1 | | | 108 | 51 | 51 |
| | `mov %eax,8049a1c` | | 113 | 51 | **51** |

Note the "PC/eax" columns are **per-thread private state** (exactly Part 1.2's table made concrete) — each thread has its *own* `eax` value the whole time; the only thing genuinely *shared* in this entire trace is the single memory location `counter`, and that's precisely where the collision happens.

### 5.4 The vocabulary this failure earns
- **Race condition** (or more specifically, **data race**): the result depends on the exact timing of execution — specifically, on precisely when an untimely context switch happens to land.
- **Indeterminate**: running the *same* program on the *same* input can produce **different outputs on different runs**, purely due to scheduling timing. This is a direct violation of the "computers are deterministic" intuition most programmers start with.
- **Critical section**: a piece of code that accesses a shared variable (or more generally, a shared resource) and **must not be concurrently executed by more than one thread** — `counter = counter + 1;` is exactly such a critical section.
- **Mutual exclusion**: the property we actually want — a guarantee that **if one thread is executing inside the critical section, all others are prevented from doing so** until it's done. This is the formal name for "form a line" from Part 0's peach analogy.

**Historical note**: all four of these terms were coined by **Edsger Dijkstra**, whose 1968 paper *"Cooperating Sequential Processes"* is credited as an exceptionally clear early description of this entire problem — he developed much of this thinking while working on the "THE" operating system.

## PART 6 — The Wish for Atomicity

### 6.1 The hypothetical fix: a single, more powerful instruction
If hardware offered one instruction like:
```asm
memory-add 0x8049a1c, $0x1
```
that performed load-modify-store as **one indivisible unit**, this whole problem would vanish — an interrupt could never land *in the middle* of it, because there is no "middle" as far as anything else in the system can observe: **either the instruction has not run at all, or it has run to completion; no in-between state is ever visible.**

### 6.2 What "atomic" means, precisely
> **Atomically** means "as a unit" — "all or none." No observer (including a context-switching OS) can ever see a partially-completed atomic operation.

This is stated as a genuinely deep, broadly recurring idea in computer systems — not just for concurrency, but also (with a forward-reference, since your course will reach these topics later) for **file systems**, which use techniques like **journaling** or **copy-on-write** (a term you've already encountered in the Page Faults guide, though for an entirely different purpose there — atomically transitioning on-disk state after a crash) — and for **database transactions** (grouping many operations so that either *all* of them take effect or *none* do).

### 6.3 Why we can't just ask hardware for infinite atomic instructions
The chapter poses a deliberately absurd counter-example: would we want hardware to offer an "atomically update this entire B-tree" instruction? Obviously not — that's far too specific a piece of policy to bake into silicon. **The real approach**: hardware provides a **small number of simple, general-purpose atomic primitives**, and software builds general **synchronization primitives** (locks, and later condition variables) on top of them, combined with OS support. This is the exact same mechanism-vs-policy split from your earlier VM guide (Part 4.6, and the RISC-V `ecall` minimalism discussion in the Syscall guide's Part 6.2) — applied here to a completely different hardware feature: **hardware gives you a handful of atomic instructions; software builds everything else** (locks, mutexes, semaphores — the subjects of the chapters that come right after this one).

**The three questions this whole upcoming unit of the course exists to answer, stated explicitly:**
1. What support do we need from the **hardware**?
2. What support do we need from the **OS**?
3. How do we build these primitives **correctly and efficiently**, and how do programs actually **use** them?

## PART 7 — One More Problem: Waiting for Another Thread

This section deliberately distinguishes **two different kinds of thread interaction**, since it's easy to conflate them:

1. **Mutual-exclusion problems** (everything in Parts 4–6): multiple threads racing to access the *same* shared data at *roughly the same time*.
2. **A genuinely different interaction**: one thread must **wait** for another to finish some action before it can continue — not because they're racing over the same data right now, but because there's a real *dependency* in time. The example given: a process performs a disk I/O and is put to sleep; when that I/O completes, the process needs to be **woken up** so it can proceed.

The chapter explicitly flags this second interaction as requiring **different machinery** than mutual exclusion alone — sleeping/waking support, which is the subject of a later chapter on **condition variables**. This guide's job is just to name that this second problem exists and is genuinely distinct from the first — the actual mechanism (condition variables) is deliberately deferred to later material, matching how the source chapter itself handles it.

## PART 8 — Why This Belongs in an OS Course

The chapter's own one-word answer: **history**. **The OS was the first concurrent program** — long before multi-threaded application programming existed, OS designers already had to solve this exact problem for the kernel's own internal data structures.

### 8.1 A worked example: two processes both appending to the same file
Imagine two processes both call `write()` to **append** data to the same file (increasing its length). To do this correctly, the kernel must, for each process: allocate a new disk block, record that new block's location in the file's **inode**, and update the file's recorded size. **Because an interrupt can occur at any time**, the code performing these updates — modifying a shared allocation bitmap, or a shared inode — is **exactly a critical section**, in the same sense as `counter = counter + 1;` in Part 4. If both processes' kernel-mode code interleaves badly while updating the same inode or the same free-block bitmap, the file system's on-disk structures can end up corrupted, in a way directly analogous to the "lost update" in Part 5.2 — except now the "lost update" is a filesystem structure instead of an integer, which is a far more serious kind of bug.

### 8.2 The generalization
> "Not surprisingly, page tables, process lists, file system structures, and virtually every kernel data structure has to be carefully accessed, with the proper synchronization primitives, to work correctly."

This directly connects back to structures you've already studied in earlier guides — the free-page list (`palloc`/`pfree`, from your VM guide's Part 6.8), the process table, page tables themselves — **every one of those is a shared kernel data structure that multiple execution contexts (interrupt handlers, multiple CPU cores, multiple processes making syscalls concurrently) can touch**, and every one of them is therefore a potential critical section requiring careful synchronization, using exactly the primitives this new part of the course is about to build.

## Quick-Reference: The Four Key Terms (as the source explicitly calls them out)
| Term | Definition |
|---|---|
| **Critical section** | A piece of code that accesses a shared resource (usually a variable or data structure) |
| **Race condition** (data race) | Arises when multiple threads enter a critical section at roughly the same time, both attempting to update shared data, producing a surprising/undesirable outcome |
| **Indeterminate** (program) | A program containing one or more race conditions, whose output varies from run to run depending on which threads ran when |
| **Mutual exclusion** | The property, provided by synchronization primitives, that guarantees only a single thread ever enters a critical section at a time — avoiding races and restoring deterministic output |

## Quick-Reference: Thread vs. Process, One More Time
| | Process | Thread |
|---|---|---|
| Address space | Private | **Shared** with sibling threads in the same process |
| PC, registers, stack | Private | Private (own TCB, own stack) |
| Context switch cost | Includes page-table switch (`satp` + `sfence.vma`, per the VM guide) | **No** page-table switch needed — same address space throughout |
| Natural use case | Logically separate tasks, little data sharing needed | Tasks that need to cooperate closely on shared data |
