## PART 1 — Four Words That Must Not Be Confused: Core, Hart, Process, Thread

| Term | Meaning in this lecture |
|---|---|
| **Core** | A physical processor implementation — actual silicon. |
| **Hart** | A RISC-V **hardware execution context** — has its own architectural state (registers, PC, CSRs). RISC-V's own term for "a thing that can independently fetch and execute instructions in hardware." |
| **Process** | A resource-and-protection container: address space, open files, PID. (Everything your VM guide built.) |
| **Software thread** | An **independently schedulable execution stream inside a process** — a *software/OS* concept, not a hardware one. |

**The rule stated explicitly**: *do not confuse a RISC-V hart with a software thread.* A hart is a piece of hardware that can run instructions; a software thread is an OS-level bookkeeping concept the scheduler assigns to run *on* some hart, for some stretch of time. One hart can run many different software threads over time (via context switches); conversely, a system can have far more software threads than harts, all sharing the limited number of harts through scheduling.

## PART 2 — The Bridge From VM: Per-Hart CSRs, Shared Page Tables

### 2.1 Each hart has its own private register file
```
Hart 0                          Hart 1
x0–x31                          x0–x31
pc                               pc
sstatus                          sstatus
sepc / scause / stval            sepc / scause / stval
satp                             satp
```
**These are separate hardware states.** `Hart 0.satp` and `Hart 1.satp` are physically different registers — recall from the earlier VM guide's Part 5.5 that `satp` holds the physical address of the active page-table root; here the key addition is that **there is one `satp` per hart**, not one per machine.

### 2.2 The precise statement about `satp` and sharing
> **Two harts may run the same address space.**

```
                     Process P
                page table root PT_P
                         │
          ┌──────────────┴──────────────┐
        Hart 0                        Hart 1
      T0 running                    T1 running
   H0.satp = PT_P               H1.satp = PT_P
```
The CSRs themselves are per-hart, private hardware — but **their values can point at the exact same physical page-table root**. This is the crucial fact that makes multi-threading on multiple cores possible at all: two harts, each with their own independent registers and CSR state, can nonetheless both be "inside" the same process's address space simultaneously, because `satp` is just a pointer, and two different pointers (in two different registers) can hold the identical value.

### 2.3 The table worth memorizing: thread switch vs. process switch
| Switch | Registers / PC / SP | Address space / `satp` value |
|---|---|---|
| P:T0 → P:T1 (same process, different thread) | change | **same** page-table root |
| P:T0 → Q:T0 (different process) | change | **different** page-table root |
| P:T0 on H0 *and* P:T1 on H1 (simultaneously, on two harts) | independent on both harts | **both** `satp` CSRs point to `PT_P` |

> **A thread is execution state. An address space is process state.**

This one sentence is the cleanest possible summary of everything in Part 1 of your earlier Concurrency guide, restated in hardware terms: switching *threads* only ever touches registers/PC/SP; switching *address spaces* is the only thing that ever touches `satp` (and correspondingly requires the `sfence.vma` discipline from the earlier VM guide's Part 5.5).

## PART 3 — Current Luit: Processes, Not (Yet) POSIX-Style User Threads

### 3.1 The honest baseline
```
struct proc
├── address space          ┐
├── trapframe / context    ├─  ONE address space + ONE execution context, bundled together
├── kernel stack           │
├── state / PID            │
└── open files             ┘
```
Baseline Luit's `struct proc` bundles **exactly one address space together with exactly one execution context** — there is no separate notion of "a schedulable thing" apart from "a process." **This is explicitly named as a divergence from OSTEP Chapter 27**, which assumes a pthreads-style world where a single process can contain many independently-schedulable threads. The lecture is careful not to let this go unstated, since a student reading OSTEP's pthread examples and then looking at Luit's `struct proc` could otherwise be confused about why there's no `pthread_create()` equivalent in the kernel baseline.

### 3.2 What Luit would need, if it *did* have user threads
The fix is to **split what's currently bundled together** — separate the resource container from the execution state:

| Shared process state | Per-thread execution state |
|---|---|
| page table / address space | PC and general registers |
| code, globals, heap | user stack and stack pointer |
| open files and cwd | trapframe and kernel stack |
| PID / address-space lifetime | TID and scheduler context |

> **The thread abstraction does not duplicate the address space; it duplicates the execution context.**

This is the single sentence that answers "what actually changes if Luit grows user threads?" — you'd add more `(PC, registers, stack, trapframe, kernel stack)` tuples per process, but you would **not** create a second page table, a second open-file table, or a second PID for each new thread. Exactly mirroring the shared-vs-private split from your earlier Concurrency guide's Part 1.2, now spelled out down to which specific kernel structures would need to multiply and which wouldn't.

## PART 4 — Why Concurrency At All? (Restated Crisply)

| Motivation | Meaning |
|---|---|
| **Parallelism** | Use multiple harts/cores to finish one job faster. |
| **Overlap with I/O** | Run useful work while another execution stream waits (disk, network, or — per your earlier Concurrency guide's Part 2.2 — a page fault). |
| **Structure** | Split program logic into cooperating activities, even on a single core, for cleaner design. |

> **The danger is not concurrency itself; the danger is unsafely shared mutable state.**

This one-liner is worth holding onto for a viva: it's tempting to say "concurrency is dangerous," but that's imprecise — a program with many threads that never touch the same mutable data has **zero** race-condition risk, no matter how many threads it has. The risk comes specifically from **sharing** plus **mutation** plus **no coordination** — all three conditions, together.

### 4.1 Processes isolate; threads share
| Many processes | Many threads in one process |
|---|---|
| separate address spaces | one address space |
| better fault isolation | cheap shared-memory communication |
| IPC needed to communicate | ordinary loads/stores can communicate |
| context switch may change `satp` root | thread switch in same process keeps same root |

This table is the exact trade-off your earlier VM guide flagged repeatedly at the page-table level (isolation vs. sharing cost) — now applied explicitly to the choice between processes and threads as a *design decision a programmer makes*, rather than something baked into the hardware.

## PART 5 — Definition, Address Space Layout, and the Scheduler's View

### 5.1 The formal definition
> **A software thread is an independently schedulable execution stream within a process.**
> Process = resources and protection. Thread = running state.

### 5.2 Threads share memory, but not their stacks
```
code
globals
heap
─────────────────  (free VA region)
stack T1
─────────────────  (free VA region)
stack T0
```
Each thread has its own call chain, so it needs its **own stack pointer and own user stack**. Local variables and return addresses are per-thread precisely *because* they live in stack frames — this is the same conclusion your earlier Concurrency guide's Part 1.4 reached from the OSTEP figure, drawn here with explicit "free VA region" gaps between stacks (a direct nod to the fact that, per that same earlier guide, squeezing multiple stacks into one address space means none of them gets unlimited room to grow).

### 5.3 The complete shared/private table
| Shared by threads of one process | Private to each thread |
|---|---|
| page table / address space | PC |
| code | general-purpose registers |
| globals and heap | SP and user stack |
| open file table | trapframe / saved context |
| current working directory | kernel stack |

> "This is the table that explains both speed and danger" — **speed**, because a thread switch touches only the small "private" column (cheap: no `satp`/`sfence.vma`); **danger**, because anything in the "shared" column is a potential race if multiple threads touch it without coordination.

### 5.4 The scheduler's actual job
The scheduler's job, restated in this hardware-grounded vocabulary: **choose which execution context runs on which hart, right now** — e.g., Process A's T0 and T1 might be runnable at once, and the scheduler could place T0 on Hart 0 and T1 on Hart 1 simultaneously, while Process B's T0 waits its turn. Baseline Luit doesn't expose user-level threads for this to operate over yet (Part 3.1), but **the kernel scheduler already does exactly this job across multiple harts, for multiple processes** — which is precisely the seed of Part 8's "the kernel is already concurrent" pivot.

## PART 6 — The First Concurrency Bug, Restated With RISC-V Assembly

This is the exact bug from your earlier Concurrency guide's Parts 4–5, but with **RISC-V** instructions instead of x86, and one genuinely new insight about single-hart races.

### 6.1 The canonical example
```c
static volatile int counter = 0;

void *worker(void *arg) {
    for (int i = 0; i < loops; i++)
        counter = counter + 1;
    return NULL;
}
// main creates two worker threads and joins them
```
**Expected**: `2 × loops`. **Observed**: changes across runs. *"The input is the same; the schedule is different."*

### 6.2 A common mistake: `volatile` does not make this atomic
This is a genuinely important clarification the earlier guide didn't cover in this much detail:
- `volatile` may force the compiler to **actually perform** the memory accesses (rather than, say, optimizing them into a register that's never written back) — it's a compiler-optimization directive.
- It does **not** combine load, add, and store into one indivisible operation.
- It does **not** stop another hart or thread from accessing the same memory location concurrently.
- **Correct synchronization needs a lock or another atomic mechanism** — this is the single clearest way the lecture states why the next lecture (locks) is unavoidable.

### 6.3 The RISC-V lowering of `counter = counter + 1`
```asm
lw   t0, 0(a0)      # load counter
addi t0, t0, 1      # increment local register
sw   t0, 0(a0)      # store counter back
```
Exactly the same structural bug as the x86 `mov`/`add`/`mov` from your earlier guide — **"the single C statement is not a single memory action."** The exact register names differ by compiler/architecture, but the load-modify-store shape is universal.

### 6.4 The interleaving trace
| T0 / Hart 0 | T1 / Hart 1 | counter |
|---|---|---|
| `lw` → t0 = 100 | | 100 |
| `addi` → t0 = 101 | | 100 |
| | `lw` → t0 = 100 | 100 |
| | `addi` → t0 = 101 | 100 |
| | `sw` → counter = 101 | 101 |
| `sw` → counter = 101 | | 101 |

**Expected: 102. Actual: 101.** Identical structure to your earlier guide's Part 5.3 x86 trace — one increment silently lost.

### 6.5 The genuinely new point: a race does not require two harts
| Single-hart timeline | What happens |
|---|---|
| T0: `lw`; `addi` | T0 has 101 sitting in its **private register** (not yet written to memory) |
| timer interrupt | scheduler runs |
| T1: `lw`; `addi`; `sw` | counter becomes 101 |
| T0 resumes: `sw` | counter **remains** 101 |

> **Parallelism makes races easier to observe, but interleaving alone is enough.**

This is a subtlety worth being precise about in a viva: you do **not** need two physical harts running literally simultaneously to get this bug — a single hart, with the OS **switching between two software threads via ordinary timer-interrupt-driven context switches**, produces the *exact same* lost update, because the failure mode is about the **timing of when work becomes visible in shared memory**, not about literal simultaneity. **Concurrency ≠ parallelism**: concurrency is about multiple logically-independent things making progress (possibly overlapped in time, possibly just interleaved); parallelism specifically means multiple things running at the *exact same instant* on separate hardware. A race condition is a concurrency bug, and it exists even with zero parallelism.

## PART 7 — Vocabulary, Restated Precisely
| Term | Meaning |
|---|---|
| **Race condition** | Program correctness depends on timing or interleaving. |
| **Data race** | Specifically: same memory location, concurrent accesses, **at least one write**, **no synchronization**. |
| **Critical section** | Code that accesses shared state and must be coordinated. |
| **Indeterminate** | Same input can produce different outputs. |

(Note the sharpened definition of **data race** here versus the earlier Concurrency guide — this slide deck adds the precise three-part condition: same location + concurrent access + at least one write + no synchronization. A race with only concurrent *reads* and no writes at all is not a data race, since nothing is being mutated.)

## PART 8 — What We Want: Atomicity, Then Mutual Exclusion

### 8.1 Atomicity, restated as a code fiction
```c
atomic {
    counter = counter + 1;
}
// conceptually: nobody observes the middle
```
> "Hardware will not make every C block atomic. The OS and runtime build synchronization from a few atomic instructions."

Identical conclusion to your earlier guide's Part 6.3 — mechanism (a handful of hardware atomic instructions) vs. policy (everything else, built in software).

### 8.2 The first solution idea: mutual exclusion via a lock
```c
lock(&L);
counter = counter + 1;    // critical section
unlock(&L);
```
And the lecture ends this section with the exact question it's deliberately deferring:
> **Question for the next lecture: how can `lock()` itself be implemented without a race?**

This is a genuinely sharp puzzle worth sitting with before the next lecture answers it: `lock()` itself must, at some point, check "is this free?" and then "claim it" — and that check-then-act pattern is *exactly* the same two-step structure that caused the original bug (recall Part 0's peach analogy: look, then grab). So how do you build a *correct* lock out of instructions that are themselves subject to the same interleaving danger? The answer (hardware atomic read-modify-write instructions) is explicitly flagged as "next lecture" material — this guide deliberately doesn't answer it either, matching the source.

## PART 9 — The Luit Pivot: The Kernel Is Already Concurrent

This is the section that most sharply distinguishes this lecture from your earlier, more general Concurrency guide.

### 9.1 The scenario
```
Hart 0                              Hart 1
Process A syscall                   Process B syscall
        │                                  │
        └──────────────┬───────────────────┘
                        ▼
                  LUIT kernel
              shared kernel state
```
**Two different processes, on two different harts, can both be executing kernel code — inside the very same kernel — at the same time**, e.g., because both happened to make a system call simultaneously (recall the Syscall guide's `usertrap()` → `syscall()` path — that entire path is kernel code, and nothing prevents two harts from running it concurrently).

> **So the lock problem is real even before Luit has user-level threads.**

This is the single most important point of divergence to hold onto: **you do not need POSIX-style user threads for the race-condition problem to matter.** Luit's baseline (Part 3.1) has no `pthread_create()` for user programs — but the *kernel itself*, running on multiple harts simultaneously, is already exposed to the exact same danger, because multiple harts executing kernel code concurrently is functionally identical to "multiple threads sharing memory" — the shared memory here is just the kernel's own internal data structures, not a user-level global variable.

### 9.2 Real Luit kernel shared-state examples
| Shared object | Invariant that must survive concurrency |
|---|---|
| **physical-page free list** | a page is allocated to at most one user |
| **PID allocation** | two processes do not get the same PID |
| **process state** | the scheduler never sees inconsistent state transitions |
| **ticks counter** | timer updates and readers see a consistent value |
| **buffer cache** | metadata and buffer ownership remain consistent |

> **A lock protects data and invariants.**

Direct payoff of your earlier Concurrency guide's Part 8: the **physical-page free list** (`palloc`/`pfree`, from the earlier VM guide's Part 6.8, "the next pointer lives inside the free page itself") is exactly this kind of shared kernel structure — if two harts call `palloc()` at the same moment without any coordination, both could read the same freelist head, both could believe they've claimed the same physical page, and **the exact same page could be handed out to two different callers simultaneously** — a direct violation of the "a page is allocated to at most one user" invariant, and a bug of genuinely serious consequence (two processes silently sharing one physical frame, corrupting each other's memory, with no fault ever raised to signal the problem).

### 9.3 The companion map: same concepts, different realization
| OSTEP side | Luit side |
|---|---|
| user threads sharing memory | kernel executions sharing kernel data across harts |
| `pthread_mutex` | spinlock `acquire()`/`release()` |
| condition variable `wait`/`signal` | `sleep(chan, lock)` / `wakeup(chan)` analogue |
| semaphores | built from lock + sleep/wakeup ideas |
| concurrency bugs | duplicate PID, lost wakeup, wrong lock order, deadlock |

**The explicit caution**: *"Do not read this as API equality. It is a conceptual bridge."* A Luit spinlock and a pthread mutex solve the same underlying problem (mutual exclusion) but are not interchangeable, drop-in-compatible APIs — they have different implementations suited to their different contexts (kernel-mode spinning across harts, vs. user-mode blocking via the OS scheduler).

## PART 10 — The pthread API (OSTEP Chapter 27), as Reference

The lecture is explicit: this section is "reference API from OSTEP Chapter 27; not a current Luit user API" — i.e., **this is what OSTEP teaches for user-space programming, and Luit doesn't currently expose an equivalent**, per Part 3.1's named divergence. Learn it as the standard model, and separately understand (Part 11) what Luit would need to add to support it.

### 10.1 `pthread_create` and `pthread_join`
```c
int pthread_create(pthread_t *thread, const pthread_attr_t *attr,
                    void *(*start_routine)(void *), void *arg);
int pthread_join(pthread_t thread, void **value_ptr);
```
Four arguments to `create`:
- **`thread`** — a pointer to a `pthread_t`, which `pthread_create()` initializes; you keep this around to later refer to this specific thread (e.g., to `join` it).
- **`attr`** — thread attributes (stack size, scheduling priority, etc.), set up separately via `pthread_attr_init()`; **`NULL` gives sane defaults**, which is what you'll use in almost all cases.
- **`start_routine`** — a **function pointer**: the function this new thread will begin executing. Its signature is fixed by the API: takes one `void *` argument, returns one `void *` result.
- **`arg`** — the actual argument value passed to `start_routine` when the thread starts.

**Why `void *` everywhere?** A `void *` argument lets you pass **any type** of data into the thread (by casting a pointer to your actual argument struct into `void *`, and casting it back inside the thread function); a `void *` return value symmetrically lets the thread return **any type** of result.

```c
typedef struct { int a; int b; } myarg_t;

void *mythread(void *arg) {
    myarg_t *args = (myarg_t *) arg;
    printf("%d %d\n", args->a, args->b);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p;
    myarg_t args = { 10, 20 };
    int rc = pthread_create(&p, NULL, mythread, &args);
    ...
}
```
Once created, this genuinely *is* a live, independently-executing entity — its own call stack, running inside the same address space as every other thread in this program (Part 5.2's diagram, made concrete).

`pthread_join(thread, &value_ptr)` blocks the calling thread **until** the specified thread finishes, and, via the `void **value_ptr` out-parameter, hands back whatever that thread returned. **Why a pointer to a pointer?** Because the routine's return type is `void *`, and `join` needs to *write* that returned value somewhere the caller can read it — hence a pointer to the location that should receive the `void *` result.

```c
typedef struct { int x; int y; } myret_t;

void *mythread(void *arg) {
    myret_t *rvals = Malloc(sizeof(myret_t));
    rvals->x = 1; rvals->y = 2;
    return (void *) rvals;
}

int main(...) {
    pthread_t p;
    myret_t *rvals;
    myarg_t args = { 10, 20 };
    Pthread_create(&p, NULL, mythread, &args);
    Pthread_join(p, (void **) &rvals);
    printf("returned %d %d\n", rvals->x, rvals->y);
    free(rvals);
    return 0;
}
```

### 10.2 The dangerous mistake: never return a pointer to a stack-allocated variable
```c
void *mythread(void *arg) {
    myarg_t *args = (myarg_t *) arg;
    myret_t oops;              // ALLOCATED ON STACK — BAD!
    oops.x = 1; oops.y = 2;
    return (void *) &oops;     // dangling pointer the instant this function returns
}
```
`oops` lives on `mythread`'s **own private stack** (recall Part 5.3's "private" column — SP and user stack belong to the thread). The instant the function returns, that stack frame is deallocated (that's precisely *why* stacks are cheap and easy — automatic, scope-based cleanup) — so the caller receives a pointer into memory that's no longer validly allocated for this purpose. **Reading through it afterward is undefined behavior** — it might look fine, might print garbage, might crash, non-deterministically, depending on what happens to reuse that stack space next. **The fix, generalized**: to share data between threads (or hand data back via a return value), the data must live in the **heap** or another globally-accessible location — never on a stack frame that's about to be torn down. This is exactly Part 5.3's "private" column made into a concrete bug pattern.

### 10.3 A simpler pattern: pass a single scalar directly
```c
void *mythread(void *arg) {
    long long int value = (long long int) arg;
    printf("%lld\n", value);
    return (void *) (value + 1);
}

int main(...) {
    pthread_t p;
    long long int rvalue;
    Pthread_create(&p, NULL, mythread, (void *) 100);
    Pthread_join(p, (void **) &rvalue);
    printf("returned %lld\n", rvalue);
    return 0;
}
```
When the payload is small enough to fit inside a pointer-sized value, you can skip the struct-packing entirely and just cast the integer directly into and out of the `void *` slots — a common shortcut worth recognizing.

### 10.4 A pointed observation: is `create` + immediate `join` even useful?
> "The use of `pthread_create()` followed by an immediate call to `pthread_join()` is a pretty strange way to create a thread. In fact, there is an easier way to accomplish this exact task; it's called a procedure call."

This is a deliberately dry joke with a real point: if you create exactly one thread and then immediately wait for it before doing anything else, you've gained *nothing* over just calling the function directly — the whole value of threads comes from creating **multiple** threads and letting them run **concurrently** before joining. Note also: **not all multi-threaded code even uses `join`** — a long-lived server that spawns worker threads and never expects them to finish (e.g., a web server accepting requests indefinitely) may simply never join; `join` is specifically for "wait until this piece of work is done," which doesn't apply to workers meant to run forever.

### 10.5 Locks: `pthread_mutex_lock` / `pthread_mutex_unlock`
```c
pthread_mutex_t lock;
pthread_mutex_lock(&lock);
x = x + 1;    // critical section
pthread_mutex_unlock(&lock);
```
Semantics: if no other thread holds the lock, the calling thread acquires it immediately and proceeds. If another thread **does** hold it, the calling thread **blocks inside `pthread_mutex_lock()`** and doesn't return until it successfully acquires the lock (i.e., until whoever holds it calls `unlock`). Many threads may be simultaneously blocked waiting for the same lock; **only the thread that currently holds it should ever call `unlock`**.

**Two real bugs in the snippet above, both worth internalizing as "always check for these":**
1. **Missing initialization.** A lock must be initialized before use, or its internal state is garbage and it won't behave correctly. Two ways:
   ```c
   pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;         // static
   // — or, dynamically at runtime —
   int rc = pthread_mutex_init(&lock, NULL);
   assert(rc == 0);
   ```
   (A corresponding `pthread_mutex_destroy()` should be called when done with a dynamically-initialized lock.)
2. **Missing error checking.** Like virtually any UNIX library call, `lock`/`unlock` **can fail**. Silently ignoring a failed lock call could let multiple threads into a critical section simultaneously — precisely the bug locks exist to prevent. Minimal fix: wrap the calls to assert success:
   ```c
   void Pthread_mutex_lock(pthread_mutex_t *mutex) {
       int rc = pthread_mutex_lock(mutex);
       assert(rc == 0);
   }
   ```
   (Production code that can't simply exit on failure should handle the error properly instead of asserting.)

Two related, generally-avoid-unless-you-know-why variants:
```c
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_timedlock(pthread_mutex_t *mutex, struct timespec *abs_timeout);
```
`trylock` returns failure immediately if the lock is already held (never blocks). `timedlock` blocks up to a given timeout, then gives up if the lock still isn't available (a `timedlock` with a zero timeout degenerates to `trylock`). Both are flagged as generally worth avoiding, with a forward-reference to a future chapter on **deadlock**, where controlled avoidance of indefinite blocking becomes genuinely useful.

### 10.6 Condition variables: `pthread_cond_wait` / `pthread_cond_signal`
```c
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);
```
A condition variable is for the **second kind of thread interaction** flagged (but deferred) in your earlier Concurrency guide's Part 7: not "who gets exclusive access," but **"one thread must wait for another to do something before it continues."** A condition variable is always used **together with an associated lock**, which must be held whenever either routine is called.

**The waiting side:**
```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  cond = PTHREAD_COND_INITIALIZER;

Pthread_mutex_lock(&lock);
while (ready == 0)
    Pthread_cond_wait(&cond, &lock);
Pthread_mutex_unlock(&lock);
```
**The signaling side (run by some other thread):**
```c
Pthread_mutex_lock(&lock);
ready = 1;
Pthread_cond_signal(&cond);
Pthread_mutex_unlock(&lock);
```

**Three details the lecture and chapter both stress as easy to get subtly wrong:**

1. **The lock must be held while touching the shared predicate (`ready`) and while signaling.** This is a direct, small-scale instance of the entire "critical section" idea (Part 7): `ready` is shared mutable state, so both reading it (in the `while` check) and writing it (setting it to 1) must happen under the same lock, or you've simply reintroduced the exact race the lock was meant to prevent.

2. **`pthread_cond_wait` takes a lock argument; `pthread_cond_signal` does not — and this asymmetry is meaningful, not arbitrary.** `wait` does two things atomically: it **releases the lock** and **puts the calling thread to sleep**, as one indivisible step. This has to be atomic, or there's a gap between "release the lock" and "actually go to sleep" during which the signaling thread could acquire the lock, set `ready=1`, signal — and have that signal be **completely missed**, because the waiter wasn't asleep yet to receive it (this exact failure mode is named later, in Part 9.3's companion map, as the **"lost wakeup"** bug). Before `wait` returns (after being woken), it **re-acquires the lock** automatically — so a thread using this pattern is guaranteed to hold the lock at every point between the initial `lock()` call and the final `unlock()` call, with the "sleeping" interval being the sole, carefully-managed exception.

3. **Always re-check the condition in a `while` loop, never a plain `if`.** Even after being woken, the waiting thread must **re-verify** that the condition it cares about is genuinely true before proceeding — because some pthread implementations can produce **spurious wakeups** (waking a thread even though nobody actually signaled it for this reason). Treat "I was woken up" as a *hint* that something might have changed, not a guaranteed fact — the `while` loop's re-check is what makes this safe regardless.

### 10.7 The tempting-but-wrong shortcut: a spin flag instead of a condition variable
```c
// waiting thread:
while (ready == 0)
    ;   // spin

// signaling thread:
ready = 1;
```
**Never do this.** Two concrete reasons given:
1. **Performance**: spinning wastes CPU cycles the entire time it waits, rather than actually sleeping and letting the scheduler run something useful.
2. **Correctness**: a cited empirical study found that roughly **half** of ad hoc synchronization attempts like this one, in real production code, were buggy. Manual flag-based signaling looks deceptively simple but hides genuine subtleties (memory visibility across cores, missed updates, compiler reordering) that condition variables are specifically engineered to avoid.

### 10.8 Compiling
```
gcc -o main main.c -Wall -pthread
```
`#include <pthread.h>` in your source, and **explicitly link the pthreads library** with `-pthread` on the compile/link line — a small but easy-to-forget practical detail.

## PART 11 — The Take-Home Extension: A Hypothetical Luit Thread API

The lecture pairs the abstract "what would Luit need" discussion from Part 3.2 with a concrete, minimal, **non-POSIX-complete** sketch, explicitly framed as a take-home exercise:

```c
int  thread_create(void (*fn)(void *), void *arg, void *stack);
void thread_exit(void);
int  thread_join(int tid);
```

Implementation sketch, connecting directly back to the Syscall guide's trapframe machinery:
- **Share the parent's address space** — no new page table; the new thread's `satp` is the same value as its parent's (Part 2.3's "same page-table root" row).
- **Create a new PC, SP, trapframe, kernel stack, and scheduler context** — exactly the "per-thread execution state" column from Part 3.2's table, instantiated concretely.
- **Set `sepc = fn`, `a0 = arg`, `sp = top of supplied stack`** — this is a direct, satisfying callback to the Syscall guide's Part 10: recall that `sepc` is what `sret` uses as the jump target, and `a0` is exactly the ABI register a function's first argument arrives in (Syscall guide, Part 2.3). Manufacturing a "fake" trapframe with these three fields set is precisely how you'd bootstrap a brand-new thread to begin executing `fn(arg)` the first time it's ever scheduled — as if it had *already* trapped in from user mode and were merely resuming, even though it never actually ran before.
- **Deliberately delay POSIX completeness**: attributes, cancellation, detached threads, thread-local storage (TLS), and signal semantics are all explicitly named as things this minimal sketch does **not** attempt to handle — a reasonable simplification for a first implementation, but a real gap between this exercise and a production-grade thread library.

### 11.1 The precise gap list, restated as engineering requirements
| Needed mechanism | Why it is needed |
|---|---|
| shared address-space object | multiple schedulable entities must point to the same mappings |
| per-thread trapframe/context | two harts may trap independently, from two different threads of the same process |
| per-thread user stack | independent calls and local variables |
| lifetime/refcount rule | do not free the shared page table when *one* thread among several exits |
| thread-aware join/exit | reclaim thread-specific resources (stack, trapframe, TCB) at the right time, without disturbing sibling threads or the shared address space |

The **refcount rule** is worth flagging as a genuinely new correctness concern, not present at all when there's only one execution context per address space (baseline Luit, Part 3.1): with multiple threads sharing one page table, "when do we free the address space?" now has a real answer — only when the *last* thread using it exits, not the first. This is structurally the same reference-counting discipline your Page Faults guide's Part 7.5 used for physical pages shared under COW — same idea (shared resource + refcount governs when it's safe to reclaim), applied here to an entire address space rather than a single physical page.

## Quick-Reference: New Vocabulary From This Lecture
| Term | One-line meaning |
|---|---|
| **Hart** | RISC-V hardware execution context — its own registers, PC, CSRs |
| **Software thread** | Independently schedulable execution stream inside a process (OS-level, not hardware) |
| **`pthread_create`/`pthread_join`** | Start a new execution stream at a function; wait for it to finish and collect its return value |
| **`pthread_mutex_lock`/`unlock`** | POSIX mutual exclusion — block until the critical section is safe to enter |
| **`pthread_cond_wait`/`signal`** | POSIX condition variable — atomically sleep-while-releasing-lock; wake a waiter and let it re-acquire |
| **Data race** | Same location, concurrent access, at least one write, no synchronization (the sharpened definition from this lecture) |
| **Lost wakeup** | The bug `pthread_cond_wait`'s atomic release-and-sleep is specifically designed to prevent |
