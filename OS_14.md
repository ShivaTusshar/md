# Harts, Threads, and the Thread API: Complete Concept Guide

This lecture does two things your earlier **Concurrency: An Introduction** guide didn't: it draws a **hard line between a RISC-V hart and a software thread** (and shows Luit doesn't have POSIX-style user threads at all — its kernel is concurrent for a different reason), and it works through the **full pthread API** (OSTEP Ch. 27) that the earlier guide only gestured at. Everything from your earlier guide's Parts 0–8 (the peach analogy, shared-address-space state, the `counter++` race, critical sections, mutual exclusion) is a direct prerequisite here and is only briefly recapped, not re-derived — this guide focuses on what's genuinely new.

## PART 1 — Terminology: Core, Hart, Process, Software Thread

This is the lecture's foundational move, and it's worth getting exactly right, since the slide states outright: **"Do not confuse a RISC-V hart with a software thread."**

| Term | Meaning |
|---|---|
| **Core** | A physical processor implementation — actual silicon. |
| **Hart** | A RISC-V **hardware execution context** — one hart has its own complete architectural state (registers, PC, CSRs). A single physical core can implement more than one hart (hardware multithreading), though the lecture's focus is the conceptual distinction, not that implementation detail. |
| **Process** | A **resource and protection container** — an address space, a set of open files, a PID. This is the "container" concept from all of your earlier VM/syscall/page-fault guides. |
| **Software thread** | An **independently schedulable execution stream inside a process**. |

**The crucial asymmetry**: a hart is a piece of *hardware* — it exists whether or not any software concept of "threads" is in use at all. A software thread is a piece of *OS/programming* abstraction — the OS schedules software threads *onto* harts. **You can have multiple harts with no software threads at all** (this is exactly Luit's current baseline, Part 4) — each hart is just running one process's single execution context.

## PART 2 — The Bridge From Virtual Memory: Per-Hart State

### 2.1 Every hart has its own complete register and CSR set
Recall from your VM guide (Part 5.5) and Syscall guide (Part 2.1) the CSRs: `satp`, `sepc`, `scause`, `stval`, `sstatus`. **On a multi-hart machine, every single one of these is duplicated per hart** — they are genuinely separate physical registers, not one shared value:

```
        Hart 0                          Hart 1
      x0 – x31                        x0 – x31
         pc                              pc
      sstatus                         sstatus
sepc / scause / stval          sepc / scause / stval
        satp                            satp
```
**Hart 0's `satp` and Hart 1's `satp` are not the same physical register.** This matters enormously the moment you start reasoning about concurrency, because it means two harts really can be doing completely independent things — including running completely independent page-table walks, completely independent trap handling — at the exact same instant.

### 2.2 The precise `satp` statement
Here's the subtlety the lecture wants nailed down precisely: **separate `satp` registers can still hold the *same value*.**

```
                        Process P
                   page table root PT_P

    Hart 0                              Hart 1
  T0 running                          T1 running
H0.satp = PT_P                     H1.satp = PT_P
```

Two different harts, running two different **threads** of the *same process*, will each have their **own** `satp` CSR (per Part 2.1) — but both of those CSRs happen to be **loaded with the identical page-table-root address**, because both threads belong to the same process and thus share one address space. **The CSRs are per-hart; the value stored in them can still point to shared state.** This single fact is the hardware-level foundation for everything about why threads are "cheap to share memory with" — from a translation-hardware point of view, both harts are quite literally walking the *same physical tree* when either one accesses a shared virtual address.

### 2.3 Thread switch vs. process switch, precisely
This table generalizes your earlier guide's Part 1.3 (which only covered a *single*-hart thread switch) to also cover the **multi-hart** case:

| Switch | Registers / PC / SP | Address space / `satp` value |
|---|---|---|
| P:T0 → P:T1 (same process, same hart) | change | **same** page-table root |
| P:T0 → Q:T0 (different process, same hart) | change | **different** page-table root |
| P:T0 on Hart 0 *and* P:T1 on Hart 1 (simultaneously) | independent on both harts | **both** `satp` CSRs point to `PT_P` |

**One-sentence summary the slide gives explicitly:** *"A thread is execution state. An address space is process state."* Switching *which thread* runs never has to touch `satp` if the new thread belongs to the same process (exactly your earlier guide's point) — but crucially, this table also shows that **two threads of the same process can be genuinely running at the same instant on two different harts**, each with its own private registers, both pointed at the same page table. This is the concrete hardware picture behind "parallelism" (Part 6.1 below / your earlier guide's Part 2.1).

## PART 3 — Current Luit: A Named Divergence From OSTEP

### 3.1 What Luit actually has
```
struct proc
    address space        ┐
    trapframe / context  │  one address space + one execution
    kernel stack         │  context, bundled together, per process
    state / PID          │
    open files           ┘
```
**Baseline Luit has processes, not POSIX-style user threads.** Every `struct proc` bundles together exactly **one** address space *and* exactly **one** execution context (one trapframe, one kernel stack, one saved PC/registers). There is no existing Luit mechanism for a single process to have *two* independently-schedulable execution streams sharing that one address space.

**Why this needs to be named explicitly**: OSTEP Chapter 27 (Part 5+ below) is written entirely in terms of `pthread_create()`, assuming the reader's OS already supports exactly what Luit's baseline doesn't. The lecture is upfront that this is a genuine **mismatch** you need to keep straight — you can learn the *pthreads* API from the book, and separately learn how *Luit's* kernel handles concurrency (which is a different problem entirely, tackled in Part 8 below), but you should not expect a 1:1 `pthread_create()` equivalent to already exist in the Luit kernel you're studying.

### 3.2 If Luit *had* user threads — what would have to split apart
This is presented as a design exercise, not something already implemented — it shows *precisely* what "a thread duplicates execution state, not the address space" (your earlier guide's core claim) means at the level of actual kernel data structures:

| Shared process state (one copy, for all threads) | Per-thread execution state (one copy, per thread) |
|---|---|
| page table / address space | PC and general registers |
| code, globals, heap | user stack and stack pointer |
| open files and cwd | trapframe and kernel stack |
| PID / address-space lifetime | TID and scheduler context |

**The line worth remembering verbatim:** *"The thread abstraction does not duplicate the address space; it duplicates the execution context."* Everything in the left column stays a single, shared object; everything in the right column needs its own separate instance per thread — directly generalizing your earlier guide's TCB discussion (Part 1.3) into concrete Luit terms (trapframe, kernel stack — both concepts straight out of your Syscall guide's Part 7.3).

## PART 4 — Why Concurrency At All? (Recap, Sharpened)

Your earlier guide's Part 2 already covered "parallelism" and "avoiding I/O blocking" as the two reasons to use threads. This lecture adds a **third**, and restates the underlying risk more precisely:

| Motivation | Meaning |
|---|---|
| **Parallelism** | Use multiple harts/cores to finish one job faster (Part 2.3's simultaneous-hart picture, made concrete) |
| **Overlap with I/O** | Run useful work on one execution stream while another waits (same as your earlier guide's Part 2.2) |
| **Structure** | Split program logic into cooperating activities — a genuinely separate motivation from raw speed: sometimes threads make a program's *design* cleaner, independent of whether it runs faster |

**The line worth remembering:** *"The danger is not concurrency itself; the danger is unsafely shared mutable state."* This reframes your earlier guide's entire Part 4–5 (the `counter` race) as a special case of a more general principle — concurrency alone never breaks anything; it's specifically **shared, mutable, uncoordinated** state that does.

### Processes vs. threads, restated as a direct trade-off table
| | Many processes | Many threads in one process |
|---|---|---|
| Address spaces | separate | one, shared |
| Fault isolation | better (one process crashing can't easily corrupt another) | weaker — a bug in one thread can corrupt data any thread in the process can see |
| Communication | needs IPC | ordinary loads/stores |
| Context switch | may change `satp` root | thread switch in same process keeps same root |

## PART 5 — The Race, Reworked in RISC-V

Your earlier guide's Part 5 walked through this exact bug in **x86** assembly (`mov`/`add`/`mov`). This lecture gives the **RISC-V** version, which is what you should actually expect to see when reading Luit/QEMU disassembly:

```asm
lw    t0, 0(a0)      # load counter
addi  t0, t0, 1      # increment local register
sw    t0, 0(a0)      # store counter back
```
Structurally **identical** to the x86 version from your earlier guide — one C statement (`counter = counter + 1;` or `counter++`) still compiles to **three separate instructions**: a load, a register-only modify, and a store. **"The single C statement is not a single memory action"** — this is the exact same root cause as before, just in a different instruction set, and it's worth being able to recognize both forms.

### 5.1 The unlucky interleaving, RISC-V version
Starting `counter = 100`:

| T0 / Hart 0 | T1 / Hart 1 | counter |
|---|---|---|
| `lw` → t0=100 | | 100 |
| `addi` → t0=101 | | 100 |
| | `lw` → t0=100 | 100 |
| | `addi` → t0=101 | 100 |
| | `sw` → counter=101 | 101 |
| `sw` → counter=101 | | **101** |

**Expected: 102. Actual: 101.** Exactly the same lost-update bug as your earlier guide's Part 5.3, restated in the RISC-V register names you'll actually be reading in Luit coursework.

### 5.2 The `volatile` misconception, addressed head-on
This is new material — your earlier guide didn't cover this, but it's a genuinely common mistake:

> `volatile` does **not** make `counter++` atomic.

What `volatile` actually does: it forces the **compiler** to genuinely perform the memory load and store as written, rather than, say, keeping `counter` cached in a register across loop iterations and optimizing the repeated accesses away. What it does **not** do:
- combine load, add, and store into a **single indivisible operation**,
- stop another hart (or another thread on the same hart) from accessing the same memory location **in between** those steps.

`volatile` is a compiler-level directive about **when** memory is touched relative to the *compiler's* optimizations; it says **nothing** to the **hardware** about atomicity, and nothing about scheduling. **Correct synchronization needs a lock or another genuine atomic mechanism** (Part 7 below) — this single point is exactly why the earlier guide's Part 6 ("The Wish for Atomicity") exists, and it's worth having this specific misconception ready to correct in a viva.

### 5.3 A race doesn't require two harts
This is a genuinely important generalization beyond your earlier guide, which only demonstrated the bug via a timer-interrupt-driven context switch on what could be read as either one or two cores. This lecture makes the **single-hart** case explicit and unambiguous:

| Single-hart timeline | What happens |
|---|---|
| T0: `lw`; `addi` | T0 has 101 sitting in its **private register**, not yet written back |
| timer interrupt | scheduler runs |
| T1: `lw`; `addi`; `sw` | `counter` becomes 101 |
| T0 resumes: `sw` | `counter` **remains** 101 — the interrupt is what created the race, no second hart needed |

**The takeaway, stated directly:** *"Parallelism makes races easier to observe, but interleaving alone is enough."* This is the same underlying point as your earlier guide's Part 5.2 trace (which used exactly this scenario) — but this lecture is explicit that you should **not** think "no parallelism, therefore no race is possible." A single CPU with preemptive scheduling is entirely sufficient to produce this bug — **concurrency and parallelism are not the same idea**, and a race is a concurrency problem, not specifically a parallelism problem.

## PART 6 — Vocabulary, Sharpened

Your earlier guide already introduced four terms (Part 5.4). This lecture adds a **fifth, more precise** one and tightens the definitions:

| Term | Meaning |
|---|---|
| **Race condition** | Program correctness depends on **timing or interleaving** |
| **Data race** *(new, more precise)* | **Same memory location**, **concurrent accesses**, **at least one write**, **no synchronization** |
| **Critical section** | Code that accesses shared state and must be coordinated |
| **Indeterminate** | Same input can produce different outputs |

**Why "data race" is worth distinguishing from "race condition" precisely**: a *race condition* is the broader, more informal idea (correctness depends on timing) — a *data race* is a specific, well-defined technical condition (concurrent access to the same location, at least one writer, no synchronization) that is one common **cause** of race conditions. Not all race conditions are necessarily framed as data races in every formalization, but every data race is a race condition. This distinction matters if you're ever asked to define these terms precisely rather than casually.

## PART 7 — Atomicity and Mutual Exclusion, Previewed as Code

Your earlier guide covered atomicity conceptually (Part 6). This lecture shows the actual **code shape** the next lecture will build toward:

### 7.1 Atomicity as a code fragment
```c
atomic {
    counter = counter + 1;
}
// conceptually: nobody observes the middle
```
**Hardware will not make every C block atomic** — this pseudo-syntax doesn't exist in real C. The **OS and runtime build synchronization from a small number of genuinely atomic hardware instructions**. This is the mechanism-vs-policy split, restated concretely: hardware gives you a few narrow atomic primitives; software (locks, and eventually condition variables) is where the general-purpose "make this block atomic" behavior actually gets constructed.

### 7.2 The first solution idea: `lock()`/`unlock()`
```c
lock(&L);
counter = counter + 1;     // critical section
unlock(&L);
```
This directly implements mutual exclusion (your earlier guide's Part 5.4 definition) around the critical section. **But the lecture poses the deliberately unresolved question that the next lecture exists to answer:**

> How can `lock()` **itself** be implemented without a race?

This is a genuinely sharp point: `lock()` is presumably just more code, and that code presumably touches some shared state (the lock variable itself) — so naively, `lock()`'s own implementation looks like it has exactly the same problem it's trying to solve. Resolving this (via hardware atomic read-modify-write instructions) is explicitly deferred to the next lecture (Part 9 below flags this as "Next Time").

## PART 8 — The Luit Pivot: Kernel Concurrency Without User Threads

This is the lecture's central original contribution, and the reason Part 3's "Luit doesn't have POSIX threads" isn't the end of the concurrency story for Luit.

### 8.1 The key realization
```
      Hart 0                                Hart 1
 Process A syscall                     Process B syscall
        │                                     │
        └───────────────┬─────────────────────┘
                         ▼
                   LUIT kernel
               shared kernel state
```
**Two different harts can enter the kernel at the same time.** Recall from your Syscall guide's Part 6.1: `ecall` doesn't switch page tables, and every process's page table already maps the kernel. **This means nothing structurally prevents Hart 0 (handling process A's syscall) and Hart 1 (handling process B's syscall) from both executing kernel C code simultaneously** — and if both of those code paths touch the same kernel data structure (say, the physical-page free list from your VM guide's Part 6.8), you have exactly the same race-condition risk as the `counter` example, except now the "shared variable" is a piece of the kernel's own internal state.

**The lecture's explicit point:** *"So the lock problem is real even before LUIT has user-level threads."* You do not need Part 3.2's hypothetical user-thread extension to already have a genuine concurrency problem in Luit — multiple harts concurrently running kernel code on behalf of *different, entirely unrelated processes* is enough on its own.

### 8.2 Concrete kernel shared-state examples, and their invariants
| Shared object | Invariant that must survive concurrency |
|---|---|
| **Physical-page free list** (`palloc`/`pfree`, VM guide Part 6.8) | A page is allocated to at most one user — two harts racing on `palloc()` must never both walk away believing they own the *same* physical frame |
| **PID allocation** | Two processes must never end up with the same PID |
| **Process state** | The scheduler must never observe an inconsistent state transition (e.g., a process caught halfway between "sleeping" and "runnable") |
| **Ticks counter** | Timer-interrupt updates and any reader must see a consistent value, never a half-written one |
| **Buffer cache** | Metadata and buffer ownership must remain consistent even when multiple harts are using the cache concurrently |

**One sentence tying this to everything you already know:** *"A lock protects data and invariants."* Every single one of the concrete kernel structures from your earlier VM/Page-Fault guides — the free list, the process table, page-table pages themselves — is a legitimate answer to "what needs a lock in Luit," precisely because concurrent, uncoordinated access to any of them could violate the invariant that makes the rest of the kernel's logic correct.

## PART 9 — The Companion Map: OSTEP Concepts vs. Luit Realizations

The lecture is explicit that this table is a **conceptual bridge**, not a claim of API equivalence — *"Do not read this as API equality."*

| OSTEP side (user-level, pthreads) | LUIT side (kernel-level, cross-hart) |
|---|---|
| user threads sharing memory | kernel executions sharing kernel data across harts |
| `pthread_mutex` | spinlock `acquire()`/`release()` |
| condition variable `wait`/`signal` | `sleep(chan, lock)` / `wakeup(chan)` analogue |
| semaphores | built from lock + sleep/wakeup ideas |
| concurrency bugs | duplicate PID, lost wakeup, wrong lock order, deadlock |

Each row is "the same underlying *problem*, solved by a *different concrete mechanism* appropriate to that layer" — a pthread mutex is a user-space library call that ultimately blocks via the OS scheduler; a Luit spinlock is a kernel-internal primitive that (as the name suggests) busy-waits rather than sleeping, appropriate for short critical sections deep inside kernel code where sleeping isn't safe or possible. The condition-variable row gets its own dedicated caution in Part 12 below, since it's easy to over-map.

## PART 10 — The Full Pthread API (OSTEP Ch. 27)

This is genuinely new material relative to your earlier guide — a complete reference walkthrough of thread creation, joining, mutexes, and condition variables.

### 10.1 Thread creation: `pthread_create()`
```c
int pthread_create(pthread_t *thread,
                    const pthread_attr_t *attr,
                    void *(*start_routine)(void*),
                    void *arg);
```
Four arguments:
- **`thread`** — a pointer to a `pthread_t`, which `pthread_create()` **initializes**; you keep this around afterward to refer to this specific thread (e.g., to `join` it later).
- **`attr`** — optional attributes (stack size, scheduling priority, etc.), set up via a separate `pthread_attr_init()` call if needed. **Passing `NULL` uses sensible defaults**, which is what you'll do in the overwhelming majority of cases.
- **`start_routine`** — a **function pointer**: the function this new thread should begin executing. Its signature is fixed by the API: it takes one `void *` argument and returns a `void *`. Using `void *` on both ends is deliberate — it lets you pass **any type** of argument in, and return **any type** of result out, at the cost of needing explicit casts on both sides.
- **`arg`** — the actual value passed to `start_routine` when the new thread begins.

```c
typedef struct { int a; int b; } myarg_t;

void *mythread(void *arg) {
    myarg_t *args = (myarg_t *) arg;
    printf("%d %d\n", args->a, args->b);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p;
    myarg_t args = { 10, 20 };
    int rc = pthread_create(&p, NULL, mythread, &args);
    ...
}
```
**Once `pthread_create()` returns, you genuinely have another live, independently executing entity — with its own call stack — running inside the same address space as every other thread already in the program.** This is the exact mechanism behind your earlier guide's Part 3.3 (unpredictable execution ordering): the new thread may start immediately, or the scheduler may delay it — nothing about the API promises a specific timing.

### 10.2 Waiting for completion: `pthread_join()`
```c
int pthread_join(pthread_t thread, void **value_ptr);
```
- **`thread`** — which thread to wait for (the same `pthread_t` that `pthread_create()` initialized).
- **`value_ptr`** — a pointer **to** the return-value pointer you want filled in. Since the thread's return value is itself a `void *`, and `pthread_join()` needs to *write* that returned pointer somewhere the caller can see it, you pass a pointer-to-a-pointer (`void **`), not the pointer itself.

```c
typedef struct { int x; int y; } myret_t;

void *mythread(void *arg) {
    myret_t *rvals = Malloc(sizeof(myret_t));
    rvals->x = 1; rvals->y = 2;
    return (void *) rvals;
}

int main(...) {
    pthread_t p;
    myret_t *rvals;
    myarg_t args = { 10, 20 };
    Pthread_create(&p, NULL, mythread, &args);
    Pthread_join(p, (void **) &rvals);
    printf("returned %d %d\n", rvals->x, rvals->y);
    free(rvals);
}
```
**Simplifications worth knowing**: if a thread takes no arguments, just pass `NULL` as `arg`; if you don't care about the return value, pass `NULL` as `pthread_join()`'s second argument. If you're only passing/returning a single simple value (e.g., a `long long int`), you can skip the struct-packing entirely and just cast the value directly to/from `void *`:
```c
void *mythread(void *arg) {
    long long int value = (long long int) arg;
    printf("%lld\n", value);
    return (void *) (value + 1);
}
```

### 10.3 A genuinely dangerous mistake: returning a pointer to a stack variable
```c
void *mythread(void *arg) {
    myarg_t *args = (myarg_t *) arg;
    printf("%d %d\n", args->a, args->b);
    myret_t oops;              // ALLOCATED ON STACK: BAD!
    oops.x = 1; oops.y = 2;
    return (void *) &oops;     // returning address of now-dead stack memory
}
```
**Never return a pointer to something allocated on the thread's own call stack.** The instant `mythread` returns, its stack frame is deallocated — the *address* is still technically a valid-looking pointer, but the memory it points to is no longer reserved for that data at all; anything could subsequently overwrite it (another function call, another thread's activity, etc.). The values you read back through that pointer later will likely — but not necessarily — be garbage. **`gcc` will often warn about this**, which is itself a good reason to always pay attention to compiler warnings.

### 10.4 A subtlety worth naming: not everything joins
`pthread_create()` immediately followed by `pthread_join()` is, on its own, a strange way to structure a program — it's essentially just a convoluted way of making a **synchronous function call**. Realistic multi-threaded programs create several threads and coordinate them meaningfully. Also worth knowing: **not all multi-threaded code calls `join()` at all** — e.g., a long-lived multi-threaded web server might spawn worker threads once and let the main thread accept requests indefinitely, never joining the workers, since the program's whole lifetime is spent with all of them running concurrently. **A parallel program that spawns threads to do one bounded chunk of work, however, typically does join**, to know the work is genuinely finished before moving on.

### 10.5 Locks: `pthread_mutex_lock()` / `pthread_mutex_unlock()`
```c
int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);
```
```c
pthread_mutex_t lock;
pthread_mutex_lock(&lock);
x = x + 1;                    // critical section
pthread_mutex_unlock(&lock);
```
**Semantics**: if no other thread currently holds the lock, the calling thread acquires it immediately and proceeds. If another thread *does* hold it, the calling thread **does not return** from `pthread_mutex_lock()` until it successfully acquires the lock — which can only happen once the current holder calls `pthread_mutex_unlock()`. Multiple threads may be simultaneously blocked waiting to acquire the same lock; **only the thread that currently holds it should ever call unlock** on it.

**This snippet, as written, is broken in two important ways** — worth internalizing as habits, not just facts:

**Problem 1 — missing initialization.** A lock must be properly initialized before use, or its internal state is garbage and it won't behave correctly. Two ways to initialize:
```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;   // static initializer
```
or, at runtime:
```c
int rc = pthread_mutex_init(&lock, NULL);
assert(rc == 0);   // always check success!
```
The dynamic form (`pthread_mutex_init`) is the more commonly used of the two in practice. A corresponding `pthread_mutex_destroy()` should be called once you're done with the lock.

**Problem 2 — no error checking.** Like virtually any UNIX library call, `pthread_mutex_lock`/`unlock` **can fail** — and if your code ignores the return value, that failure happens **silently**, potentially letting multiple threads into the critical section at once (defeating the entire purpose of the lock). Minimally, use an assert-wrapping helper:
```c
void Pthread_mutex_lock(pthread_mutex_t *mutex) {
    int rc = pthread_mutex_lock(mutex);
    assert(rc == 0);
}
```
(This is exactly the `Pthread_create`/`Pthread_join` capitalized-wrapper convention used throughout this guide's code listings — the pattern generalizes to any pthread call.)

### 10.6 Two more lock-acquisition variants
```c
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_timedlock(pthread_mutex_t *mutex, struct timespec *abs_timeout);
```
- **`trylock`** returns failure immediately if the lock is already held, rather than blocking.
- **`timedlock`** blocks, but gives up (returning failure) after a specified timeout if the lock still hasn't been acquired. A timeout of zero degenerates exactly to `trylock`'s behavior.

**Both should generally be avoided** in ordinary code — but they become genuinely useful in specific situations, notably **deadlock avoidance** (a topic explicitly flagged as coming in a future chapter — not covered by this guide).

### 10.7 Condition variables
```c
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);
```
Condition variables solve a **different** problem than mutexes: not "only one thread may be in this section at a time," but **"a thread needs to wait until some other thread makes something true, and then be woken up."** This is exactly the second kind of thread interaction your earlier guide's Part 7 flagged as distinct from mutual exclusion, and this section is where it finally gets a concrete mechanism.

**Both routines require an associated lock to be held when called.**

**The waiting side:**
```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  cond = PTHREAD_COND_INITIALIZER;

Pthread_mutex_lock(&lock);
while (ready == 0)
    Pthread_cond_wait(&cond, &lock);
Pthread_mutex_unlock(&lock);
```
**The signaling side (run by some other thread):**
```c
Pthread_mutex_lock(&lock);
ready = 1;
Pthread_cond_signal(&cond);
Pthread_mutex_unlock(&lock);
```

**Four subtleties this exact pattern is built to satisfy, each worth being able to explain independently:**

1. **The lock is held around every access to `ready`, on both sides** — including the signal call itself. This is what prevents a race on the `ready` flag itself; changing `ready` and checking it are themselves critical-section operations, and get the same mutual-exclusion protection as anything else shared.
2. **Why `wait` takes a lock argument but `signal` doesn't**: `pthread_cond_wait()` does more than just "go to sleep" — it **atomically releases the held lock at the moment it goes to sleep**, and **reacquires that same lock before returning** once woken. If it didn't release the lock while sleeping, no other thread could ever acquire that lock to reach the signaling code in the first place — the program would deadlock immediately. Because `signal` doesn't sleep, it has no analogous need to release/reacquire anything.
3. **Why the condition is checked in a `while` loop, not a plain `if`**: some pthread implementations can produce **spurious wakeups** — a waiting thread can wake up even though nobody actually signaled a real state change. If the wait were guarded by `if` instead of `while`, a spurious wakeup would cause the thread to proceed as though `ready` had genuinely become true, when it hadn't. **The safe mental model: waking up is a hint that something might have changed, not a guarantee that it has** — so always re-check the actual condition after waking, in a loop.
4. **Why the lock is genuinely necessary around the `ready` check itself**, not just around the wait/signal calls: without it, there's a race between "checking `ready`" and "going to sleep" — another thread could set `ready = 1` and signal in the gap between the check and the sleep, and that signal would be missed entirely (a classic **lost wakeup** — explicitly named again in Part 9's bug list, and flagged there as relevant to Luit's `sleep`/`wakeup` too).

### 10.8 Never use a spin-flag instead of a condition variable
A tempting-looking "simpler" alternative:
```c
// waiting side
while (ready == 0)
    ;               // spin

// signaling side
ready = 1;
```
**Don't ever do this.** Two concrete reasons given:
1. **Performance**: spinning burns CPU cycles the entire time it waits, accomplishing nothing, for however long the wait lasts.
2. **Correctness**: cited research found that **roughly half** of ad-hoc synchronization attempts using flags like this, in real studied code, were **buggy**. This is a strong empirical warning against believing "it's simple, so it must be safe" — the pattern is deceptively easy to get subtly wrong (visibility/ordering issues that a proper condition-variable implementation is specifically designed to avoid).

**Always use condition variables (with their associated lock) even when a flag looks like it would obviously work.**

### 10.9 Compiling pthread code
```
prompt> gcc -o main main.c -Wall -pthread
```
Include `pthread.h`, and pass `-pthread` on the link line. That's the entire mechanical requirement — whether the resulting program is actually *correct* multi-threaded code is, of course, an entirely separate question from whether it compiles.

## PART 11 — Thread API Guidelines (Practical Tips)

A concise list worth internalizing as habits, not just facts to recall:
- **Keep it simple.** Tricky thread interactions lead to bugs — complexity in synchronization code is disproportionately dangerous compared to complexity elsewhere.
- **Minimize thread interactions.** Fewer, more carefully-designed points of interaction between threads means fewer opportunities for subtle timing bugs.
- **Always initialize locks and condition variables.** Skipping this produces code that works *most* of the time and fails in bizarre, hard-to-reproduce ways — exactly the "indeterminate" behavior from Part 6's vocabulary.
- **Always check return codes.** Silent failures in synchronization primitives can silently defeat the very protection you were trying to add.
- **Never return a pointer to a stack-allocated variable** (Part 10.3) — share data via the heap or another globally accessible location instead.
- **Remember each thread has its own stack** — a function-local variable is private to whichever thread is executing that function; nothing else can (easily) reach it.
- **Always use condition variables to signal between threads** — never a bare flag (Part 10.8).
- **Read the manual pages** — `man -k pthread` on Linux surfaces over a hundred related APIs; this chapter covers only the essentials.

## PART 12 — Being Careful With the Luit Analogy

Directly building on Part 9's companion map — this section exists specifically to prevent a mapping mistake:

| Pthread concept | LUIT-style kernel concept |
|---|---|
| wait on a condition variable | sleep on a **channel**, while releasing a lock |
| signal one waiter | `wakeup(chan)` wakes sleepers on that channel |
| predicate protected by a mutex | condition protected by a kernel lock |
| lost wakeup bug | **also** the key danger in kernel sleep/wakeup |

**This is explicitly an analogue, not an API equivalence** — Luit's `sleep(chan, lock)` / `wakeup(chan)` mechanism is a **kernel-internal**, lower-level primitive (built for kernel code, not exposed as a user API, and without the exact same guarantees pthread condition variables provide out of the box) that solves the *same class of problem* (thread A needs to wait for thread B to make something true) using a *conceptually similar* release-lock-then-sleep, reacquire-on-wake pattern. **The lecture defers the actual mechanics of Luit's sleep/wakeup to after locks are covered** — this guide names the connection now so you're not caught off guard when it's built properly later, but the real implementation is genuinely future material.

## PART 13 — A Hypothetical Luit User-Thread API (Take-Home Direction)

Presented as an exercise sketch, not existing code — this shows what actually adding user threads to Luit's baseline would concretely require:

```c
int  thread_create(void (*fn)(void *), void *arg, void *stack);
void thread_exit(void);
int  thread_join(int tid);
```
What creating such a thread would need to do, mechanically:
- **Share the parent's address space** — no new page table, no `uvmcreate()` from your VM guide; this new thread's mappings are the *same* mappings the creating process already has.
- **Create a new PC, SP, trapframe, kernel stack, and scheduler context** — exactly Part 3.2's "per-thread execution state" column, made concrete as actual objects that must be allocated.
- **Set `sepc = fn`, `a0 = arg`, `sp` = top of the caller-supplied stack** — this is the exact mechanism by which a brand new execution stream gets pointed at the right starting function with the right argument already in place, directly reusing the trapframe-return machinery from your Syscall guide's Part 10 (`usertrapret`/`userret` restore exactly these fields before `sret`).
- **Delay POSIX-completeness deliberately**: attributes, cancellation, detached threads, thread-local storage, and signal semantics are all explicitly named as things a minimal experimental implementation can defer — a smaller, honest API rather than a half-correct attempt at full POSIX compliance.

### The precise gap this reveals in the current kernel
| Needed mechanism | Why it is needed |
|---|---|
| Shared address-space object | Multiple schedulable entities must point to the *same* mappings |
| Per-thread trapframe/context | Two harts may trap into the kernel **independently**, on behalf of different threads of the same process — each needs its own saved state |
| Per-thread user stack | Independent function calls and local variables per thread (your earlier guide's Part 1.4) |
| Lifetime/refcount rule | Must **not** free the shared page table just because *one* thread of a multi-threaded process happens to exit — this is directly the same reference-counting discipline your Page Faults guide's Part 7.5 used for COW physical pages, applied here to an entire address space instead of a single page |
| Thread-aware join/exit | Reclaim exactly the per-thread resources at exactly the right time, without touching the shared resources other threads still need |

## Quick-Reference: New Vocabulary and Distinctions From This Lecture
| Term | One-line meaning |
|---|---|
| **Hart** | A RISC-V hardware execution context — distinct from a software thread |
| **Data race** | The precise technical condition: same location, concurrent access, ≥1 writer, no synchronization |
| **`PTHREAD_MUTEX_INITIALIZER`** | Static way to initialize a mutex; `pthread_mutex_init()` is the dynamic equivalent |
| **Spurious wakeup** | A condition-variable wait returning without an actual corresponding signal — the reason `while`, not `if`, guards the wait |
| **Lost wakeup** | A signal sent while the waiter isn't yet actually asleep, and thus never observed — prevented by holding the lock around both the check-and-wait and the modify-and-signal sequences |
| **`sleep(chan, lock)` / `wakeup(chan)`** | Luit's kernel-internal analogue to condition variables — conceptually similar, not API-identical |
