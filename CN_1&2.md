# CHAPTER 1: Computer Networks and the Internet

## 1.1 What Is the Internet?

The book explains the Internet in two ways: what it's physically made of ("nuts and bolts"), and what services it offers to programs that use it.

### 1.1.1 The Nuts-and-Bolts View

**End systems (hosts):** Any device connected to the Internet that runs applications — your laptop, phone, a server, a smart TV, even a smart thermostat. "End system" and "host" mean the same thing. They sit at the *edge* of the network.

**Network of networks:** The Internet isn't one network — it's millions of smaller networks (home networks, university networks, corporate networks, ISP networks) all connected together. That's literally where the name comes from: "inter-net" = a network *between* networks.

**Communication links:** The physical (or wireless) pathways data travels over — fiber optic cable, copper wire, radio spectrum, satellite links. Each link has a **transmission rate**, measured in **bits per second (bps)** — how fast data can be pushed onto that link (e.g., a 100 Mbps link can push 100 million bits per second).

**Packets:** End systems don't send raw data in one continuous stream. They chop data into small chunks called packets before sending them. Think of it like sending a long letter by tearing it into numbered pages and mailing each page separately — the destination reassembles them.

**Packet switches:** Devices inside the network that receive a packet on one link and forward it out on another, moving it closer to its destination. The two main types:
- **Routers** — used in the core of the network (network layer devices).
- **Link-layer switches** — typically used in access networks (e.g., inside a company or home).

**Route (or path):** The specific sequence of communication links and packet switches a packet travels through, from sending end system to receiving end system.

**ISP (Internet Service Provider):** A company that provides Internet access — think Comcast, Jio, Airtel, AT&T. End systems connect to the Internet through an ISP. ISPs themselves connect to *other* ISPs, forming the network of networks.

**Protocols:** The agreed-upon rules that control how information is sent and received. This is the single most important concept in the whole book — see 1.1.3 below.

**Internet Standards / RFCs:** Protocols and standards for the Internet are developed by the **IETF (Internet Engineering Task Force)**. Their standards documents are called **RFCs** (Requests for Comments).

### 1.1.2 A Services Description

Instead of describing wires and switches, you can describe the Internet as **infrastructure that provides services to applications**. Examples of services: web browsing, video streaming, email, video calls. The Internet gives application developers an **API (Application Programming Interface)** — a set of rules an app on one end system uses to hand data to the Internet for delivery to an app on another end system. Analogy: it's like a postal service — you follow rules for addressing an envelope, and the postal system worries about delivering it.

### 1.1.3 What Is a Protocol?

**A protocol defines the format and order of messages exchanged between two or more communicating entities, and the actions taken when a message is sent and/or received.**

Human analogy from the book: when two people talk, one says "Hi," the other says "Hi" back, then conversation proceeds. If one party says "Hi" and gets no reply, or gets an unexpected reply, the "protocol" doesn't work. Network protocols work the same way: machines exchange specific messages in a specific order, and take specific actions when messages arrive or time out.

Every time data moves on the Internet, protocols are involved — controlling things like: how a device gets an address, how a web browser requests a page, how a lost packet gets retransmitted.

## 1.2 The Network Edge

The **network edge** = the end systems (hosts) plus the access networks connecting them.

Hosts are divided into two categories:
- **Clients** — typically desktops, mobile devices — they *request* services (e.g., a web browser requesting a page).
- **Servers** — typically more powerful machines that *provide* services (e.g., a web server storing pages). Often housed in large **data centers**.

### 1.2.1 Access Networks

An **access network** is the network that physically connects an end system to the first router on its path to any other end system — called the **edge router**.

Key access network types covered:
- **DSL (Digital Subscriber Line):** Uses existing telephone lines. Splits the line's frequency into separate bands for data and phone calls.
- **Cable Internet:** Uses the cable TV company's existing infrastructure (coaxial + fiber, called **HFC — Hybrid Fiber Coax**). Cable is a **shared broadcast medium** — multiple homes share the same cable line, so it functions differently from DSL, where each home has a dedicated line back to a central office.
- **FTTH (Fiber to the Home):** Fiber optic cable run directly to the home, offering very high speeds.
- **Ethernet / LANs (Local Area Networks):** Used heavily in offices, campuses, and homes for wired connections — typically 100 Mbps to 10+ Gbps.
- **WiFi (wireless LANs):** Based on the IEEE 802.11 standard family. Devices connect wirelessly to an **access point**, which connects to the wired network.
- **Cellular Internet access (3G/4G/5G):** Devices connect via cell towers operated by a cellular provider.

**Key numbers/concepts to know here:**
- **Bandwidth** — informally, how much data per second a link can carry (same idea as transmission rate).
- **Home network** — typically consists of a **router/modem**, connected to WiFi access points and wired devices.

### 1.2.2 Physical Media

Data travels as **bits** — the bit moves from one end system, through switches/routers, to another. Each bit travels along a **physical medium**. Two categories:

- **Guided media:** signal travels along a solid medium.
  - **Twisted-pair copper wire** — cheapest, used in home/office LANs and phone lines. Two insulated wires twisted together (twisting reduces electrical interference).
  - **Coaxial cable** — used in cable TV/Internet; can be shared (broadcast) medium.
  - **Fiber optic cable** — thin flexible glass fiber carrying light pulses; very high speed, low signal loss, immune to electromagnetic interference; more expensive to install.
- **Unguided media:** signal propagates through the air/space (radio).
  - **Terrestrial radio, satellite radio (including geostationary satellites)**, WiFi, cellular signals.

## 1.3 The Network Core

The **network core** = the mesh of interconnected routers that ties the Internet's end systems together. The fundamental question this section answers: *how is data moved through this core?* Two fundamental approaches: **packet switching** and **circuit switching**. The Internet uses packet switching.

### 1.3.1 Packet Switching

Instead of reserving a dedicated path, end systems break messages into **packets**. Each packet travels independently through the network.

**Store-and-forward transmission:** A key behavior of most packet switches — a router must receive the **entire** packet before it can begin forwarding even the first bit of it onward. Why it matters: this adds delay proportional to packet size and link speed.

- If a packet has **L** bits and the link's transmission rate is **R** bits/sec, the time to push the whole packet onto the link is **L/R** seconds. This is the **transmission delay** (explained more in 1.4).

**Queues (output buffers):** Each router has a buffer (memory) in front of each outgoing link. If packets arrive faster than they can be sent out on a link, they wait in this queue.

**Packet loss:** Queues are finite in size. If a queue is full when a packet arrives, the router **drops** the packet — it's simply discarded. This is called packet loss, and is a normal, expected occurrence in packet-switched networks under heavy load.

**Forwarding tables & addressing:** Every end system has an **address**. When a packet arrives at a router, the router looks at part of the packet's address and uses a **forwarding table** to decide which outgoing link to send it on.

**Two approaches for how routers decide where to forward a packet:**
- **Datagram networks** (what the Internet uses) — every packet carries the destination address, and each router independently decides how to forward it based on that address. No "connection setup" needed beforehand.
- **Virtual-circuit networks (VCs)** — a path is established before data is sent, and every packet along the way follows that pre-established path, identified by a **virtual-circuit number** rather than a full address. Requires call setup and signaling protocols. (The Internet is a datagram network; VC networks are more common in older telephone-style networks.)

### 1.3.2 Circuit Switching

The alternative to packet switching. Used in traditional telephone networks. In circuit switching, before communication starts, the network **reserves a fixed set of resources** (a "circuit") along the entire path between sender and receiver, for the whole duration of the connection — even if no data is actually being sent at some moment.

- **FDM (Frequency-Division Multiplexing):** Each circuit is given a slice of the frequency spectrum on the link, all circuits sent simultaneously on different frequencies.
- **TDM (Time-Division Multiplexing):** Time is divided into slots (frames), and each circuit gets a fixed slot in a repeating cycle.

**Packet switching vs circuit switching — the core trade-off:**
- Circuit switching *guarantees* a fixed amount of bandwidth for a connection's whole duration, but wastes resources if the circuit is idle (e.g., silence during a phone call).
- Packet switching lets many users' traffic share network resources on demand (called **statistical multiplexing**) — much more efficient for "bursty" traffic like web browsing, but doesn't guarantee performance, and can suffer delay/loss under congestion.

The book's conclusion: packet switching is generally more efficient and simpler to implement for the kind of bursty data traffic the Internet carries, which is why it's the Internet's chosen approach.

### 1.3.3 A Network of Networks

How do millions of separate networks actually connect into "the Internet"? Roughly:

- End users connect to **access ISPs** (local Internet providers).
- Access ISPs connect to larger **regional** and **tier-1 ISPs** — huge providers with networks spanning countries/continents, who all interconnect with each other (so that any two points on Earth can reach each other).
- **IXPs (Internet Exchange Points):** Meeting points where multiple ISPs' networks physically connect to exchange traffic directly, rather than paying a bigger ISP to carry it.
- **Content-provider networks:** Companies like Google/Netflix build their own private global networks connecting their data centers directly to access ISPs, to deliver content faster/cheaper — bypassing some of the layers above.

The big-picture takeaway: the real Internet is a **loosely hierarchical structure of interconnected ISPs and networks**, not a single centrally-owned system.

## 1.4 Delay, Loss, and Throughput in Packet-Switched Networks

This section quantifies the imperfections of a packet-switched network: data doesn't move instantly, and some data gets lost. As a packet moves from a source, through routers, to a destination, it experiences delay at every single node (router) along the way.

### 1.4.1 The Four Types of Nodal Delay

At each router, a packet experiences these delays, which sum to the **total nodal delay**:

1. **Processing delay (d_proc):** Time for the router to examine the packet's header (and check for errors) and decide which outgoing link to send it on. Usually tiny — microseconds or less.

2. **Queuing delay (d_queue):** Time the packet waits in the outgoing link's queue before it can be transmitted, because other packets are ahead of it or the link is busy. Highly variable — depends on network congestion.

3. **Transmission delay (d_trans):** Time to push all of the packet's bits onto the link. Formula: **d_trans = L / R**, where L = packet length in bits, R = link's transmission rate in bits/sec. (Analogy from the book: a "caravan" of 10 cars at a tollbooth — the time to push the whole caravan through the booth is like transmission delay.)

4. **Propagation delay (d_prop):** Time for a bit, once transmitted, to physically travel across the link to the next router. Formula: **d_prop = d / s**, where d = physical distance of the link, s = propagation speed of the signal in that medium (close to the speed of light, roughly 2×10⁸ to 3×10⁸ meters/sec).

**Important distinction (commonly confused by beginners):** Transmission delay is about pushing bits *into* the link (depends on packet size & link rate). Propagation delay is about how long a bit takes to *travel across* the link once it's on it (depends on distance & medium). These are two completely separate quantities, even though they happen back-to-back.

### 1.4.2 Queuing Delay and Packet Loss

Queuing delay is the trickiest and most variable of the four. It depends on:
- The rate at which packets arrive (**arrival rate**, a),
- The packet size (L),
- The link's transmission rate (R).

**Traffic intensity = La/R** — this ratio describes how "loaded" a link is:
- If La/R is close to 0: the link is lightly used, queuing delay is near zero.
- If La/R approaches 1: the link is close to its capacity — queues start growing rapidly, and average delay grows sharply.
- If La/R exceeds 1 for a sustained period: more data is arriving than the link can push out, so the queue grows without bound (in an idealized infinite-buffer model) — in reality the queue is finite, so this leads to **packet loss**.

**Packet loss:** Because real router queues have finite size, when a packet arrives and finds a full queue, it's simply **dropped**. From the sender's perspective, that packet just "disappears" into the network. Higher-layer protocols (discussed in Chapter 3) may retransmit lost data.

### 1.4.3 End-to-End Delay

Total delay from source to destination = the sum of nodal delays at every router along the path, plus delays at the two end systems. A tool called **traceroute** actually measures this in practice — it sends specially-marked packets designed to get a response from each router along the path, letting you see the route and round-trip delay to every hop.

Two other delay-related terms worth knowing:
- **Round-Trip Time (RTT):** Time for a small packet to travel from source to destination and back again.
- **End-system delays:** Delays in packetizing data, plus **media packetization delay** in real-time applications like VoIP.

### 1.4.4 Throughput in Computer Networks

**Throughput** = the rate (bits/second) at which data is actually delivered from sender to receiver. This is different from transmission rate/bandwidth of any one link — throughput along a whole path is limited by the slowest link on the path, called the **bottleneck link**.

- If a file transfer passes through links of rates R1, R2, ... Rn, the end-to-end throughput is roughly **min(R1, R2, ..., Rn)** — it can only go as fast as the slowest link allows.
- When many flows share a link (e.g., 10 users downloading through one shared "core" link), each flow may only get a fraction of that link's total capacity — throughput per user drops as the shared link becomes the bottleneck instead of each user's own access link.

## 1.5 Protocol Layers and Their Service Models

### 1.5.1 Layered Architecture

Rather than building one giant, monolithic system to handle everything the Internet needs to do, network designers split the job into **layers** — each layer handles a specific piece of functionality and offers a defined **service** to the layer above it, while relying on the services of the layer below it.

**Analogy the book uses:** the airline system — ticketing, baggage, gates, and flight routing are all separate functional "layers" that combine to get you from one airport to another. Each layer does its job independently; you can change *how* one layer works internally (e.g., how boarding is organized) without needing to change any other layer, as long as the same service is still offered upward.

**Benefits of layering:**
- Breaks a complex system into manageable, modular pieces.
- Allows changing the implementation of one layer without disturbing others, as long as its interface/service to the layer above stays the same.

**The Internet's 5-layer protocol stack** (top to bottom):

| Layer | Handles | Data unit name |
|---|---|---|
| **Application** | Network applications and their protocols (HTTP, SMTP, DNS, etc.) | Message |
| **Transport** | Process-to-process data delivery across the network (TCP, UDP) | Segment |
| **Network** | Moving datagrams (packets) from source host to destination host; routing (IP) | Datagram |
| **Link** | Moving frames from one node to the physically next node (Ethernet, WiFi) | Frame |
| **Physical** | Moving individual bits across the physical medium | Bit |

Details on each:
- **Application layer:** Where network apps and their protocols live — HTTP (web), SMTP (email), DNS (naming), etc. The packet of information here is called a **message**.
- **Transport layer:** Moves application messages between the client and server sides of an application. The Internet has two transport protocols: **TCP** (connection-oriented, reliable, provides flow control and congestion control) and **UDP** (connectionless, no reliability guarantees, "no-frills"). Data unit: **segment**.
- **Network layer:** Responsible for moving network-layer packets (called **datagrams**) from one host to another, across the whole path of routers. Contains the famous **IP (Internet Protocol)**, which defines the datagram format, plus **routing protocols** that determine the actual paths. There is only one IP — every device with a network layer must run it (this is a core "hourglass" design principle of the Internet).
- **Link layer:** Moves a **frame** from one network element (host or router) to the physically *next* one along the route (not all the way to the destination — just one hop). Examples: Ethernet, WiFi (802.11), PPP.
- **Physical layer:** Moves the individual raw bits of a frame from one node to the next, across whatever physical medium (copper, fiber, radio) is being used.

**Which devices run which layers?**
- **Hosts** implement all five layers.
- **Routers** implement only layers 1–3 (physical, link, network) — enough to make forwarding decisions using IP addresses.
- **Link-layer switches** implement only layers 1–2 — they can't see IP addresses, only link-layer (e.g., Ethernet) addresses.

This design puts most of the "smarts"/complexity at the edges (in hosts), keeping the network core relatively simple — a key Internet design philosophy sometimes called the **end-to-end principle**.

Also worth knowing: **ISO's OSI model** is a similar, older 7-layer reference model (adds separate Session and Presentation layers between Transport and Application) that's often taught alongside the Internet's 5-layer model, though the Internet itself is built and described using the 5-layer version.

### 1.5.2 Encapsulation

**Encapsulation** is the process by which, as data descends the protocol stack on the sending side, each layer adds its own **header** (control information) to the data it received from the layer above:

1. Application creates a **message (M)**.
2. Transport layer wraps it with a transport header → becomes a **segment**.
3. Network layer wraps that with a network header → becomes a **datagram**.
4. Link layer wraps that with a link header (and trailer) → becomes a **frame**.
5. Physical layer sends the actual bits.

At the receiving end, this process runs in reverse — each layer strips off and reads its corresponding header as data moves back up the stack, until the original message reaches the destination application. Each layer's header lets that specific layer's protocol do its job (e.g., the network-layer header carries the destination's address so routers know where to forward the packet).

## 1.6 Networks Under Attack

A short but important section: the Internet was originally designed assuming "a group of mutually trusting users attached to a transparent network" — security was not baked in from the start, which is why attacks are so common today. Key attack types introduced (studied in depth in Chapter 8):

- **Malware:** Malicious software that can infect a host — includes **viruses** (need some user action, like opening an infected file, to spread) and **worms** (spread on their own, without user action, by exploiting vulnerabilities). Malware can turn a device into part of a **botnet** — a network of compromised hosts controlled remotely, often used to send spam or launch attacks.
- **Denial-of-Service (DoS) attacks:** Attacks that make a network, host, or service unusable for legitimate users, typically by overwhelming it with traffic or requests. Types:
  - **Vulnerability attack** — sending crafted messages that exploit a bug in the target software.
  - **Bandwidth flooding** — sending so many packets that the target's access link is overwhelmed.
  - **Connection flooding** — opening so many connections that the target can't accept legitimate ones.
  - **DDoS (Distributed DoS):** The attack is launched from many (often thousands of) compromised hosts (a botnet) simultaneously — much harder to defend against than an attack from a single source.
- **Packet sniffing:** A passive attacker with access to a network segment (e.g., an open WiFi network) can capture (a "sniff") every packet passing by, potentially reading sensitive unencrypted data.
- **IP spoofing:** Creating packets with a false ("spoofed") source address, so the packet appears to come from somewhere it didn't — used to disguise the true origin of an attack.
- **Man-in-the-middle:** An attacker positions themselves between two communicating parties to intercept, and possibly alter, their traffic.

## 1.7 History of Computer Networking and the Internet

A brief timeline (good to know conceptually, less important to memorize in detail):

- **1961–1972 — Development of packet switching:** Early theoretical work on packet switching (Kleinrock, Roberts, others). **ARPAnet** — the first packet-switched network, funded by the U.S. Department of Defense — went live in 1969, initially connecting 4 university sites.
- **1972–1980 — Proprietary networks and internetworking:** ARPAnet grows; other independent, incompatible packet-switched networks emerge. **Cerf and Kahn** develop the principles of **internetworking** — connecting separate, independently-designed networks together — leading to the design of **TCP/IP**.
- **1980–1990 — A proliferation of networks:** More networks are built worldwide; TCP/IP becomes the standard; the **Domain Name System (DNS)** is created to give hosts human-friendly names instead of raw numeric addresses.
- **1990s — The Internet explosion:** The **World Wide Web** is invented by **Tim Berners-Lee** (HTML, HTTP, URLs); the Mosaic/Netscape web browsers make the Internet accessible to the public; massive commercial growth follows.
- **The new millennium:** Explosive growth of broadband access, WiFi, smartphones, cloud computing/data centers, social networks, and streaming video — all of which reshape traffic patterns and drive continued evolution of the Internet's architecture.

## 1.8 Chapter 1 — Key Takeaways

- The Internet = end systems + access networks + the core (routers, switches, links), all governed by protocols.
- A **protocol** defines message format, order, and required actions.
- Data moves as **packets** using **packet switching**, not **circuit switching**.
- Delay has 4 components at every node: **processing, queuing, transmission, propagation**.
- **Throughput** of an end-to-end path is limited by the **bottleneck link**.
- The Internet is organized into **5 layers**: Application, Transport, Network, Link, Physical — each with its own protocols and its own name for a "packet" (message, segment, datagram, frame, bit).
- **Encapsulation** wraps data with headers as it goes down the stack, and unwraps it as it goes up.
- The Internet was not designed with security as a priority, leading to vulnerabilities like malware, DoS/DDoS, sniffing, and spoofing.

# CHAPTER 2: Application Layer

Chapter 2 zooms into the **top layer** of the stack — where the actual programs you use (browsers, email clients, streaming apps) live, and the protocols that let them talk to each other.

## 2.1 Principles of Network Applications

The central idea of this chapter: you can build a network application by writing software that runs on **end systems only** — you never have to write software that runs on routers or switches inside the network core. This is a direct consequence of the layered design and the "keep the core simple" philosophy from Chapter 1.

### 2.1.1 Network Application Architectures

Two dominant architectural models for how application processes are organized:

- **Client-server architecture:** An always-on **server** has a fixed, well-known address and serves requests from many **clients**. Clients don't talk directly to each other — they always go through the server. Example: the Web, where browsers (clients) request pages from web servers. Popular services often use **data centers** — huge server farms — to handle massive numbers of clients.
- **Peer-to-peer (P2P) architecture:** Minimal (or no) reliance on always-on servers. Instead, application instances (called **peers**) communicate directly with each other. Peers ask each other for data rather than a central server. Example: BitTorrent file-sharing. Key advantage: **self-scalability** — as more peers join, they also add more capacity to the system (each new peer both requests service and provides service to others).

Some apps use a **hybrid** of both.

### 2.1.2 Processes Communicating

The actual entities communicating are **processes** (running programs) on different end systems — not "programs" or "hosts" in the abstract.

- In the client-server model, the process that initiates contact is the **client**; the process that waits to be contacted is the **server**.
- **Socket:** The software interface between a process and the network — the "door" through which an application sends and receives messages to/from the network. Analogy from the book: a socket is like a house's door — the process is like a resident who sends messages by giving them to the network through this door, without needing to know how the network actually delivers them, similar to how a letter sender doesn't manage how the postal service physically moves the letter.
- **Addressing processes:** To send a message to a specific process, you need two things:
  1. The destination host's **IP address** — identifies the host on the Internet.
  2. A **port number** — identifies the specific process/application running on that host (since a host can run many networked applications at once). Example: web servers conventionally listen on **port 80** (or 443 for HTTPS).

### 2.1.3 Transport Services Available to Applications

When designing an app, the developer must choose a transport-layer protocol, and understand what services it can offer along four key dimensions:

1. **Reliable data transfer:** Guarantees that data sent is received completely and correctly, with nothing lost or corrupted. Some apps (file transfer, web pages) absolutely need this. Others (some real-time audio/video) can tolerate some **loss** since a few lost bits just cause minor, tolerable glitches.
2. **Throughput:** Some apps (like video streaming) need a guaranteed minimum throughput to function well — these are called **bandwidth-sensitive applications**. Others (like email) are **elastic applications** — they can use whatever bandwidth happens to be available, taking more time if less is available.
3. **Timing:** Some apps (like real-time voice/video calls) need low **latency** (delay) — data that arrives too late is useless, even if it's not lost.
4. **Security:** Whether the transport service itself provides encryption, data integrity checks, etc.

### 2.1.4 Transport Services Provided by the Internet

The Internet provides two main transport-layer protocols, offering different service combinations:

**TCP (Transmission Control Protocol):**
- **Connection-oriented:** requires a "handshake" (preliminary exchange of control messages) between client and server before real data flows, to set up the parameters of the data transfer. This creates a logical connection between the two processes' sockets.
- **Reliable data transfer service:** guarantees delivery of all data, correctly and in order.
- **Congestion control:** throttles a sending process when the network is congested, aiming for fairness among all TCP connections sharing a bottleneck link — this is a service to the network's general health, not just to the individual app.
- Does **not** guarantee a minimum throughput or bounded delay.

**UDP (User Datagram Protocol):**
- **Connectionless:** no handshake before sending data.
- **Unreliable data transfer service:** no guarantee data arrives at all, or arrives in order, or arrives without errors.
- No congestion control, no flow control, no reliability, no timing/throughput guarantees — a bare-bones service.
- Used by apps that need speed and can tolerate loss, or that want to build their own custom reliability mechanism (e.g., some real-time apps, DNS, some streaming protocols).

**Neither TCP nor UDP provides encryption by default.** For security, apps typically use **TLS (Transport Layer Security)**, layered on top of TCP, providing encrypted data transfer, data integrity, and end-point authentication (this is what makes "HTTPS" secure).

### 2.1.5 Application-Layer Protocols

An **application-layer protocol** defines:
- The types and format of messages exchanged (e.g., request messages, response messages).
- The meaning of fields within a message.
- Rules for when/how a process sends and responds to messages.

Note: an application-layer protocol is only *one piece* of a full network application (e.g., HTTP is part of the Web, but "the Web" also includes standards for document formatting like HTML, browsers, servers, etc.)

## 2.2 The Web and HTTP

### 2.2.1 Overview of HTTP

**HTTP (HyperText Transfer Protocol)** is the Web's application-layer protocol, implemented in two programs: a **client** program (the browser) and a **server** program (running on a web server), which talk to each other by exchanging HTTP messages.

- A **Web page** consists of objects (an **object** = a file such as an HTML file, an image, a video clip, etc.) addressable by a single **URL (Uniform Resource Locator)**.
- A URL has two components: the hostname of the server storing the object, and the object's path name on that server.
- HTTP uses **TCP** as its underlying transport protocol — client and server establish a TCP connection first, then exchange HTTP messages.
- HTTP is a **stateless protocol** — the server does not (by default) keep any memory of past requests from a client. This simplifies server design, at the cost of needing extra mechanisms (like cookies) to implement things like "remembering" a logged-in user.

### 2.2.2 Non-Persistent and Persistent Connections

- **Non-persistent connections:** Each object requested requires opening a brand-new TCP connection, which is closed after that one object is transferred. Inefficient — the overhead of the TCP handshake happens repeatedly for every image, script, etc., on a page.
- **Persistent connections:** The default in modern HTTP — the same TCP connection stays open and is reused to fetch multiple objects, one after another (or even in parallel with **pipelining**), saving the overhead of repeated connection setup.
- **RTT (Round-Trip Time)** matters here: for non-persistent connections, roughly 2 RTTs are needed per object (1 to set up the TCP connection, 1 for the actual HTTP request/response) — so fewer connections = less delay.

### 2.2.3 HTTP Message Format

**HTTP request message** — plain, human-readable text, structured as:
- A **request line**: contains the **method** (GET, POST, HEAD, PUT, DELETE, etc.), the requested URL/path, and the HTTP version.
- **Header lines**: extra information (e.g., which browser is asking — `User-Agent`; what languages are acceptable — `Accept-Language`).
- A blank line, then an optional **entity body** (used for methods like POST, which submit data — e.g., a filled-out web form).

**HTTP response message** — structured as:
- A **status line**: contains the HTTP version, a **status code**, and a short **status phrase**.
- Common status codes: **200 OK** (success), **301 Moved Permanently**, **400 Bad Request**, **404 Not Found**, **505 HTTP Version Not Supported**.
- **Header lines**, then a blank line, then the **entity body** (the actual requested content, e.g., the HTML of the page).

### 2.2.4 User-Server Interaction: Cookies

Since HTTP is stateless, sites use **cookies** to identify users across multiple requests/visits. How it works:
1. Server includes a `Set-Cookie` header in its response, containing a unique identification number.
2. The browser stores this in a **cookie file** and automatically includes that same identifier in a `Cookie` header on all future requests to that site.
3. The server keeps a **backend database** matching cookie identifiers to information about that user (login state, shopping cart, browsing history, preferences, etc.)

This is how sites "remember" you're logged in, remember your shopping cart, and (controversially) track your browsing behavior for advertising.

### 2.2.5 Web Caching

A **Web cache (proxy server)** is a network entity that satisfies HTTP requests on behalf of the actual origin server, storing copies of recently-requested objects. Benefits:
- Reduces response time for the client (if the cache is closer/faster than the real server).
- Reduces traffic on an institution's (or the wider Internet's) access link, since fewer requests need to reach the actual origin server.
- On a large scale, caching reduces overall Internet traffic, improving performance for everyone.

**Conditional GET:** A mechanism to make sure a cached copy is still up-to-date. The cache sends a request with an `If-Modified-Since` header; if the object hasn't changed since that date, the server replies with a short **304 Not Modified** response (no body needed), saving bandwidth — otherwise it sends the updated object with **200 OK**.

**CDN (Content Distribution Network):** A large, distributed system of caching servers spread across many geographic locations (or ISPs), designed to serve popular content (video, images, etc.) from a location near each user, drastically reducing delay for large-scale content providers like Netflix or YouTube. (Covered more in section 2.6.)

### 2.2.6 HTTP/2

A newer version of HTTP designed mainly to reduce perceived delay when loading web pages with many objects. Key ideas:
- Breaks messages into small **frames**, and interleaves the frames of multiple request/response pairs over a single TCP connection, so a large response doesn't block smaller ones behind it (**head-of-line blocking** in HTTP/1.1 is reduced).
- Lets the server prioritize sending certain frames (e.g., HTML before large images) rather than always going strictly first-come-first-served.
- (Newer than the book covers in depth: HTTP/3 later moved from TCP to a UDP-based protocol called QUIC — not required for this chapter, but useful context.)

## 2.3 Electronic Mail in the Internet

Email has three major components: **user agents** (the mail-reading/writing program, e.g., Outlook, Gmail interface), **mail servers**, and the **SMTP** protocol.

- **Mail servers** form the core of the email infrastructure: each user has a **mailbox** on their mail server holding incoming messages, and an **outgoing message queue** for messages waiting to be sent.

### 2.3.1 SMTP (Simple Mail Transfer Protocol)

SMTP is the protocol used to **transfer** mail from a sender's mail server to a recipient's mail server (and from a user agent to the sender's mail server). Key facts:
- Uses **TCP** for reliable data transfer.
- Restricted to sending messages made of basic **7-bit ASCII text** in its original form — non-text data (images, video, non-ASCII text) must be encoded into ASCII before transfer (this is what MIME extensions handle).
- Uses a **push protocol** model — the sending mail server pushes the message to the receiving mail server (contrast with mail *access* protocols below, which are pull-based).

### 2.3.2 Mail Message Formats

Email messages have a header (fields like `From:`, `To:`, `Subject:`) and a body. **MIME (Multipurpose Internet Mail Extensions)** extends the format to allow non-ASCII content (attachments, images, etc.) by adding extra header lines describing how to interpret the encoded body.

### 2.3.3 Mail Access Protocols

SMTP pushes mail from sender's server to recipient's server, but the recipient still needs a way to **retrieve** ("pull") mail from their own mail server to their device. Protocols for this:
- **POP3 (Post Office Protocol version 3):** Simple protocol — typically downloads messages to the local device (traditionally then deletes them from the server, though "leave a copy" options exist).
- **IMAP (Internet Mail Access Protocol):** More full-featured — keeps all messages and folder structures organized on the server, letting a user access the same mailbox from multiple devices with a consistent view.
- **HTTP-based webmail:** Many modern email services (Gmail, etc.) simply use HTTP/HTTPS for the user to access their mailbox through a web browser, instead of POP3/IMAP.

## 2.4 DNS — The Internet's Directory Service

**DNS (Domain Name System)** solves a basic problem: humans want to use easy-to-remember **hostnames** (like `www.example.com`), but routers need numeric **IP addresses** (like `192.0.2.1`) to actually route packets. DNS translates between the two.

### 2.4.1 Services Provided by DNS

- **Hostname-to-IP-address translation** (the main service).
- **Host aliasing:** A host can have one canonical (real) name and multiple alias names; DNS can look up the canonical name and IP address given any alias.
- **Mail server aliasing:** Similarly, allows a company's mail server to have a memorable alias.
- **Load distribution:** For sites with multiple redundant servers (multiple IP addresses for one hostname), DNS can distribute load by returning a different (or rotated) IP address to different requesters.

### 2.4.2 Overview of How DNS Works

DNS is itself implemented as a **distributed database** run across a hierarchy of many **DNS servers** worldwide, plus an application-layer protocol that lets hosts query this database. It is **not** a single centralized server — that would be a single point of failure and a massive traffic/scalability bottleneck.

**DNS server hierarchy (three main levels):**
1. **Root DNS servers:** The top of the hierarchy — there are a limited number of root server clusters worldwide. They know how to direct a query to the correct **TLD server**.
2. **TLD (Top-Level Domain) servers:** Responsible for domains like `.com`, `.org`, `.net`, `.edu`, and country codes like `.in`, `.uk`. They direct queries toward the correct **authoritative server** for a specific domain.
3. **Authoritative DNS servers:** Every organization with publicly-accessible hosts must provide DNS records mapping its hostnames to IP addresses — these are held on the organization's own (or its DNS provider's) authoritative server.

There's also a fourth important type:
- **Local DNS server (resolver):** Not strictly part of the hierarchy — this is typically run by your ISP (or a public resolver like 8.8.8.8). When your device wants to resolve a hostname, it first asks its local DNS server, which then does the work of querying the hierarchy above on your behalf, and **caches** the result for a while to speed up future queries.

**Query types:**
- **Recursive query:** The host asks its local DNS server to do all the work and just return the final answer.
- **Iterative query:** The local DNS server queries the root, then TLD, then authoritative server itself step by step, following referrals at each stage (this is the typical pattern between the local server and the rest of the hierarchy).

**DNS Caching:** To reduce the number of queries hitting root/TLD servers, DNS servers cache the results of past lookups for a limited time (a **Time-to-Live, TTL**, sent with the response), speeding up repeated lookups and reducing load on the overall system.

### 2.4.3 DNS Records and Messages

DNS servers store information as **resource records (RR)**, each a four-tuple: `(Name, Value, Type, TTL)`. The meaning of Name and Value depends on Type:

- **Type A:** Name = hostname, Value = its IP address (the standard hostname → IP mapping).
- **Type NS:** Name = a domain, Value = the hostname of an authoritative DNS server that knows how to obtain IP addresses for hosts in that domain (used to walk down the hierarchy).
- **Type CNAME:** Name = an alias hostname, Value = the canonical ("real") hostname it points to.
- **Type MX:** Name = a domain, Value = the canonical name of a mail server for that domain (lets a mail server have an alias name distinguishable from other services' aliases at the same domain).

**DNS messages:** Both queries and replies use the same message format, including a header (with flags marking it as a query vs. reply, whether it's authoritative, etc.) and sections for the question, the answer(s), and any additional records.

DNS runs mostly over **UDP** (fast, lightweight, and DNS queries are typically small — fits well with UDP's connectionless, no-handshake model), falling back to TCP for larger messages.

## 2.5 Peer-to-Peer (P2P) File Distribution

Contrasts the client-server file distribution model with P2P (using **BitTorrent** as the running example):

- **Client-server file distribution:** Time to distribute a file to N users scales roughly linearly (or worse) with N, because the single server's fixed upload bandwidth must be divided among all requesters — the server itself is the bottleneck.
- **P2P file distribution:** Every peer that has downloaded some of the file can simultaneously **upload** pieces of it to other peers. As more peers join, total system capacity actually *grows* (each new peer adds both demand *and* supply) — this is the property of **self-scalability** mentioned earlier.

**BitTorrent specifics:**
- The collection of peers participating in distributing one particular file is called a **torrent**.
- The file is divided into fixed-size **chunks** (pieces); peers download different chunks from different peers, and simultaneously upload chunks they already have to others.
- A **tracker** keeps track of which peers are participating in a torrent.
- Peers use strategies like **rarest first** (prioritize downloading chunks that are least available among neighbors, to keep the overall chunk pool well-distributed) and **tit-for-tat** (a peer prioritizes uploading to peers who are currently uploading to it at the best rate, encouraging reciprocity and discouraging "free-riding").

## 2.6 Video Streaming and Content Distribution Networks

### 2.6.1 Internet Video

Video streaming dominates Internet traffic. A video is essentially a sequence of images displayed at a constant rate, and can be **compressed** to trade off quality vs. bit rate.

### 2.6.2 HTTP Streaming and DASH

- **HTTP streaming:** The video is simply stored as an ordinary file on an HTTP server, and the client uses regular HTTP GET requests to fetch it.
- **DASH (Dynamic Adaptive Streaming over HTTP):** The video is encoded into multiple versions at different bit rates/quality levels, each broken into small chunks. The client's software measures currently-available bandwidth and dynamically requests chunks from whichever quality version fits the current network conditions — this is why video quality can smoothly go up or down while you're watching, adapting to your connection.

### 2.6.3 Content Distribution Networks (CDNs)

CDNs own and manage geographically-distributed servers that store copies of content, and route each user's request to whichever server can deliver content best (usually the closest/least congested), reducing delay and network load. Two general CDN design philosophies:
- **Enter Deep:** deploy many small clusters of servers deep inside access ISPs, close to end users (this was Akamai's original approach).
- **Bring Home:** build fewer, larger clusters at strategic locations (e.g., at IXPs), and "bring" ISPs to these clusters rather than pushing servers deep into every ISP.

CDNs typically use DNS to redirect a client's request to an appropriate nearby server cluster automatically.

### 2.6.4 Case Studies: Netflix and YouTube

Illustrates real-world CDN strategies: Netflix uses a mix of its own CDN infrastructure and third-party cloud services to store and serve pre-encoded video at multiple bit rates; YouTube (Google) relies on Google's own massive global data-center and private-network infrastructure.

## 2.7 Socket Programming: Creating Network Applications

This section is more hands-on/practical — teaching how to actually write networked applications using **sockets**, the programming interface between an application process and the transport layer (introduced conceptually in 2.1.2).

### 2.7.1 Socket Programming with UDP

- UDP is **connectionless** — there's no handshake, so a UDP socket program simply creates a socket and directly sends/receives datagrams, each one explicitly labeled with its destination IP address and port.
- Because UDP offers no reliability, the application itself must handle any needed error-checking or retransmission logic if it cares about reliability.

### 2.7.2 Socket Programming with TCP

- TCP is **connection-oriented** — before any data is exchanged, the client must actively connect to a server socket, and the server must be listening and accept that connection, establishing a dedicated connection between the two sockets.
- Once connected, both sides can simply read/write a continuous, reliable byte stream through the socket, without needing to specify a destination on every send (since the connection was already established) — TCP handles ordering, retransmission of lost data, and flow/congestion control transparently underneath.

## 2.8 Chapter 2 — Key Takeaways

- Network applications follow either a **client-server** or **peer-to-peer (P2P)** architecture (or a hybrid).
- Processes communicate via **sockets**; a process is addressed by an **IP address + port number** pair.
- The Internet offers two transport services: **TCP** (connection-oriented, reliable) and **UDP** (connectionless, unreliable, no-frills) — application requirements (reliability, throughput, timing, security) determine which to use.
- **HTTP** is the Web's protocol: stateless, uses TCP, uses persistent connections by default, structured as request/response messages with methods, status codes, and headers; **cookies** add state; **caching/CDNs** improve performance.
- **Email** uses **SMTP** to push mail between servers, and **POP3/IMAP/webmail** to let users pull mail down to their devices.
- **DNS** is a distributed, hierarchical database (root → TLD → authoritative servers, plus local resolvers and caching) translating hostnames to IP addresses, using resource records like **A, NS, CNAME, MX**.
- **P2P systems** (like BitTorrent) achieve **self-scalability** by having every participant both consume and provide resources.
- **Video streaming** relies on adaptive bit-rate techniques (**DASH**) and **CDNs** to deliver content efficiently at scale.
- **Socket programming** is the practical mechanism through which application code actually uses TCP or UDP.
