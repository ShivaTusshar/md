# Locks: From Races to RISC-V Atomics to Concurrent Data Structures

This guide answers the exact question your earlier *Harts, Threads, and the Thread API* guide deliberately left open: **"how can `lock()` itself be implemented without a race?"** It merges three sources: the CS3105/Luit slide deck (Lecture C2, companion to OSTEP Ch. 28), OSTEP Chapter 28 ("Locks") in full, and OSTEP Chapter 29 ("Lock-based Concurrent Data Structures"). Read this as: **the problem restated → why two intuitive fixes fail → what hardware must provide → how Luit actually uses it → what a lock costs → how real data structures use locks well.**

---

## PART 0 — Where We Left Off

Recall the exact bug from your earlier guides:
```c
counter = counter + 1;
```
```asm
lw    t0, 0(a0)       # load old counter
addi  t0, t0, 1        # compute new value
sw    t0, 0(a0)        # store back
```
**"The C statement looks like one operation. On the machine, it is a load–modify–store sequence. Another hart or thread can interleave between these instructions."** Two harts both reading 100 before either writes back produces a lost update: expected 102, actual 101. **Locks exist because "obvious" code is not automatically atomic.**

## PART 1 — The Basic Idea of a Lock

### 1.1 A lock as a variable with two states
```c
lock_t mutex;
...
lock(&mutex);
balance = balance + 1;   // critical section
unlock(&mutex);
```
A lock is **just a variable** holding one of two states: **available** (unlocked/free — no thread holds it) or **acquired** (locked/held — exactly one thread holds it, presumably inside a critical section). Implementations may store more (which thread holds it, a queue of waiters) — but that's hidden from the user of the lock.

### 1.2 The semantics of `lock()`/`unlock()`
- If the lock is free, `lock()` acquires it immediately and the caller becomes the **owner**.
- If the lock is held, `lock()` **does not return** until the current owner calls `unlock()`.
- On `unlock()`: if nobody is waiting, the lock simply becomes free; if threads are waiting, one of them will eventually notice and acquire it.

### 1.3 What a lock is really doing: handing scheduling control back to the programmer
> "We generally view threads as entities created by the programmer but scheduled by the OS, in any fashion the OS chooses. Locks yield some of that control back to the programmer... Thus locks help transform the chaos that is traditional OS scheduling into a more controlled activity."

This is a genuinely useful way to think about what a lock *is*: not just "a thing that blocks," but a deliberate, programmer-placed constraint on an otherwise arbitrary scheduler.

### 1.4 POSIX naming: mutex
```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
Pthread_mutex_lock(&lock);
balance = balance + 1;
Pthread_mutex_unlock(&lock);
```
POSIX calls a lock a **mutex** (mutual exclusion). Different locks can protect different data — **fine-grained locking** (many locks, each protecting a small piece of data, allowing more concurrency) versus **coarse-grained locking** (one big lock for everything, simpler but more serializing).

The slide deck's diagram of this same idea:
```
                    successful acquire()
      FREE  ───────────────────────────►  HELD
    locked = 0                          locked = 1
      ◄───────────────────────────────
                   release()
```

## PART 2 — Evaluating Locks: The Scorecard

Every lock design in this guide gets judged on the same four axes:

| Criterion | Question |
|---|---|
| **Correctness** | Does it enforce mutual exclusion? At most one thread in the critical section, ever. |
| **Progress** | If the lock is free and threads want it, does *someone* eventually proceed? |
| **Fairness** | Can a waiting thread starve forever, or does every waiter eventually get a turn? |
| **Performance** | CPU time wasted while waiting; uncontended cost; behavior with 1 CPU vs. many CPUs. |

Keep this table in mind through every attempt below — each one fails (or succeeds) on a *specific* one of these axes, and naming which axis is the point of studying "broken" attempts at all.

## PART 3 — Attempt 1: Disable Interrupts

```c
void lock()   { DisableInterrupts(); }
void unlock() { EnableInterrupts(); }
```

### 3.1 Why it seems to work
On a **single processor**, if nothing can interrupt the currently running code, a short region genuinely runs without scheduler preemption — trivially "atomic" by construction. Simple to reason about, and genuinely used historically as the very first mutual-exclusion technique (pre-dating hardware atomic instructions entirely).

### 3.2 Why it fails, as a general-purpose lock
Three concrete problems:
1. **Requires trusting user code with a privileged operation.** A greedy program could call `lock()` immediately and monopolize the CPU forever; a malicious or buggy one could loop endlessly with interrupts off, and the OS would **never regain control** — the only recourse being a full restart.
2. **Does not work on multiprocessors** (this is the point the lecture slide dramatizes):
   ```
        Hart 0                    Hart 1
    interrupts OFF            interrupts ON
            \                    /
             \                  /
              shared kernel data
   ```
   **Hart 0 masking its own interrupts has zero effect on Hart 1.** If both harts try to touch the same shared structure, disabling interrupts on just one of them provides no protection at all — a cross-hart mutual-exclusion mechanism is still needed. This is the same "harts have separate, independent hardware state" fact from your earlier Harts/Threads guide's Part 2.1, now shown to be the *reason* this whole approach fails on modern (multi-core) machines.
3. **Long disabled intervals can lose interrupts.** If interrupts stay off too long, a device interrupt (e.g., "disk read finished") could be missed entirely — and then the OS has no way to know it should wake the process waiting on that I/O.

**Where it's still legitimately used**: inside the OS itself, to protect the OS's *own* internal data structures on a single-hart segment of code, or to prevent certain messy interrupt-handling situations — since the trust issue disappears when the OS is trusting only itself.

### 3.3 The Luit nuance: interrupt disabling solves a *different* problem than the lock itself
This is a genuinely subtle and important point the slide deck adds beyond the plain OSTEP chapter: **Luit disables interrupts while holding a spinlock, but not as the mutual-exclusion mechanism itself** — the atomic instruction (Part 6) is what provides cross-hart exclusion. Interrupt disabling here solves **same-hart self-deadlock**:

```
Normal kernel path on Hart 0             Interrupt handler on Hart 0

acquire(&tickslock);
// lock is held
                                          timer interrupt arrives
                                              acquire(&tickslock);
                                              spins forever: the interrupted
                                              code (which owns the lock) can
                                              never resume to release it
```
If a timer interrupt fires **while this same hart already holds a spinlock**, and the interrupt handler tries to acquire that *same* lock, it will spin forever — because the only code that could ever release the lock is the very code this interrupt just preempted, and that code can't run again until the interrupt handler finishes, which it never will. **This is not a race between two different harts — it's one hart deadlocking against itself via its own interrupt handler.** Therefore: **Luit disables local interrupts before acquiring a spinlock, and restores the previous interrupt state after release** — purely to prevent this self-deadlock, entirely separate from the atomic instruction that provides the actual cross-hart exclusion.

## PART 4 — Attempt 2: A Plain Shared Flag (Ordinary Loads and Stores)

```c
typedef struct { int flag; } lock_t;

void lock(lock_t *lk) {
    while (lk->flag == 1)
        ;                  // spin
    lk->flag = 1;          // take lock
}
void unlock(lock_t *lk) {
    lk->flag = 0;
}
```

### 4.1 The intent, and the flaw
Right idea: wait until the flag looks free, then mark it held. **The flaw: testing and setting are two separate operations, not one.**

### 4.2 The race inside the lock itself
```
Hart 0                         Hart 1              flag
read flag → 0                                        0
                              read flag → 0           0
flag = 1; enter                                       1
                              flag = 1; enter          1
```
**Both harts see the flag as free before either one stores "held."** Both then set it to 1 and both enter the critical section — **the exact same load-then-store race as `counter++` itself, just applied to the mechanism that was supposed to prevent races.** This is the deepest lesson of the whole lecture: **the lock itself needs synchronization** — you cannot bootstrap mutual exclusion out of code that has the identical two-step (test, then set) vulnerability as the original bug.

### 4.3 The performance flaw, separately
Even setting correctness aside: a thread waiting via this `while` loop is **spin-waiting** — burning CPU cycles doing nothing useful. This waste is *especially* bad on a single processor, where the thread holding the lock literally **cannot run** (and thus can't release it) until a context switch eventually happens.

## PART 5 — The Lesson: We Need an Atomic Read-Modify-Write

> "A correct lock needs an operation that reads the old value and writes the new value **as one indivisible step with respect to other harts.**"

```
     read old  ────────────────►  write new
     No other hart may observe the middle.
```

**This property is not about masking interrupts** (that only ever helps within one hart — Part 3.3). It is about **memory-system indivisibility across harts** — a genuinely different, stronger guarantee that only the hardware's memory subsystem itself can provide.

### 5.1 The mental discipline for spotting these bugs: think like a malicious scheduler
> "Pretend you are a malicious scheduler, one that interrupts threads at the most inopportune of times in order to foil their feeble attempts at building synchronization primitives... Although the exact sequence of interrupts may be improbable, it is possible, and that is all we need to demonstrate that a particular approach does not work."

This is worth internalizing as a general debugging habit for concurrent code: to show an approach is broken, you only need to find **one** legal interleaving that breaks it — not argue about which interleavings are "likely."

## PART 6 — Hardware Atomics: From TestAndSet to RISC-V AMO

### 6.1 The abstract primitive: TestAndSet
```c
int TestAndSet(int *addr, int newval) {
    int old = *addr;
    *addr = newval;
    return old;
}
```
| old value returned | meaning |
|---|---|
| 0 | I acquired the lock |
| 1 | somebody already owns it |

**Only the atomic hardware version of this is meaningful** — the C-looking pseudocode above merely *describes the effect*; on real hardware, this read-then-write happens as a single indivisible step, with no other hart able to observe an in-between state. (Historically, called by different names per architecture: `ldstub` on SPARC, locked `xchg` on x86 — this instruction family has existed since the earliest multiprocessor systems, e.g., the Burroughs B5000 in the early 1960s.)

### 6.2 The RISC-V realization: AMOSWAP
```asm
# conceptual effect of amoswap.w
old = memory[addr]
memory[addr] = new
return old

# lock acquisition shape
amoswap.w.aq old, one, (addr)
```
- **AMOSWAP** performs the read and the write atomically with respect to *competing atomic accesses* from other harts.
- The **`.aq`** suffix gives **acquire ordering** specifically for lock acquisition (Part 9 unpacks exactly what this buys you).
- **Scope note the lecture is careful about**: assume the base RISC-V "A" (atomic) extension profile used by Luit; don't assume newer optional store-release or AMOCAS forms unless the specific target explicitly enables them.

### 6.3 Why this actually fixes the race
```
                       lock initially 0
      Hart 0: AMOSWAP(lock,1)         Hart 1: AMOSWAP(lock,1)
             old = 0                          old = 1
            SUCCESS                         FAIL / spin
```
**The impossible result, guaranteed never to happen: Hart 0 returns 0 *and* Hart 1 also returns 0.** Exactly one hart can ever see the "old value was 0" result for a given swap to 1 — this is precisely the "no other hart may observe the middle" property from Part 5, now backed by a concrete hardware guarantee rather than a wish.

## PART 7 — The First Working Spinlock

```c
typedef struct { int locked; } lock_t;

void lock(lock_t *lk) {
    while (TestAndSet(&lk->locked, 1) == 1)
        ;      // spin
}
void unlock(lock_t *lk) {
    lk->locked = 0;
}
```
**Why it works, traced through both cases:**
- **Lock is free** (`locked == 0`): `TestAndSet(locked, 1)` atomically returns the old value `0` *and* sets `locked` to `1` in the same indivisible step — the calling thread doesn't spin, and the lock is now held, all at once. No other thread can slip in between "seeing 0" and "setting 1," because those are now literally the same hardware operation.
- **Lock is held** (`locked == 1`): `TestAndSet` keeps returning `1` (and harmlessly re-sets it to `1` each time) for as long as another thread holds it — the caller spins. The moment the holder calls `unlock()` (`locked = 0`), the *next* `TestAndSet` call to observe that transition will get `old == 0`, acquire the lock, and proceed.

**Why it's called a "spin" lock**: it's the simplest lock to build, and it works purely by spinning — burning cycles — until the lock frees up. **On a single processor, it requires a preemptive scheduler** (timer-interrupt-driven, per your earlier VM guide's Part 1.1 multiprogramming discussion) — without preemption, a spinning thread on a single CPU would spin *forever*, since nothing would ever force the lock-holder back onto the CPU to release it.

### 7.1 Evaluating this spinlock against the Part 2 scorecard
- **Correctness**: ✅ Yes — only one thread ever enters the critical section, guaranteed by the atomic RMW.
- **Fairness**: ❌ **No guarantee at all.** A spinning thread could, in principle, spin forever under contention — this basic spinlock provides zero fairness and can starve a thread.
- **Performance**:
  - **Single CPU**: potentially painful — if the lock-holder is preempted *inside* the critical section, every other thread (say N−1 of them) will each spin for an entire wasted timeslice before giving up the CPU.
  - **Multiple CPUs** (with roughly as many threads as CPUs): spinlocks actually work reasonably well — if Thread A on CPU 1 holds a short critical section and Thread B spins on CPU 2 waiting, B doesn't waste much, since the wait is genuinely short and B isn't preventing A from finishing (they're on separate hardware).

## PART 8 — Reading the Luit Kernel: `acquire()` and `release()`

### 8.1 `acquire()`, line by line
```c
void acquire(struct spinlock *lk) {
    push_off();

    if (holding(lk))
        panic("acquire");

    while (__sync_lock_test_and_set(&lk->locked, 1) != 0)
        ;

    __sync_synchronize();
    lk->cpu = hal_hart_id();
}
```

| Line | Purpose |
|---|---|
| `push_off()` | Local interrupt discipline — the self-deadlock defense from Part 3.3, entered *before* attempting the atomic acquire. |
| `holding(lk)` check → `panic` | Catch a self-acquire bug immediately (Part 8.4). |
| `__sync_lock_test_and_set(...)` loop | The actual atomic ownership acquisition — this is Luit's portable route to the RISC-V AMO from Part 6.2 (see Part 8.2 below for the mapping). |
| `__sync_synchronize()` | The memory-ordering barrier (Part 9). |
| `lk->cpu = hal_hart_id()` | Debug/owner metadata — **not** part of the actual locking mechanism (Part 8.5). |

### 8.2 How OSTEP's TestAndSet maps onto Luit's real source
| OSTEP | C builtin | RISC-V |
|---|---|---|
| `TestAndSet` | `__sync_lock_test_and_set` | atomic RMW |

Until you disassemble the exact build, the honest description is "compiler atomic RMW on the RISC-V A-enabled target" — on many builds this lowers to an AMO such as **AMOSWAP with acquire ordering**, exactly as sketched in Part 6.2. **The stable OS-level idea, regardless of exact codegen**: Luit's `acquire()` relies on a genuine hardware atomic operation, never a normal load/store flag (Part 4's broken attempt).

### 8.3 `release()`, line by line
```c
void release(struct spinlock *lk) {
    if (!holding(lk))
        panic("release");

    lk->cpu = -1;
    __sync_synchronize();
    __sync_lock_release(&lk->locked);

    pop_off();
}
```
In order: verify the current hart actually owns this lock (another self-check, symmetric to `acquire`'s); clear the debug ownership metadata **before** making the lock free (so no other hart can ever observe stale ownership info alongside a freshly-available lock); place a memory barrier so that all the critical section's memory effects are visible to other harts before the lock word itself is released (Part 9 explains exactly why the *order* of these two steps matters); release the atomic lock word; and finally restore the local interrupt state via the nesting discipline (Part 8.6).

### 8.4 Non-recursive locks: a hart must not acquire a lock it already holds
```
holds L  →  acquire(L)  →  waits ... forever
```
If a hart already holds spinlock `L` and then (through a bug, or through nested code calling into itself) tries to `acquire(L)` again, it will spin waiting for `L` to become free — but **the only code that could ever release `L` is this exact execution stream, which is now stuck spinning instead of running.** This is a **silent deadlock**, and it's entirely self-inflicted (no other hart or thread is even involved). **`holding(lk)` + `panic("acquire")` turns this into an immediate, loud kernel bug report** the moment it happens, rather than a mysterious hang that has to be debugged after the fact.

### 8.5 Do not confuse metadata with locking
| Field | Role | Used for |
|---|---|---|
| `lk->locked` | **the atomic lock word** | The actual synchronization mechanism — atomic test-and-set changes it 0→1. |
| `lk->cpu` | owner/debug metadata | Helps `holding()` and diagnostics. **Does not, by itself, make the lock correct.** |

**The atomic operation on `locked` is the lock.** `lk->cpu` is bookkeeping *about* the lock (which hart currently owns it, for debugging and for the self-acquire check), but it carries **zero synchronization power** on its own — if you removed `lk->cpu` entirely, the lock would still correctly provide mutual exclusion; if you removed the atomic operation on `lk->locked` and replaced it with a plain read/write, you'd be right back to Part 4's broken flag, no matter how much metadata surrounded it.

### 8.6 Why `push_off`/`pop_off`, not just `intr_off`/`intr_on`: nesting

| Step | Operation | `noff` | Interrupt state |
|---|---|---|---|
| start | — | 0 | ON |
| 1 | `acquire(A)` | 1 | OFF |
| 2 | `acquire(B)` | 2 | OFF |
| 3 | `release(B)` | 1 | **still OFF** |
| 4 | `release(A)` | 0 | restore original |

**If `release(B)` simply turned interrupts back on**, then between steps 3 and 4, interrupts would be enabled *while lock A is still held* — reopening exactly the same-hart self-deadlock hazard from Part 3.3 (an interrupt could now fire, try to acquire A, and spin forever against itself). `push_off`/`pop_off` track a **nesting count** (`noff`) instead of a raw on/off flag: interrupts are only genuinely re-enabled once the *outermost* held lock is released, restoring the interrupt state exactly as it was before the very first `acquire()` in the nest.

## PART 9 — Atomicity Is Not the Whole Story: Ordering

### 9.1 Two separate properties a lock must provide
| Property | Meaning |
|---|---|
| **Ownership** | Only one thread/hart is inside the critical section. This comes from the atomic RMW (Parts 6–7). |
| **Ordering** | Loads/stores *inside* the protected region must not effectively "move outside" the acquire/release boundaries, as observed by other harts. |

> "Atomicity decides **who owns the lock**. Memory ordering decides **what memory effects are properly inside the protected interval**."

This is a genuinely subtle addition beyond simple atomicity: even with a perfectly correct atomic RMW securing *ownership*, a modern CPU's memory system (and compiler) may otherwise be free to reorder ordinary loads/stores for performance — meaning a write made *inside* the critical section could, absent an explicit ordering guarantee, become visible to another hart either *before* the lock was actually acquired, or *after* it was already released. Both would silently break the whole point of having a critical section, even though "ownership" was never violated.

### 9.2 `.aq` and `.rl`: the architectural model
```asm
# Acquire path: later memory ops stay after lock acquisition
amoswap.w.aq old, one, (lock)

# Release path: earlier memory ops stay before lock release
amoswap.w.rl x0, zero, (lock)
```
- **`.aq`** (acquire) on the lock-taking instruction ensures memory operations that come *after* it in program order cannot be observed as happening *before* the lock was actually acquired.
- **`.rl`** (release) on the lock-releasing instruction ensures memory operations that come *before* it cannot be observed as happening *after* the lock was released.
- **Scope caution repeated from Part 6.2**: don't assume a plain `sw.rl` works for the base A profile used here, and don't assume newer optional store-release or AMOCAS forms unless the target profile specifically enables them.
- **In practice, Luit's C source expresses this ordering through compiler builtins** — specifically `__sync_synchronize()` — rather than hand-written `.aq`/`.rl` assembly, which is exactly what you saw at the concrete source level in Part 8.1 and 8.3.

### 9.3 A deliberate, important contrast: lock barriers vs. `sfence.vma`
| Operation | What it orders/flushes | Where you saw it |
|---|---|---|
| `sfence.vma` | Address-translation state: page-table changes and TLB translations | Virtual memory and page-fault repair (earlier VM/Page-Faults guides) |
| Lock acquire/release barriers | Ordinary shared-data memory ordering around critical sections | Concurrency and synchronization (this guide) |

**Both are ordering/visibility tools, but they solve genuinely different problems** — this is a distinction worth being precise about in a viva, since both instructions involve the word "fence"/"barrier" and both matter to correctness, but they operate on completely different kinds of state. `sfence.vma` ensures the CPU's cached *translations* (VA→PA mappings) are consistent with a freshly-modified page table (recall the earlier VM guide's Part 5.5, and the Page Faults guide's Part 11 — both scenarios there were specifically about **stale TLB entries**, not about ordinary data races). A lock's memory barrier, by contrast, has nothing to do with address translation at all — it ensures ordinary **data** reads/writes to shared memory become visible to other harts in the right order relative to the lock acquire/release. Confusing the two — e.g., assuming a page-table change is safe without `sfence.vma` because "there's a lock around it" — would be a real bug, since a data-ordering barrier says nothing about translation caches.

## PART 10 — Other Hardware Primitives

### 10.1 The family, at a glance
| Primitive | Effect | Why it matters |
|---|---|---|
| TestAndSet / Swap | Return old value; install new value. | Natural for simple spinlocks (Parts 6–7). |
| CompareAndSwap | If memory equals `expected`, replace it; return old value either way. | Common in lock-free algorithms; more powerful than TestAndSet. |
| LR/SC (Load-Reserved/Store-Conditional) | Load-reserve, then store succeeds only if the reservation is still valid. | RISC-V's base-A way to build conditional atomics, including CAS-like behavior. |
| FetchAndAdd | Return old value; increment memory. | Builds ticket locks and scalable counters. |

### 10.2 Compare-and-swap (CAS)
```c
int CompareAndSwap(int *ptr, int expected, int new) {
    int original = *ptr;
    if (original == expected)
        *ptr = new;
    return original;
}
```
(Called compare-and-exchange on x86, compare-and-swap on SPARC.) Building a lock with it is nearly identical to TestAndSet:
```c
void lock(lock_t *lock) {
    while (CompareAndSwap(&lock->flag, 0, 1) == 1)
        ; // spin
}
```
As a *lock*, CAS's behavior is functionally identical to the plain spinlock from Part 7 — but CAS is a **strictly more powerful primitive**, since it lets code check "did the value change to something unexpected since I last looked?" — the foundation for **lock-free synchronization** techniques covered elsewhere, well beyond simple locking.

### 10.3 RISC-V's base-A note on CAS: no native instruction required
> "Base A does not require a native CAS instruction... In the base A profile, CAS-like behaviour is constructed with LR/SC loops. Newer optional Zacas adds AMOCAS, but do not assume it for LUIT unless the toolchain/target profile enables it."

```asm
retry:
    lr.w   t0, (addr)          # read + reserve
    bne    t0, expected, fail
    sc.w   t1, new, (addr)     # t1=0 success, nonzero fail
fail:
    bnez   t1, retry
```
**Mental model**: LR says "remember I read this address"; SC says "store only if nobody disturbed my reservation" — if any other hart wrote to that address between this hart's LR and SC, the SC simply fails (returns nonzero), and correct software retries. **For this lecture, AMOSWAP (Part 6.2) remains the main path into Luit's actual spinlock** — LR/SC is presented as the *general* RISC-V mechanism CAS-like behavior is built from, not necessarily what Luit's specific spinlock uses directly.

### 10.4 Fetch-and-add and ticket locks: buying fairness
```c
int FetchAndAdd(int *ptr) {
    int old = *ptr;
    *ptr = old + 1;
    return old;
}
```
```c
typedef struct { int ticket; int turn; } lock_t;

void lock(lock_t *lock) {
    int myturn = FetchAndAdd(&lock->ticket);
    while (lock->turn != myturn)
        ;      // spin
}
void unlock(lock_t *lock) {
    lock->turn = lock->turn + 1;
}
```
**The mechanism**: acquiring the lock atomically grabs the next "ticket" number; a thread proceeds only once the globally-visible `turn` counter reaches its own ticket number; releasing simply advances `turn` by one, letting the *next* waiting thread in line proceed.

**The genuinely new property this buys, beyond the basic spinlock**: **it guarantees progress for every thread, not just for whichever thread happens to win a race.** Once a thread has been handed a ticket, it is *guaranteed* to be scheduled at some point once everyone ahead of it has passed through — unlike the plain TestAndSet spinlock (Part 7), where a spinning thread could, in the worst case, lose every single race forever and starve indefinitely.
```
Lesson: hardware atomics can build stronger fairness than a basic spinlock,
but at extra cost and complexity.
```

## PART 11 — Real Kernel Data: What Locks Actually Protect

### 11.1 The Luit lock inventory
| Lock | Protected data / invariant | Why it matters |
|---|---|---|
| `kmem.lock` | Free physical-page list | Two harts must not allocate the same page. |
| `p->lock` | One process/thread's state | Scheduling and state transitions must be consistent. |
| `pid_lock` | Next PID counter | Avoid duplicate PIDs. |
| `wait_lock` | Parent/child wait-exit relations | Avoid lost child-exit state. |
| `tickslock` | Timer tick counter | Consistent update/read of ticks. |
| `bcache.lock` | Buffer-cache metadata | Avoid duplicate/conflicting buffers. |

This is the concrete payoff of your earlier Harts/Threads guide's Part 9.2 — the same table appeared there as *motivation* ("here's why the kernel needs locks even without user threads"); here you finally have the actual mechanism (Parts 6–8) that makes each of these locks correct.

### 11.2 Worked example: the physical-page free list
```
      Hart 0                                        Hart 1
     kalloc()                                       kalloc()
         \                                            /
          \                                          /
           free-page list in physical memory
                        |
        acquire(&kmem.lock);
            // remove one page from free list
        release(&kmem.lock);
```
**Invariant**: each free page appears at most once on the list; no two harts remove the same node at the same time. Recall the earlier VM guide's Part 6.8 — `palloc()`/`pfree()` implement the freelist by threading a `struct run { struct run *next; }` pointer through the free pages themselves, popping the head to allocate. **Without `kmem.lock`, two harts could both read the same freelist head simultaneously (Part 4's exact race, just relocated to a pointer instead of an integer), and both would believe they'd claimed the same physical page** — precisely the catastrophic scenario your earlier Harts/Threads guide's Part 9.2 flagged as a real, serious consequence: two processes silently sharing one physical frame, with no fault ever raised to signal the corruption.

## PART 12 — Too Much Spinning: What Now?

### 12.1 The problem, restated concretely
Two threads, one CPU. Thread 0 holds a lock, gets preempted mid-critical-section. Thread 1 tries to acquire, finds it held, and **spins for an entire wasted timeslice** before a timer interrupt finally lets Thread 0 run again and release the lock. With N threads all contending, N−1 timeslices can be wasted this way — pure waste, since none of that spinning does any useful work.

> **The crux: how can we develop a lock that doesn't needlessly waste time spinning on the CPU? Hardware support alone cannot solve this — we need OS support too.**

### 12.2 First try: just yield
```c
void lock() {
    while (TestAndSet(&flag, 1) == 1)
        yield();     // give up the CPU instead of spinning
}
```
`yield()` is an OS primitive that moves the calling thread from **running** to **ready**, descheduling itself and promoting some other thread to run. **Works reasonably well with just two threads on one CPU** — but with many threads (say 100) contending, the other 99 will each run-and-yield in a round-robin pattern before the lock-holder gets scheduled again, and **a context switch itself has real cost**, so this still wastes a great deal compared to the ideal. **Worse: it still does not address starvation** — a thread can be caught in an endless yield loop while others repeatedly cut in and take the lock instead.

### 12.3 A genuine correctness hazard spin locks introduce: priority inversion
This is worth flagging as a *correctness*, not just performance, reason to be wary of spin locks. Suppose Thread T2 has higher scheduling priority than T1, and the scheduler always prefers T2 when both are runnable. If **T1 grabs a spin lock**, then **T2 becomes runnable and immediately preempts T1** (because T2 is higher priority), and T2 then tries to acquire the *same* lock — **T2 will spin forever**, because T1 (the only thread that could release the lock) can never be scheduled again, since the scheduler always prefers T2 over T1. **The system hangs.**

More insidiously, this can occur even with three threads and no direct lock contention between the highest and lowest priority ones: T1 (lowest) holds a lock; T3 (highest) preempts T1 and blocks waiting for the lock; T2 (middle) becomes runnable and, being higher priority than T1, simply runs indefinitely — starving out T1 (who could release the lock) even though T2 itself doesn't even want the lock, and thereby indirectly starving T3 as well, despite T3 having the *highest* priority in the system. (This is a documented real-world bug class — it occurred on the Mars Pathfinder mission.)

**Mitigations**: avoid spin locks specifically in priority-differentiated systems; **priority inheritance** (temporarily boost a lock-holder's priority to that of the highest-priority thread waiting on it, so it can finish and release); or the simplest fix — give all relevant threads the same priority.

### 12.4 A better fix: queues, sleeping instead of spinning
The real problem with yielding is that it **leaves too much to chance** — the scheduler decides who runs next, with no coordination to who's actually waiting for what. The fix requires **explicit control** over which thread gets the lock next, via a queue plus OS support:
```c
void lock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1)
        ;                              // spin briefly, just for the guard
    if (m->flag == 0) {
        m->flag = 1;                   // lock acquired
        m->guard = 0;
    } else {
        queue_add(m->q, gettid());
        m->guard = 0;
        park();                        // sleep — give up the CPU entirely
    }
}
void unlock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1)
        ;
    if (queue_empty(m->q))
        m->flag = 0;                   // free; nobody wants it
    else
        unpark(queue_remove(m->q));    // hand the lock directly to the next waiter
    m->guard = 0;
}
```
Two ideas combined: a `guard` field acts as a tiny **inner spinlock** that protects only the bookkeeping (the flag and the queue) — the actual spin-waiting here is limited to a handful of instructions, never the user's full critical section. `park()`/`unpark(threadID)` (a Solaris-style primitive; similar mechanisms exist elsewhere) let a thread that can't get the lock **truly sleep** — no CPU wasted — until explicitly woken by whoever releases it.

**A subtle, deliberate design point**: when a thread is `unpark`ed, `flag` is **not** reset to 0 in between — the lock is passed **directly** from the releasing thread to the next waiter, since the woken thread doesn't hold `guard` at that moment and so couldn't safely set `flag` itself anyway.

### 12.5 The wakeup/waiting race, and `setpark()`
There's a genuine remaining race just before `park()`: if a thread is about to sleep (believing the lock is still held), and gets switched out right before actually parking, another thread could release the lock and call `unpark()` in that gap — and the first thread's *subsequent* `park()` call would then sleep **forever**, having missed the wakeup entirely. (This is precisely the **lost wakeup** hazard named in your earlier Harts/Threads guide's Part 9.3 companion map.) **Solaris's fix**: a third call, `setpark()`, lets a thread declare "I am about to park" — if it's interrupted and `unpark` is called before the actual `park()`, the subsequent `park()` returns immediately instead of sleeping. (An alternative design: pass the guard into the kernel, letting it atomically release the lock and dequeue the thread as one operation.)

### 12.6 Linux's real-world answer: futex
Linux provides a **futex** — associated with a specific physical memory address plus a per-futex in-kernel wait queue. Two calls: `futex_wait(address, expected)` sleeps *only if* the value at `address` still equals `expected` (avoiding exactly the lost-wakeup race from Part 12.5 by making the check-and-sleep atomic within the kernel); `futex_wake(address)` wakes one waiter.

**A clever real-world optimization worth noting**: Linux's mutex implementation packs *both* "is the lock held" (the high bit) and "how many threads are waiting" (the remaining bits) into a **single integer** — when uncontended, acquiring/releasing costs just one atomic bit-test-and-set plus one atomic increment, with **no futex syscall at all** in the common case. The kernel is only bothered when there's genuine contention.

### 12.7 Two-phase locks: combining both ideas
> "A two-phase lock realizes that spinning can be useful, particularly if the lock is about to be released."

Phase 1: spin for a short while, hoping the lock frees up quickly (cheap if it does). Phase 2: if it doesn't free up in that window, fall back to sleeping via `park`/`futex`-style OS support. Linux's futex-based mutex above is a (single-spin) instance of exactly this pattern — a more general version would spin in a bounded loop before falling back to sleeping. **Whether this actually helps depends heavily on hardware, thread count, and workload** — there's no universally optimal lock design.

## PART 13 — Spin vs. Sleep: The Decision the Kernel Must Make

### 13.1 The scheduler-awareness problem
> "The scheduler does not know who holds the lock."

```
A holds the lock
   A    B    C    D            A    B    C    D
      B/C/D spin           A finally runs and unlocks
```
If B, C, and D are all spinning waiting for A to release a lock, a naive scheduler may simply keep giving B, C, and D their fair share of timeslices anyway — even though **only A** can actually make progress by finishing its critical section and releasing the lock. This wastes real CPU time on three threads that are structurally incapable of doing anything useful until a fourth, currently-descheduled thread gets to run. **This is precisely what motivates yield, blocking locks, and sleep/wakeup** as covered in Part 12.

### 13.2 The general spin-vs-sleep tradeoff
| Comparison | Spin | Sleep / block |
|---|---|---|
| Cost | Burns CPU while waiting | Pays context-switch and wakeup overhead |
| Best when | Expected wait *t* ≪ context-switch cost *C* | Expected wait *t* > *C* |
| Kernel use | Short critical sections; never sleep while holding | Long waits, I/O, condition waiting |

**The honest caveat**: *we usually don't know t in advance.* Real systems don't try to solve this perfectly in general — they use **simple rules and separate primitives**: spinlocks for genuinely short kernel critical sections (Luit's actual approach throughout this guide), and sleep/wakeup or sleep-locks for anything expected to wait a long time.

## PART 14 — Lock-Based Concurrent Data Structures (OSTEP Ch. 29)

Having a correct lock (Parts 1–13) is only step one. **Where you put the lock, and how much code you put inside it, determines both correctness and performance** of any larger data structure built on top.

### 14.1 The simplest pattern: one lock around every method
```c
typedef struct { int value; pthread_mutex_t lock; } counter_t;

void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}
```
This is "thread safe" and correct — and structurally resembles the automatic lock/unlock discipline of **monitors**, where entering/exiting an object's methods automatically acquires/releases a lock. **If this is fast enough, stop here** — "no need to do something fancy if something simple will work."

### 14.2 When simple isn't fast enough: the approximate (sloppy) counter
**The problem, measured**: a single global lock around a shared counter, updated a million times per thread, scales *terribly* — 1 thread: ~0.03s; 2 threads: over 5 seconds; worse with more. This is far from **perfect scaling** (where N threads finish in the same time as 1, since the work is genuinely parallel).

**The fix**: represent one logical counter as **many local physical counters (one per CPU) plus one global counter**, each with its own lock:
```c
typedef struct {
    int global; pthread_mutex_t glock;
    int local[NUMCPUS]; pthread_mutex_t llock[NUMCPUS];
    int threshold;
} counter_t;

void update(counter_t *c, int threadID, int amt) {
    int cpu = threadID % NUMCPUS;
    pthread_mutex_lock(&c->llock[cpu]);
    c->local[cpu] += amt;
    if (c->local[cpu] >= c->threshold) {
        pthread_mutex_lock(&c->glock);
        c->global += c->local[cpu];
        pthread_mutex_unlock(&c->glock);
        c->local[cpu] = 0;
    }
    pthread_mutex_unlock(&c->llock[cpu]);
}
```
**Mechanism**: increments almost always just touch the **local**, per-CPU counter and its own lock — no cross-CPU contention at all in the common case. Only when a local counter reaches a threshold `S` does it get flushed into the global counter (briefly taking the global lock).

**The tradeoff, explicit and tunable**: small `S` behaves almost like the plain global-lock counter (accurate, but not scalable); large `S` scales beautifully (measured: near-perfect scaling even at 4 threads/4 CPUs) but the value returned by `get()` can lag the true count by up to `S × NUMCPUS`. **`get()` is explicitly documented as returning only an approximation** — this is a genuine, named accuracy/performance tradeoff, not a bug.

> **Tip: more concurrency isn't necessarily faster.** A scheme that adds overhead (frequent lock acquisition, extra complexity) may not pay for itself. Simple, low-overhead schemes often win. The only way to really know is to build both and measure.

### 14.3 Concurrent linked lists: shrink the critical section, don't just wrap the whole function
**Naive version**: lock the entire `insert`/`lookup` function, including `malloc()` and the failure path. **Problem**: a `malloc()` failure now requires remembering to `unlock()` before returning — an easy bug to introduce, and empirically a common one (the chapter cites a study finding ~40% of Linux kernel bugs occur on such rarely-exercised error paths).

**The fix**: only lock the part that genuinely touches shared state.
```c
int List_Insert(list_t *L, int key) {
    node_t *new = malloc(sizeof(node_t));   // NOT locked — malloc is its own thread-safe structure
    if (new == NULL) { perror("malloc"); return -1; }
    new->key = key;

    pthread_mutex_lock(&L->lock);            // only the shared-list update needs the lock
    new->next = L->head;
    L->head = new;
    pthread_mutex_unlock(&L->lock);
    return 0;
}
```
And for lookup, restructure to a **single exit path** (set a return-value variable, `break` out of the loop, unlock once) rather than multiple early-return points each needing their own paired unlock — fewer lock/unlock sites means fewer chances to forget one.

> **General tip: be wary of locks and control flow.** Any function that acquires a lock (or allocates memory, or holds other stateful resources) and then has an early-exit error path must remember to undo that state before returning on *every* path — a structurally error-prone pattern worth minimizing wherever possible.

**Scaling further — hand-over-hand locking (lock coupling)**: instead of one lock for the whole list, put a lock **per node**; traversal grabs the next node's lock before releasing the current node's. Conceptually enables more concurrent traversals — but **in practice, the per-node lock acquire/release overhead usually makes it slower than just using one simple lock**, even for large lists and many threads. A worthwhile lesson: more fine-grained locking is not automatically a win; it has to actually be measured.

### 14.4 Concurrent queues: two locks instead of one (Michael and Scott)
```c
typedef struct {
    node_t *head, *tail;
    pthread_mutex_t head_lock, tail_lock;
} queue_t;
```
**The trick**: a **dummy node**, allocated at initialization, sits permanently between `head` and `tail` conceptually — this lets `enqueue` (which only ever touches the tail) and `dequeue` (which only ever touches the head) use **separate locks**, so the two operations can genuinely proceed concurrently with no contention between them, in the common case. (A fully-general bounded queue — one where a thread can *wait* if the queue is empty or full — needs condition variables, explicitly flagged as the subject of the next chapter, not this one.)

### 14.5 Concurrent hash table: many locks, one per bucket
```c
#define BUCKETS (101)
typedef struct { list_t lists[BUCKETS]; } hash_t;

int Hash_Insert(hash_t *H, int key) {
    return List_Insert(&H->lists[key % BUCKETS], key);
}
```
Built directly on top of the concurrent linked list from Part 14.3, with **one lock per bucket** rather than one lock for the entire table. **This scales magnificently** — measured performance shows the hash table scaling far better than a plain single-locked linked list under concurrent load, precisely because operations on different buckets never contend with each other at all.

### 14.6 The general lessons from Chapter 29
1. **Start with a single lock around everything.** It's simple and correct — only add complexity if measurement shows you actually need to.
2. **Be careful with control flow around locks** — error/early-return paths are exactly where "forgot to unlock" bugs hide.
3. **Reducing the size of the critical section** (locking only what genuinely needs protecting, not the whole function) often helps more, and more safely, than adding more locks.
4. **More locks/more concurrency is not automatically faster** — measure. Fine-grained approaches (hand-over-hand lists) can lose to simple ones (single-locked lists) once overhead is accounted for; other fine-grained approaches (per-bucket hash tables) can win decisively. There's no substitute for actually benchmarking your specific structure and workload.

| Term | One-line meaning |
|---|---|
| **Spinlock** | A lock where a waiting thread busy-waits (spins) rather than sleeping |
| **TestAndSet / AMOSWAP** | Atomic read-modify-write: read the old value, install a new one, indivisibly |
