# Condition Variables, Semaphores, Concurrency Bugs, and Events: Complete Concept Guide

This guide covers four connected OSTEP chapters plus their Luit realization: **Ch. 30 (Condition Variables)**, **Ch. 31 (Semaphores)**, **Ch. 32 (Common Concurrency Problems)**, and **Ch. 33 (Event-Based Concurrency)**. Together they answer the question your earlier *Locks* guide's Part 13 left open — locks solve *mutual exclusion*, but what does a thread do when it needs to **wait for some other thread to make something true**? And once you have locks and condition variables, what actually goes wrong in real code, and is there an alternative to threads entirely?

## PART 0 — Where We Left Off

Your earlier Locks guide established that a spinlock is correct for short critical sections but wasteful for long waits (Part 13's spin-vs-sleep table). This raises today's question directly:

```
short wait        long wait         condition false
   spin      →   sleep/block   →   wait for state
```

**Today's question: how can a thread wait without burning a hart (or CPU)?**

## PART 1 — The Crux: Waiting for a Condition

```c
while (condition_is_false)
    wait somehow;
// condition is now true enough to proceed
```

Common OS situations needing exactly this:
- A parent waits for a child to finish.
- A consumer waits until a buffer is non-empty.
- A producer waits until a buffer has space.
- A process waits for disk, pipe, or child state to change.

> **A condition variable lets a thread sleep until another thread changes relevant state.**

---

## PART 2 — Motivating Example: Parent Waiting for a Child

```c
void *child(void *arg) {
    printf("child\n");
    // XXX how to indicate we are done?
    return NULL;
}
int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    pthread_t c;
    pthread_create(&c, NULL, child, NULL);
    // XXX how to wait for child?
    printf("parent: end\n");
    return 0;
}
```
**Desired order**: `parent: begin` → `child` → `parent: end`. The parent needs an **ordering constraint**: don't finish before the child has completed. Note this is the `pthread_join()` problem your earlier Harts/Threads guide's Part 10.4 mentioned using without explaining the mechanism — this chapter supplies that mechanism.

### 2.1 The bad first idea: spin on a shared flag
```c
volatile int done = 0;
void *child(void *arg) {
    printf("child\n");
    done = 1;
    return NULL;
}
// parent
while (done == 0)
    ;    // spin
```
**This will generally work** — it's not incorrect — but it is **hugely inefficient**: the parent burns an entire hart repeatedly checking a value that only changes once, somewhere else. (Recall from the earlier Locks guide's Part 4.3: spin-waiting is "especially bad on a single processor, where the thread being waited for cannot even run until a context switch occurs.") **We want the parent to sleep, not spin.**

## PART 3 — Condition Variable: The Basic Idea

### 3.1 Three separate pieces, not one
| Piece | Role |
|---|---|
| **Shared predicate** (`done`, `count`, `bytesLeft`) | The actual condition being waited for — ordinary shared program state |
| **Mutex** | Protects the predicate from races while it's being checked or changed |
| **Condition variable** | An explicit **queue of sleeping threads**, waiting on this particular predicate |

> **The condition variable is not the condition itself. The condition is the shared program state.**

This is the single most important distinction in the whole chapter, worth internalizing before anything else: a CV has **no memory of its own** about whether the predicate is true — it only holds a list of who's currently asleep waiting to be told to re-check.

### 3.2 The basic usage pattern
```c
while (predicate_is_false)
    pthread_cond_wait(&cv, &mutex);
// when woken, check predicate again
```

### 3.3 The POSIX API
```c
int pthread_cond_wait(pthread_cond_t *c, pthread_mutex_t *m);
int pthread_cond_signal(pthread_cond_t *c);
int pthread_cond_broadcast(pthread_cond_t *c);
```
| Operation | Meaning |
|---|---|
| `wait(c, m)` | Release mutex `m` and sleep, **atomically**; re-acquire `m` before returning |
| `signal(c)` | Wake one waiter, if any |
| `broadcast(c)` | Wake **all** waiters |

**`wait()` assumes the mutex is already held** by the caller — this isn't optional context, it's a precondition of the call.

## PART 4 — The Correct Parent/Child Pattern

```c
int done = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  c = PTHREAD_COND_INITIALIZER;

void thr_exit() {
    pthread_mutex_lock(&m);
    done = 1;
    pthread_cond_signal(&c);
    pthread_mutex_unlock(&m);
}
void thr_join() {
    pthread_mutex_lock(&m);
    while (done == 0)
        pthread_cond_wait(&c, &m);
    pthread_mutex_unlock(&m);
}
```
**The CV does not remember completion; `done` remembers completion.** This sentence is worth memorizing verbatim — it's the direct payoff of Part 3.1's three-piece separation.

### 4.1 Case A: parent sleeps first
```
parent: lock+check → done=0 → wait          child runs → done=1 → signal
                                                                        ↓
                                             parent wakes → rechecks → predicate true → parent end
```
`wait()` releases the mutex **while the parent sleeps**, which is exactly what lets the child acquire that same mutex and change `done` — if `wait()` didn't release the lock, the child could never get in to make progress, and the parent would deadlock waiting for a condition only the child (now permanently locked out) could ever satisfy.

### 4.2 Case B: child finishes first
```
child runs → done=1 → signal (no waiter yet)          parent: join → sees done=1 → proceeds
```
**No problem at all**: even though the `signal()` call had nobody to wake (the parent hadn't called `join()` yet), the predicate `done` itself already stores the fact that the child completed. The parent's `while (done == 0)` check simply evaluates false immediately, and it never even calls `wait()`. **This is exactly why the predicate must be a real, persistent variable, not something inferred solely from having received a signal.**

## PART 5 — Two Broken Designs, and Why Each Fails

### 5.1 Broken Design 1: no state variable
```c
void thr_exit() {
    pthread_mutex_lock(&m);
    pthread_cond_signal(&c);        // no `done = 1;` anywhere
    pthread_mutex_unlock(&m);
}
void thr_join() {
    pthread_mutex_lock(&m);
    pthread_cond_wait(&c, &m);      // waits unconditionally, no predicate check
    pthread_mutex_unlock(&m);
}
```
**Failure**: if the child runs first (`thr_exit` signals with no waiter), that signal is simply **lost** — nobody was asleep to receive it. Then when the parent later calls `thr_join()`, it unconditionally calls `wait()` and sleeps **forever**, since nothing will ever signal again. > **A condition variable is not a memory cell. It does not remember that a signal happened.** This is the direct cost of skipping Part 3.1's predicate entirely.

### 5.2 Broken Design 2: no lock around the predicate
```c
void thr_exit() {
    done = 1;
    pthread_cond_signal(&c);
}
void thr_join() {
    if (done == 0)
        pthread_cond_wait(&c);     // not real POSIX signature — illustrative
}
```
**The failure window**:
```
parent sees done == 0  →  [gap]  →  child sets done=1 and signals  →  parent sleeps forever
```
Because neither the check of `done` nor the transition into sleeping is protected by a lock, there's a **dangerous gap** between the parent's check and its actual sleep — during that gap, the child can run to completion, set `done = 1`, and signal, **before the parent has actually gone to sleep to receive it**. The signal is emitted into a moment when nobody is listening, and is gone forever. **The mutex closes the dangerous gap between checking the predicate and sleeping** — this is precisely why `pthread_cond_wait()`'s release-and-sleep must happen as one atomic unit (Part 3.3's "atomically" is not decorative language; it is the entire fix for this exact race).

### 5.3 The core, disciplined pattern that avoids both bugs
```c
// Waiting side
pthread_mutex_lock(&m);
while (predicate_is_false)
    pthread_cond_wait(&cv, &m);
// predicate true while holding m
pthread_mutex_unlock(&m);

// Signaling side
pthread_mutex_lock(&m);
change predicate state;
pthread_cond_signal(&cv);
pthread_mutex_unlock(&m);
```
`wait` requires the mutex; **holding it while changing the predicate and signaling is the disciplined pattern.** Both broken designs above violate one half of this: Design 1 has no real predicate to check at all; Design 2 has a predicate but doesn't protect it with the mutex while checking/sleeping.

## PART 6 — Mesa Semantics: Why `while`, Not `if`

### 6.1 The rule
> **A signal means: "the state may have changed." It does not promise that your condition is now true.**

```
thread wakes → re-acquire mutex → check predicate again → continue only if true
```
```c
while (predicate_is_false)
    wait(cv, mutex);
```
This is called **Mesa semantics** (named after the language/system where this convention originated), as opposed to an alternative (**Hoare semantics**) where a signal would guarantee immediate, exclusive handoff of the condition's truth to exactly one waiter. **Mesa semantics is what POSIX and Luit both use** — and it is precisely *why* every correct waiter must re-check its predicate in a loop, never trust a wakeup at face value.

### 6.2 Wakeup is not immediate ownership of the state
```
producer signals C1 → C1 becomes READY → another thread runs → state changes again → C1 finally runs
```
Being made **READY** is not the same as being made **RUNNING**. Between the moment a thread is signaled/woken and the moment the scheduler actually lets it execute, **an arbitrary amount of time can pass, and other threads can run and change the very state the signal was about.** By the time C1 actually gets the CPU, the predicate it was originally woken for may no longer hold. **This is exactly why the re-check happens in a `while` loop** — not a paranoid extra step, but a direct structural consequence of what "ready" genuinely means versus what "running" means.

## PART 7 — Producer/Consumer: The Classic CV Use Case

### 7.1 The problem
Producers generate items; consumers remove them from a **finite (bounded) buffer**. Real examples: web-server work queues, pipes, device buffers, kernel queues.

### 7.2 Single-slot buffer: state and required conditions
```c
int buffer;
int count = 0;   // 0 empty, 1 full

void put(int value) { assert(count == 0); count = 1; buffer = value; }
int  get(void)       { assert(count == 1); count = 0; return buffer; }
```
| Rule | Condition required |
|---|---|
| Producer may `put` | only when `count == 0` |
| Consumer may `get` | only when `count == 1` |

`count` and `buffer` are shared state; a mutex must protect both.

### 7.3 First attempt: one CV and `if` — two bugs

```c
// producer
lock(mutex);
if (count == 1)
    wait(cond, mutex);
put(i);
signal(cond);
unlock(mutex);

// consumer
lock(mutex);
if (count == 0)
    wait(cond, mutex);
tmp = get();
signal(cond);
unlock(mutex);
```
This *works* for a simple one-producer/one-consumer schedule — but **breaks with more waiters**, in two separate ways:
- **Bug 1**: using `if` instead of `while` — a woken thread does not own the future state (exactly Part 6's Mesa-semantics lesson, now shown breaking a real program).
- **Bug 2**: one CV shared for two logically different conditions ("buffer has space" and "buffer has an item") — a signal can wake the *wrong kind* of waiter.

### 7.4 Bug 1, traced: `Tc2` sneaks in
Two consumers, `Tc1` and `Tc2`, both wanting to `get()`:
```
Tc1 waits (count=0) → producer fills (count=1) → signal makes Tc1 READY
   → Tc2 runs first, calls get(), succeeds, count→0
   → Tc1 finally resumes, but it used a plain `if`, so it never rechecks —
     it just proceeds straight into get() → assert(count==1) FAILS, count is 0
```
**The signal was only a hint.** By the time `Tc1` actually got the CPU, `Tc2` had already consumed the item — but `Tc1`'s `if` statement had already decided (once, before sleeping) that it was safe to proceed, and never looked again.

### 7.5 Fix 1: always use `while`
```c
// producer
lock(mutex);
while (count == 1)
    wait(cond, mutex);
put(i); signal(cond); unlock(mutex);

// consumer
lock(mutex);
while (count == 0)
    wait(cond, mutex);
tmp = get(); signal(cond); unlock(mutex);
```
`while` makes wakeup a **hint, not a promise** — exactly Part 6.1's rule. **This fixes Bug 1, but not Bug 2.**

### 7.6 Bug 2: one CV wakes the wrong kind of thread
```
consumers waiting for FULL  ──┐
                                ├──►  one CV `cond`  ◄──┐
producers waiting for EMPTY ──┘                          
```
With a single condition variable, **all waiters are mixed together in one queue**, regardless of *what* they're each actually waiting for. When a consumer consumes an item (freeing a slot), it should logically wake a *producer* — but `signal(cond)` has no way to know that; it might wake **another consumer** instead, who will simply recheck, find the buffer still empty, and go back to sleep — even though a *producer* was the thread that could actually make progress right now.

**Traced concretely**: two consumers sleep waiting for a full buffer; producer fills once; the woken consumer consumes the one item; but the *signal* that consumer sends afterward (intended to wake the producer, since a slot is now free) instead wakes the *other sleeping consumer* — who rechecks, finds the buffer still empty (correctly, since `while` caught it — Bug 1 is fixed), and goes right back to sleep. **The producer, who is the only thread that could actually make progress, is never woken at all, and stays asleep.** Even with `while` correctly in place, a single, undifferentiated condition variable can still leave the *right* thread starved.

### 7.7 Fix 2: two condition variables
```
empty CV (producers wait here)  ──┐
                                    ├── single mutex protects buffer state
fill CV (consumers wait here)   ──┘
```
**Producer waits on `empty` and signals `fill`. Consumer waits on `fill` and signals `empty`.** Separating the two reasons for waiting means a signal always goes to the queue of threads that could actually use it.

### 7.8 Correct single-slot solution: two CVs and `while`
```c
// producer
lock(mutex);
while (count == 1)
    wait(empty, mutex);
put(i);
signal(fill);
unlock(mutex);

// consumer
lock(mutex);
while (count == 0)
    wait(fill, mutex);
tmp = get();
signal(empty);
unlock(mutex);
```
| Part | Reason |
|---|---|
| `while` | re-checks predicate after wakeup (fixes Bug 1) |
| `empty`/`fill` | wakes the *right* class of waiter (fixes Bug 2) |
| `mutex` | protects `count` and `buffer` throughout |

## PART 8 — Generalizing to a Bounded Buffer of `MAX` Slots

### 8.1 A circular queue
```c
int buffer[MAX];
int fill_ptr = 0, use_ptr = 0, count = 0;

void put(int value) {
    buffer[fill_ptr] = value;
    fill_ptr = (fill_ptr + 1) % MAX;
    count++;
}
int get(void) {
    int tmp = buffer[use_ptr];
    use_ptr = (use_ptr + 1) % MAX;
    count--;
    return tmp;
}
```
`fill_ptr` and `use_ptr` each move modulo `MAX`, wrapping around; `count` tracks the number of currently-full slots (`0 ≤ count ≤ MAX`).

### 8.2 The general invariant and predicates
| Rule | Condition |
|---|---|
| Invariant | `0 ≤ count ≤ MAX` |
| `put` legal | `count < MAX` |
| `get` legal | `count > 0` |

```c
// producer                              // consumer
lock(mutex);                             lock(mutex);
while (count == MAX)                     while (count == 0)
    wait(empty, mutex);                      wait(fill, mutex);
put(i);                                  tmp = get();
signal(fill);                            signal(empty);
unlock(mutex);                           unlock(mutex);
```
**All changes to `count` and the pointers happen under the same mutex** — this is the natural single-slot pattern (Part 7.8) generalized purely by changing the two comparisons from `== 1`/`== 0` to `== MAX`/`== 0`. Nothing structurally new is needed — a genuinely satisfying confirmation that the single-slot reasoning generalizes cleanly.

### 8.3 The complete program (structure)
```c
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  empty = PTHREAD_COND_INITIALIZER;
pthread_cond_t  fill  = PTHREAD_COND_INITIALIZER;

void *producer(void *arg) {
    for (int i = 0; i < LOOPS; i++) {
        pthread_mutex_lock(&mutex);
        while (count == MAX)
            pthread_cond_wait(&empty, &mutex);
        put(i);
        pthread_cond_signal(&fill);
        pthread_mutex_unlock(&mutex);
    }
    return NULL;
}
void *consumer(void *arg) {
    for (int i = 0; i < LOOPS; i++) {
        pthread_mutex_lock(&mutex);
        while (count == 0)
            pthread_cond_wait(&fill, &mutex);
        int tmp = get();
        pthread_cond_signal(&empty);
        pthread_mutex_unlock(&mutex);
        printf("%d\n", tmp);
    }
    return NULL;
}
```
**Key rules, restated**: all `count`/pointer changes happen under one mutex; producers wait on `empty` and signal `fill`; consumers wait on `fill` and signal `empty`.

## PART 9 — Covering Conditions: When `signal` Isn't Enough

### 9.1 The scenario
```c
int bytesLeft = 0;
allocate(100)  → waits (needs 100 bytes free)
allocate(10)   → waits (needs 10 bytes free)
free(50)       → whom should it wake?
```
Two threads, `Ta` (needs 100 bytes) and `Tb` (needs 10 bytes), are both sleeping on the *same* CV waiting for enough memory to free up. A third thread calls `free(50)` — **50 bytes just became available, which is enough for `Tb` but not `Ta`.** If `signal()` happens to wake `Ta` (an arbitrary, unpredictable choice among waiters), `Ta` rechecks, finds 50 < 100 still insufficient, and goes right back to sleep — **even though `Tb` could have proceeded immediately** with those exact same 50 bytes.

### 9.2 The fix: `broadcast`
> **`broadcast` conservatively wakes all possible waiters.**

| Operation | Effect | Cost |
|---|---|---|
| `signal(cv)` | wake one waiter, if any | cheap, but may wake the wrong waiter |
| `broadcast(cv)` | wake **all** waiters | safe for covering conditions, but may wake many unnecessarily |

Waking everyone means each woken thread re-checks its **own** predicate (thanks to Part 6's `while` discipline) — the ones that still can't proceed simply go back to sleep harmlessly, while the one(s) that now *can* proceed do so. This costs some wasted wakeups, but guarantees no one is left incorrectly asleep.

**Rule of thumb, worth remembering for debugging**: *if `signal` seems to work only when changed to `broadcast`, inspect the predicate design first* — it may be a sign that the underlying condition genuinely needs a "covering" broadcast (multiple different threads can be satisfied by the same state change, in ways the signaler can't easily predict), or it may be masking a different design bug (like Part 7.6's mixed-queue problem) that a more targeted fix (separate CVs) would solve more precisely and cheaply.

## PART 10 — Condition-Variable Checklist

| Question | Correct answer |
|---|---|
| What is the condition? | A shared predicate such as `done`, `count`, or `bytesLeft`. |
| Who protects it? | A mutex / kernel lock. |
| How do we wait? | While predicate is false, call `wait(cv, mutex)`. |
| What does wakeup mean? | Only that the predicate *may* have changed. Re-check. |
| Who signals? | The code that changes the predicate state. |

> **Do not design around the condition variable alone. Design around the predicate.**

This single sentence is the whole chapter's thesis. Everything from Part 5's two broken designs through Part 9's covering conditions is a variation on forgetting this rule in one specific way or another.

## PART 11 — Mapping to Luit: `sleep(chan, lock)` and `wakeup(chan)`

### 11.1 The conceptual mapping
| POSIX user-level idea | Luit kernel analogue |
|---|---|
| predicate state | kernel state: child exited, pipe has data, buffer busy, etc. |
| mutex protects predicate | kernel lock protects the same state |
| `pthread_cond_wait(cv, m)` | `sleep(chan, lock)` |
| `pthread_cond_signal`/`broadcast` | `wakeup(chan)` |
| woken thread re-checks | woken process re-checks state after it runs again |

> **This is a conceptual mapping. Luit does not expose POSIX CVs as the kernel API.** (The same explicit caution your earlier Harts/Threads guide's Part 9.3 gave for the spinlock/mutex mapping applies identically here — don't treat this as API equivalence.)

### 11.2 What is a `chan` (sleep channel)?
> "In Luit, `chan` is a **wait key**: 'what condition/event am I sleeping for?'"

```
sleep(chan, lock)  →  process state: SLEEPING  ←  wakeup(chan)
```
**The channel is often an address** associated with some object or condition (e.g., the address of a particular buffer, or of a particular child process structure) — **it is not a message queue carrying data.** `wakeup(chan)` doesn't hand anything to the sleeper; it merely says "something relevant to whoever is sleeping on this key may have changed — go recheck your own predicate," exactly Part 6.1's Mesa-semantics rule, now in kernel vocabulary.

### 11.3 Lost wakeup in the kernel: why `sleep(chan, lock)` takes a lock
```c
// broken shape
if (!condition) {
    release(&lock);
    sleep(chan);      // GAP between release and sleep!
}
```
```
check condition (false)  →  [dangerous gap]  →  wakeup happens here, before sleep  →  thread sleeps forever
```
**This is exactly Part 5.2's user-level "no lock around the predicate" bug, restated at the kernel level.** If releasing the lock and actually transitioning to `SLEEPING` are two separate, non-atomic steps, another hart/process can slip into that gap, change the condition, and call `wakeup(chan)` — and that wakeup will have **nobody actually sleeping yet** to receive it. By the time this thread finally does call `sleep()`, the moment has passed, and it will sleep forever, having missed a wakeup that already fired.

**`sleep(chan, lock)` closes this gap by coordinating lock release with the SLEEPING transition as one atomic unit** — precisely mirroring how `pthread_cond_wait()`'s release-and-sleep must be atomic (Part 5.2). This is also the exact "lost wakeup" hazard your earlier Locks guide's Part 12.5 named in the context of `park()`/`unpark()` and Solaris's `setpark()` fix — the same failure mode recurs at every layer (user-level CVs, `park`/`unpark`, and now Luit's `sleep`/`wakeup`) because it's a structural property of "check, then sleep" being split into two non-atomic steps, not a quirk of any one particular API.

### 11.4 The Luit-style wait/wakeup pattern
```c
// wait path
acquire(&lock);
while (!condition)
    sleep(chan, &lock);
// condition is true enough to proceed; lock is held again here
release(&lock);

// wakeup path
acquire(&lock);
change condition state;
wakeup(chan);
release(&lock);
```
**Same rules as the POSIX pattern (Part 5.3)**: protect the predicate, sleep atomically, and re-check after wakeup. The structural identity between this and Part 5.3's `pthread_cond_wait`/`signal` pattern is deliberate — it's the same idea, expressed in the vocabulary of a kernel that manages entire processes rather than user-level threads.

### 11.5 Luit example: `wait()` and `exit()`
```
parent: wait() → checks child state → sleep if no zombie child

child: exit() → sets state ZOMBIE → wakeup(parent's chan)
```
The predicate here is **child state** (specifically, whether any child has become a **zombie** — exited but not yet reaped by the parent). The wakeup only says "check again"; the parent must still look at the actual child-state data to decide whether it can proceed, exactly Part 6's Mesa-semantics discipline.

### 11.6 Luit example: a pipe as a kernel producer/consumer
```
writer (producer) → pipe buffer (finite capacity) → reader (consumer)
```
**A pipe is literally a bounded buffer inside the kernel** — structurally identical to Part 8's user-level bounded buffer, just implemented with `sleep`/`wakeup` instead of `pthread_cond_wait`/`signal`. The writer sleeps if the pipe is full; the reader sleeps if it's empty; wakeups occur whenever the buffer's fullness state changes in a way that could unblock the other side.

## PART 12 — End-to-End Map: OSTEP → POSIX → Luit

| OSTEP idea | POSIX form | Luit analogue |
|---|---|---|
| wait for condition | `pthread_cond_wait(&cv, &m)` | `sleep(chan, lock)` |
| wake possible waiters | `pthread_cond_signal`/`broadcast` | `wakeup(chan)` |
| predicate | `done` / `count` / `bytesLeft` | child state / pipe count / buffer state |
| mutual exclusion | `pthread_mutex_t` | kernel lock |
| re-check after wake | `while` loop | `while` loop around `sleep` |

## PART 13 — Semaphores (OSTEP Ch. 31)

### 13.1 Motivation and definition
> A semaphore is useful **"when the number itself represents available resources or remembered events."**

```c
sem_t s;
sem_init(&s, 0, initial_value);
sem_wait(&s);   // P / down
sem_post(&s);   // V / up
```
| Operation | Meaning |
|---|---|
| `sem_wait` | if count > 0, decrement and continue; otherwise block |
| `sem_post` | increment count; wake a waiter if one can proceed |

**The genuinely new property versus a plain condition variable: a semaphore's count is remembered state, not just a wakeup signal.** This is the exact fix for Part 5.1's "no state variable" bug — a `sem_post()` called before anyone waits is never lost, because it's recorded as an actual increment to a persistent counter, not merely as a transient signal to whoever happens to be listening at that instant.

### 13.2 Binary semaphore for ordering (the join problem, revisited)
```c
sem_t done;
void *child(void *arg) {
    printf("child\n");
    sem_post(&done);       // remember completion
    return NULL;
}
int main(void) {
    printf("parent: begin\n");
    sem_init(&done, 0, 0);   // initial value 0
    pthread_t t;
    pthread_create(&t, NULL, child, NULL);
    sem_wait(&done);         // wait until child posts
    printf("parent: end\n");
    pthread_join(t, NULL);
    sem_destroy(&done);
    return 0;
}
```
**Why it handles both schedules correctly, with no predicate variable needed at all:**
- **Case A (parent waits first)**: `sem_wait` blocks (count is 0); child runs, `sem_post` increments to 1 and wakes the parent; parent proceeds.
- **Case B (child posts first)**: child's `sem_post` increments count to 1 immediately (nobody waiting yet); parent's later `sem_wait` simply decrements 1→0 and proceeds without ever blocking.

**Unlike a CV, the post is remembered by the count** — this is the semaphore's built-in answer to exactly the problem Part 4's `done` variable had to be manually engineered to solve for condition variables.

### 13.3 Semaphore as a mutex-like gate (initial value 1)
```c
sem_t mutex;
sem_init(&mutex, 0, 1);   // one permit
void *worker(void *arg) {
    for (...) {
        sem_wait(&mutex);   // enter
        counter++;
        sem_post(&mutex);   // leave
    }
}
```
| Value | Meaning |
|---|---|
| 1 | one thread may enter |
| 0 | permit unavailable; waiters block |

**Pedagogically fine, but the practical POSIX rule is to prefer `pthread_mutex_t` for genuine mutex ownership semantics** — a real mutex has a notion of *which thread owns it* (recall the earlier Locks guide's Part 8.5 distinction between `lk->locked`, the actual lock, and `lk->cpu`, ownership metadata used for debugging), whereas a semaphore used as a binary gate has no inherent concept of "owner" at all — any thread could technically call `sem_post` on a lock it never `sem_wait`'d, which a real mutex API would catch as a misuse but a semaphore cannot.

### 13.4 Counting semaphore: tracking multiple identical resources
```
count = 3  →  sem_wait (claim one permit)  →  count = 2
```
For `N` identical interchangeable resources, initialize the semaphore to `N`; each `sem_wait` claims one, each `sem_post` returns one. **In producer/consumer, two counting semaphores naturally track empty slots and full slots** — directly replacing the `count`-variable-plus-two-CVs machinery from Part 8.

### 13.5 Full producer/consumer with semaphores
```c
sem_t empty, full, mutex;

void put(int value) { buffer[fill_ptr] = value; fill_ptr = (fill_ptr+1)%MAX; }
int  get(void)       { int tmp = buffer[use_ptr]; use_ptr = (use_ptr+1)%MAX; return tmp; }

void *producer(void *arg) {
    for (...) {
        sem_wait(&empty);    // wait for space
        sem_wait(&mutex);    // enter critical section
        put(i);
        sem_post(&mutex);    // leave critical section
        sem_post(&full);     // one more item available
    }
}
void *consumer(void *arg) {
    for (...) {
        sem_wait(&full);     // wait for item
        sem_wait(&mutex);    // enter critical section
        int tmp = get();
        sem_post(&mutex);    // leave critical section
        sem_post(&empty);    // one more slot available
    }
}
int main(void) {
    sem_init(&empty, 0, MAX);   // MAX free slots initially
    sem_init(&full, 0, 0);      // 0 items available initially
    sem_init(&mutex, 0, 1);     // exclusive access to buffer pointers
    ...
}
```
| Semaphore | Initial value | Meaning |
|---|---|---|
| `empty` | `MAX` | free slots available |
| `full` | `0` | items available |
| `mutex` | `1` | exclusive access to buffer pointers |

**The semaphores encode the predicates directly as counts** — there's no separate `count` integer variable at all here; `empty` and `full` *are* the state, with no additional bookkeeping needed.

### 13.6 A subtle but critical ordering rule: wait on the resource *before* the mutex
```c
// WRONG producer ordering
sem_wait(&mutex);          // take the exclusive lock FIRST
sem_wait(&empty);          // then try to wait for space — may BLOCK while holding mutex!
put(i);
sem_post(&mutex);
sem_post(&full);
```
**Trace of the deadlock this causes**:
```
buffer full → producer takes mutex → producer blocks waiting on empty (buffer still full)
   → consumer cannot take mutex (producer is holding it) → consumer can never consume,
     can never free a slot, can never post to empty → DEADLOCK
```
The producer is holding `mutex` while blocked on `empty` — but the *only* thing that could ever increment `empty` is a consumer calling `get()`, and the consumer can't even start (needs `mutex`, which the blocked producer is still holding). **Correct rule: first wait for the resource condition (`empty`/`full`), then take the short critical-section mutex** — exactly the ordering shown correctly in Part 13.5. This is a concrete, semaphore-flavored instance of the general **lock-ordering deadlock** danger covered more fully in Part 15.3 below.

### 13.7 Condition variables versus semaphores: a direct comparison
| Aspect | Condition variable | Semaphore |
|---|---|---|
| State memory | Predicate variable stores truth; CV stores waiters | Counter stores available permits/events |
| Waiting | `wait(cv, mutex)` after checking predicate | `sem_wait(s)` decrements or blocks |
| Notification | `signal`/`broadcast` says predicate *may* have changed | `sem_post` increments and may wake |
| Typical use | Complex predicates under a mutex | Countable resources or event ordering |
| Producer/consumer | `empty`/`fill` CVs + `count` predicate | `empty`/`full` semaphores + `mutex` |

**Neither is strictly "better"** — a semaphore is a more compact, self-contained primitive precisely when the thing you're waiting for genuinely *is* a count (available slots, remembered completions); a condition variable is the more natural fit when the actual wait condition is an arbitrary, possibly complex boolean expression over shared state that doesn't reduce cleanly to a single counter.

## PART 14 — Common Concurrency Bugs (OSTEP Ch. 32)

### 14.1 What types of bugs actually occur? (empirical grounding)
A study (Lu et al.) examined real concurrency bugs fixed in four major open-source codebases:

| Application | What it does | Non-Deadlock | Deadlock |
|---|---|---|---|
| MySQL | Database Server | 14 | 9 |
| Apache | Web Server | 13 | 4 |
| Mozilla | Web Browser | 41 | 16 |
| OpenOffice | Office Suite | 6 | 2 |
| **Total** | | **74** | **31** |

**The majority (74 of 105, ~70%) were non-deadlock bugs** — worth noting since deadlock tends to dominate classroom discussion of concurrency bugs, but empirically isn't even the most common category in real code.

### 14.2 Non-deadlock bugs: atomicity violations
```c
// Thread 1
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}
// Thread 2
thd->proc_info = NULL;
```
**The bug**: Thread 1 checks `proc_info` is non-NULL, but if it's interrupted **between the check and the actual use**, Thread 2 can set it to NULL in that gap — Thread 1 resumes and dereferences a NULL pointer, crashing. Formally: *"the desired serializability among multiple memory accesses is violated — a code region is intended to be atomic, but the atomicity is not enforced during execution."* **This is structurally identical to the `counter = counter + 1` load-modify-store race** from your earlier Harts/Threads guide's Part 6 — the only difference is that here the "modify" step is a function call (`fputs`) rather than an arithmetic operation, but the vulnerability (an assumption of atomicity that the code never actually enforces) is the same.

**Fix**: wrap the check-and-use in the exact same lock on both threads:
```c
pthread_mutex_lock(&proc_info_lock);
if (thd->proc_info) { fputs(thd->proc_info, ...); }
pthread_mutex_unlock(&proc_info_lock);
// Thread 2:
pthread_mutex_lock(&proc_info_lock);
thd->proc_info = NULL;
pthread_mutex_unlock(&proc_info_lock);
```

### 14.3 Non-deadlock bugs: order violations
```c
// Thread 1
void init() { mThread = PR_CreateThread(mMain, ...); }
// Thread 2
void mMain(...) { mState = mThread->State; }
```
**The bug**: Thread 2 assumes `mThread` is already initialized by the time it runs — but if Thread 2 happens to run **before** Thread 1 finishes creating it, `mThread` is still NULL (or garbage), and the dereference crashes (or worse, accesses arbitrary memory if not reliably NULL). Formally: *"the desired order between two (groups of) memory accesses is flipped — A should always execute before B, but the order is not enforced during execution."*

**Fix: exactly the ordering-enforcement job condition variables exist for** (this is the direct link back to Part 1's list of "common OS situations" needing a CV):
```c
pthread_mutex_t mtLock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  mtCond = PTHREAD_COND_INITIALIZER;
int mtInit = 0;

// Thread 1
void init() {
    mThread = PR_CreateThread(mMain, ...);
    pthread_mutex_lock(&mtLock);
    mtInit = 1;
    pthread_cond_signal(&mtCond);
    pthread_mutex_unlock(&mtLock);
}
// Thread 2
void mMain(...) {
    pthread_mutex_lock(&mtLock);
    while (mtInit == 0)
        pthread_cond_wait(&mtCond, &mtLock);
    pthread_mutex_unlock(&mtLock);
    mState = mThread->State;
}
```
This is **exactly** the disciplined predicate-mutex-CV pattern from Part 5.3, applied to a real-world bug class rather than a toy example — `mtInit` is the predicate, `mtLock` protects it, `mtCond` is the waiting queue, and the `while` loop follows Mesa semantics. **97% of the non-deadlock bugs in the Lu et al. study were one of these two types** (atomicity or order violations) — a striking concentration worth remembering: most real concurrency bugs are not exotic, they're one of exactly two well-understood patterns.

### 14.4 Deadlock: the basic scenario
```c
// Thread 1                       // Thread 2
pthread_mutex_lock(L1);           pthread_mutex_lock(L2);
pthread_mutex_lock(L2);           pthread_mutex_lock(L1);
```
**This does not *necessarily* deadlock** — it depends on timing. If Thread 1 grabs `L1`, then a context switch occurs before it grabs `L2`, and Thread 2 then grabs `L2` and tries for `L1`: now each thread holds exactly the lock the other one wants, and neither can ever proceed.
```
Thread 1 --Holds--> L1 --Wanted by--> Thread 2 --Holds--> L2 --Wanted by--> Thread 1
```
**The presence of a cycle in this dependency graph is the signature of deadlock.**

### 14.5 Why deadlocks happen in practice (not just toy examples)
- **Complex, layered dependencies in large systems.** E.g., in an OS, the virtual memory system might need the file system (to page in a block from disk), while the file system might need the virtual memory system (to get a page to read the block into) — circular dependencies can arise *naturally* between subsystems that were each individually designed sensibly.
- **Encapsulation actively works against safe locking.** A seemingly innocent API like Java's `Vector.AddAll()` — `v1.AddAll(v2)` — must internally lock *both* vectors to be thread-safe. If it always locks in the order (`v1` then `v2`), and some other thread simultaneously calls `v2.AddAll(v1)` (locking `v2` then `v1`), you have a deadlock **hidden entirely behind an innocuous-looking single method call**, with no way for the calling code to see the danger from the outside.

### 14.6 The four necessary conditions for deadlock
> **If any one of these four is not met, deadlock cannot occur.**
1. **Mutual exclusion** — threads claim exclusive control of a resource (e.g., a lock).
2. **Hold-and-wait** — a thread holds one resource while waiting for another.
3. **No preemption** — a resource cannot be forcibly taken from a thread holding it.
4. **Circular wait** — a cycle of threads, each waiting on a resource held by the next.

Every prevention strategy below targets **exactly one** of these four conditions.

### 14.7 Prevention: breaking circular wait via lock ordering
**Total ordering**: always acquire locks in one globally fixed order (e.g., always `L1` before `L2`). Simple with two locks; harder with many — real systems (e.g., Linux's memory-mapping code) document **partial orderings** across many lock groups instead of one universal total order.

**A clever practical technique — order by lock address**:
```c
if (m1 > m2) {
    pthread_mutex_lock(m1);
    pthread_mutex_lock(m2);
} else {
    pthread_mutex_lock(m2);
    pthread_mutex_lock(m1);
}
```
When a function receives two lock pointers as parameters (and thus can't know in advance which "logical" order they should be locked in), **comparing the raw pointer addresses gives a consistent, deterministic ordering regardless of which order the caller happened to pass them in** — guaranteeing that `do_something(L1, L2)` and `do_something(L2, L1)`, called concurrently by two different threads, will always agree on which lock to take first.

**Caveat**: ordering is just a *convention* — a single careless piece of code that ignores it can still cause deadlock; and correctly designing the ordering requires deep understanding of the whole codebase's locking behavior.

### 14.8 Prevention: breaking hold-and-wait
**Acquire all needed locks atomically, up front**, guarded by one global "prevention" lock:
```c
pthread_mutex_lock(prevention);
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);
...
pthread_mutex_unlock(prevention);
```
Because *every* thread must hold `prevention` before acquiring any of its other locks, no thread can be interrupted mid-acquisition in a way that lets another thread's differently-ordered acquisition interleave with it. **Downsides**: requires knowing in advance exactly which locks a routine will need (breaks encapsulation — the caller must know internal locking details it normally shouldn't); and forces *all* locks to be grabbed early, even ones not needed until much later, which can hurt concurrency significantly.

### 14.9 Prevention: breaking no-preemption via `trylock`
```c
top:
    pthread_mutex_lock(L1);
    if (pthread_mutex_trylock(L2) != 0) {
        pthread_mutex_unlock(L1);
        goto top;
    }
```
`pthread_mutex_trylock()` either grabs the lock and returns success, or returns immediately with an error if it's held (recall this was already mentioned in your earlier Locks guide's Part 12.9's `trylock`/`timedlock` discussion). By releasing `L1` and retrying entirely from scratch whenever `L2` isn't immediately available, **no thread ever holds one lock while blocking indefinitely for another** — a thread can be seen as gracefully "preempting its own ownership" rather than a genuinely external force preempting it.

**A new problem this introduces: livelock.** Two threads could both repeatedly attempt-and-back-off in lockstep, forever failing to both succeed at the same time — technically not a deadlock (both are still actively running instructions, not stuck), but **no actual progress is ever made**. **Fix**: add a small random delay before retrying, to break the lockstep pattern and reduce the odds of repeated collision.

**A remaining practical complication**: if other resources (e.g., allocated memory) were acquired between `L1` and the failed `L2` attempt, the retry logic must carefully release *those* too before jumping back to the top — otherwise you leak resources on every failed attempt.

### 14.10 Prevention: eliminating mutual exclusion via lock-free structures
The most radical prevention approach: **avoid the need for exclusive locking altogether**, using hardware atomic instructions directly.
```c
void AtomicIncrement(int *value, int amount) {
    do {
        int old = *value;
    } while (CompareAndSwap(value, old, old + amount) == 0);
}
```
No lock is ever acquired — the loop simply keeps retrying the atomic swap until it succeeds (recall CompareAndSwap from your earlier Locks guide's Part 10.2). **No deadlock can arise** (there's nothing to hold-and-wait for), though **livelock remains a theoretical possibility** under sufficiently adversarial/unlucky scheduling.

**A more involved lock-free example — list insertion**:
```c
void insert(int value) {
    node_t *n = malloc(sizeof(node_t));
    n->value = value;
    do {
        n->next = head;
    } while (CompareAndSwap(&head, n->next, n) == 0);
}
```
This directly parallels the lock-based version from your earlier Locks guide's Part 14.3 (`List_Insert`), but replaces the lock/unlock pair around the shared-state update with a CAS retry loop instead: keep trying to swap `head` to point at the new node, as long as nobody else has changed `head` in the meantime; if someone did (the CAS fails), retry with the *new* current head. **Building a genuinely useful, fully-featured lock-free structure (supporting insert, delete, and lookup together) is considerably harder** than this single-operation example suggests — a substantial field of research (**lock-free** and **wait-free** synchronization) exists specifically because of this difficulty.

### 14.11 Deadlock avoidance via global scheduling knowledge
Rather than *preventing* deadlock structurally, **avoidance** uses advance knowledge of which locks each thread will need, and schedules threads to guarantee no dangerous combination ever runs concurrently.

**Example**: T1 and T2 both need locks L1 and L2; T3 needs only L2; T4 needs no locks. A smart scheduler can compute that **as long as T1 and T2 never run simultaneously**, no deadlock is possible (since neither of the other two threads could ever complete the specific cyclic-wait pattern) — so it could schedule T3 and T4 freely alongside either T1 or T2, but never let T1 and T2 overlap.

**The cost, shown starkly in a harder example**: if T1, T2, *and* T3 all need *both* locks, the only deadlock-safe static schedule may force **all three onto the same processor, one at a time** — sacrificing genuine parallelism entirely for safety. This is the classic tradeoff of approaches like **Dijkstra's Banker's Algorithm**: provably deadlock-free, but only practical in narrow, fully-specified environments (e.g., embedded systems where the complete set of tasks and their lock needs is known in advance) — not a general-purpose solution for arbitrary concurrent software.

### 14.12 Detect and recover
The final, pragmatic strategy: **let deadlocks occasionally happen, then detect and recover.** A **deadlock detector** runs periodically, builds a resource-dependency graph (Part 14.4's diagram, computed from live system state), and checks for cycles. On detecting one, the system (or the specific deadlocked component) is restarted — potentially with human involvement if data structures need careful repair afterward. **Real-world use**: many database systems use exactly this approach, on the pragmatic reasoning that if deadlocks are genuinely rare, a full prevention/avoidance scheme's cost and complexity may not be worth paying compared to occasionally just restarting.

## PART 15 — Event-Based Concurrency (OSTEP Ch. 33): An Alternative to Threads Entirely

### 15.1 The crux
> **How can we build a concurrent server without using threads, and thus retain control over concurrency as well as avoid some of the problems that seem to plague multi-threaded applications?**

Two distinct motivations: (1) getting multi-threaded synchronization *correct* is genuinely hard (everything in Part 14 is testament to that), and (2) with threads, **the programmer has little control over what the OS scheduler actually does at any given moment** — you create threads and hope for a reasonable schedule.

### 15.2 The basic idea: an event loop
```c
while (1) {
    events = getEvents();
    for (e in events)
        processEvent(e);
}
```
The code that processes one event is an **event handler**. **Critically, while one handler runs, it is the only activity in the system** — deciding which event to process next *is* the scheduling decision, made explicitly by the programmer's own loop rather than implicitly by an OS scheduler juggling threads. **This explicit control over scheduling is one of the fundamental advantages of the event-based approach.**

### 15.3 Receiving events: `select()`/`poll()`
```c
int select(int nfds, fd_set *readfds, fd_set *writefds,
           fd_set *errorfds, struct timeval *timeout);
```
Checks which file descriptors (in the provided sets) are ready for reading, writing, or have an exceptional condition — without blocking on any single one of them. `select()` returns the count of ready descriptors, and modifies the sets in place to show *which* ones. Setting `timeout` to `NULL` blocks indefinitely until something is ready; setting it to zero makes the call return immediately (useful for a fast poll-then-continue loop). `poll()` is a closely related, similarly-purposed alternative.

```c
while (1) {
    fd_set readFDs;
    FD_ZERO(&readFDs);
    for (fd = minFD; fd < maxFD; fd++)
        FD_SET(fd, &readFDs);

    int rc = select(maxFD+1, &readFDs, NULL, NULL, NULL);

    for (fd = minFD; fd < maxFD; fd++)
        if (FD_ISSET(fd, &readFDs))
            processFD(fd);
}
```
This is the concrete implementation of Part 15.2's abstract event loop — `getEvents()` is `select()`; iterating over ready descriptors and calling `processFD` is the "process each event" step.

**Blocking vs. non-blocking interfaces, defined precisely**: a **blocking (synchronous)** interface does all its work before returning; a **non-blocking (asynchronous)** interface begins work and returns immediately, letting the work continue in the background. Non-blocking interfaces can be used with threads too, but they are **essential** for event-based programming, since any call that blocks halts the *entire* single-threaded server.

> **Tip: don't block in event-based servers.** Failing to obey this design rule "will result in a blocked event-based server, frustrated clients, and serious questions as to whether you ever read this part of the book."

### 15.4 Why simpler: no locks needed
> "With a single CPU and an event-based application, the problems found in concurrent programs are no longer present... because only one event is being handled at a time, there is no need to acquire or release locks; the event-based server cannot be interrupted by another thread because it is decidedly single threaded."

**This is a genuinely important structural point**: essentially the *entire* content of Parts 1–14 of this guide (locks, condition variables, semaphores, atomicity/order-violation bugs, deadlock) exists specifically to manage the consequences of multiple execution streams genuinely interleaving over shared state. **An event-based server on a single CPU sidesteps the whole category of problem** — not by solving it more cleverly, but by never creating the underlying condition (concurrent access to shared state) that makes it a problem in the first place.

### 15.5 The problem: blocking system calls
The one thing that breaks this elegant simplicity: **what if an event handler must issue a system call that might block** — e.g., `open()`/`read()` to serve a file from disk? With threads, this is a non-issue: the blocked thread suspends, and other threads keep the CPU busy (this is precisely the earlier Harts/Threads guide's Part 4's "overlap with I/O" motivation for using threads at all). **With events, there are no other threads to run — just the one event loop.** If a handler issues a blocking call, **the entire server halts** until it returns, wasting the CPU and stalling every other pending event. **Rule: no blocking calls are allowed in event-based systems.**

### 15.6 The solution: asynchronous I/O
Modern OSes provide **asynchronous I/O** interfaces that let an application issue a request and return immediately, checking for completion separately.
```c
struct aiocb {
    int    aio_fildes;   // File descriptor
    off_t  aio_offset;   // File offset
    void  *aio_buf;      // Buffer location
    size_t aio_nbytes;   // Length of transfer
};
int aio_read(struct aiocb *aiocbp);     // issue the read, returns immediately
int aio_error(const struct aiocb *aiocbp);  // 0 = complete; EINPROGRESS = not yet
```
Fill in the `aiocb` structure, call `aio_read()` (which returns right away), and later poll `aio_error()` to check completion. **A genuine practical annoyance flagged directly**: with many outstanding I/Os, repeatedly polling each one is awkward — some systems instead use **UNIX signals** to interrupt the application and announce completion, removing the need for active polling (directly parallel to the earlier VM guide's polling-vs-interrupt distinction for device I/O, mentioned explicitly by name in the source text).

**Where async disk I/O isn't available**, a documented hybrid workaround exists (Pai et al.): use events for network I/O, but fall back to a small **thread pool** specifically to manage outstanding disk I/Os — a pragmatic compromise rather than a pure event-based design.

### 15.7 The other cost: manual stack management (continuations)
> "Event-based code is generally more complicated to write than traditional thread-based code."

**A thread-based version of "read from a file descriptor, then write the result to a socket" is trivial:**
```c
int rc = read(fd, buffer, size);
rc = write(sd, buffer, size);
```
The socket descriptor `sd` is simply sitting on the thread's own stack, still there and still valid the instant `read()` finally returns — **because threading gives you, for free, a natural place (the stack) to keep state across a blocking call.**

**In an event-based system, there is no such natural home for that state.** The `read()` becomes an asynchronous `aio_read()`, and by the time its completion is detected (via polling `aio_error()` or a signal), the original event handler function has long since returned — **its stack frame, and everything on it (including `sd`), is gone.** The event-based server must instead **manually package up whatever state the *next* step needs**, store it somewhere durable (e.g., a hash table keyed by the file descriptor), and look it up again when the corresponding completion event arrives.

**This technique has a name: a continuation.** *"Basically, record the needed information to finish processing this event in some data structure; when the event happens, look up the needed information and process the event."* Adya et al. term this discipline **manual stack management** — the event-based programmer is doing by hand, explicitly, exactly what a thread's call stack does automatically and for free.

### 15.8 What is still difficult with events, even beyond the above
- **Multicore breaks the "no locks needed" simplicity (Part 15.4) entirely.** To use more than one CPU, an event server must run multiple event handlers genuinely in parallel — and the instant it does, ordinary critical sections and locks are needed again, exactly as in thread-based code. **The core appeal of event-based programming was fundamentally a single-CPU-era argument.**
- **Implicit blocking via page faults** is very hard to avoid. If an event handler touches memory that triggers a page fault (recall your earlier Page Faults guide — the CPU genuinely must wait while the kernel repairs the mapping), the entire server blocks, even though the programmer never wrote an explicit blocking call anywhere — the "no blocking calls" rule (Part 15.3) can be violated by the hardware itself, invisibly.
- **API semantics can silently change out from under you.** If a library routine that used to be non-blocking becomes blocking in a later version, every event handler that calls it must be restructured (often split into two pieces around the new blocking point) — a maintenance burden unique to this style of programming, since the entire architecture's correctness depends on a property (non-blocking-ness) that isn't visible in a function's type signature.
- **Network and disk async I/O don't integrate as cleanly as you'd hope.** `select()` naturally handles many network sockets at once, but disk I/O typically needs the separate AIO-style interface from Part 15.6 — a real server often ends up combining both mechanisms rather than using one uniform API for everything.

## Quick-Reference: New Vocabulary From This Guide
| Term | One-line meaning |
|---|---|
| **Predicate** | The actual shared condition being waited for (`done`, `count`) — distinct from the CV itself |
| **Mesa semantics** | A signal only means "recheck"; the woken thread doesn't get exclusive, guaranteed possession of the condition |
| **Covering condition** | A predicate so general that a signal can't predict which specific waiter it will satisfy — requires `broadcast` |
| **`sleep(chan, lock)` / `wakeup(chan)`** | Luit's kernel-level analogue of `pthread_cond_wait`/`signal` |
| **Atomicity violation** | Code assumes a multi-step sequence is atomic, but no synchronization enforces it |
| **Order violation** | Code assumes A happens before B, but nothing enforces that ordering |
| **Circular wait / hold-and-wait / no preemption / mutual exclusion** | The four necessary conditions for deadlock; breaking any one prevents it |
| **Livelock** | Threads keep actively running but make no real progress (as opposed to deadlock's total halt) |
| **Lock-free / wait-free** | Building correct concurrent structures using only atomic hardware instructions, no locks |
| **Event loop** | `while(1) { events = getEvents(); processEvent(e); }` — the core of event-based concurrency |
