# CPU Scheduling: Policies, MLFQ, and the Luit Mechanism — Complete Concept Guide

This guide merges three sources: the CS3105 scheduling lecture slides (metrics → FIFO/SJF/STCF/RR → I/O → MLFQ → Luit mapping → exercises), **OSTEP Chapter 7** ("Scheduling: Introduction"), and **OSTEP Chapter 8** ("Scheduling: The Multi-Level Feedback Queue"). It builds directly on your earlier guides: the **Syscall Entry/Exit** guide (timer interrupts and `usertrap()`), the **Locks** and **Condition Variables** guides (`p->lock`, `sleep`/`wakeup`), and the **Harts/Threads** guide (one scheduler loop per hart).

The organizing idea of the whole lecture, stated once up front:

> **Policy** decides *which* runnable process runs next. **Mechanism** decides *how* to stop one process and start another. OSTEP teaches policy; Luit shows mechanism.

## PART 0 — Policy vs. Mechanism, and the Process States the Scheduler Sees

### 0.1 The state machine
```
              scheduler selects
   RUNNABLE ───────────────────────► RUNNING ───── exit() ───► ZOMBIE
      ▲  ▲  ◄── yield / preemption ──────┘  │
      │  └──────────── wakeup ──────── SLEEPING ◄── sleep / block
```
- **RUNNABLE** — ready to run, waiting for a CPU (hart).
- **RUNNING** — currently executing on a hart.
- **SLEEPING** — blocked waiting for an event (I/O, a child exiting, a pipe, …).
- **ZOMBIE** — exited, waiting to be reaped by its parent.

> **Important: `wakeup` makes a process RUNNABLE, not immediately RUNNING.** The scheduler still decides when it actually runs. (This is the "ready ≠ running" point from the Condition Variables guide's Part 6.2, seen from the scheduler's side.)

### 0.2 The split
| | Question it answers | Examples |
|---|---|---|
| **Policy** | Which runnable process should run? | FIFO, SJF, STCF, RR, MLFQ |
| **Mechanism** | How do we stop P and resume Q? | process states, timer interrupts, `yield()`, `sleep()`, `wakeup()`, `scheduler()`, `swtch()` |

This is the same mechanism/policy separation that has recurred all course (e.g., `walk()`'s `alloc` flag, `ecall`'s minimalism, "hardware gives atomics, software builds locks"). Here: Luit's simple scheduler is deliberately a *placeholder policy* over a real, complete mechanism.

## PART 1 — Workload Assumptions (Why the Early Policies Look Unrealistic)

OSTEP Ch. 7 starts by listing assumptions about the workload, then relaxes them one at a time, building a better scheduler at each step.

| # | OSTEP assumption | Relaxed by |
|---|---|---|
| 1 | Each job runs for the same amount of time | FIFO's convoy problem → SJF |
| 2 | All jobs arrive at the same time | late arrivals → STCF |
| 3 | Once started, each job runs to completion | preemption → STCF, RR |
| 4 | Jobs only use the CPU (no I/O) | treat CPU bursts as jobs; overlap I/O |
| 5 | The run-time of each job is known | "no more oracle" → MLFQ |

**Note:** the lecture slide condenses this to four assumptions (arrive together, lengths known, only CPU, run to completion) — the same ideas minus "all jobs equal length." Both versions make the same point: **the "known length" assumption (number 5) is the least realistic**, because a general-purpose OS has no oracle. Everything in Part 4 (MLFQ) exists to remove it.

## PART 2 — Two Metrics That Pull in Opposite Directions

### 2.1 Turnaround time
```
T_turnaround = T_completion − T_arrival
```
*"When did my job finish?"* If all jobs arrive at time 0, turnaround equals completion time. This is a **performance** metric.

### 2.2 Response time
```
T_response = T_first-run − T_arrival
```
*"When did the system first start serving me?"* For interactive work, this usually matters more than completion time (nobody wants to type and wait 10 seconds for the first sign of life).

### 2.3 Fairness (mentioned, not optimized)
OSTEP also names **fairness** (e.g., Jain's Fairness Index) and notes that **performance and fairness are often at odds**: a scheduler can optimize turnaround by starving a few jobs.

> **Central tradeoff: turnaround, response time, fairness, and overhead cannot all be optimized perfectly at once.**

## PART 3 — The Basic Policies, on One Workload

### 3.1 The board workload
| Job | Arrival | CPU time |
|---|---|---|
| A | 0 | 10 |
| B | 0 | 3 |
| C | 0 | 2 |

### 3.2 FIFO / FCFS — first in, first out
Run jobs in arrival order; a running job is never preempted. Order A, B, C:
```
|        A (10)        | B (3) | C (2) |
0                     10      13      15
```
| Job | Completion | Turnaround |
|---|---|---|
| A | 10 | 10 |
| B | 13 | 13 |
| C | 15 | 15 |
| **Average** | | **12.67** |

Simple, but **sensitive to arrival order**.

**The convoy effect.** If one long job sits ahead of short ones (A = 100, B = C = 10, all arriving at 0): turnarounds are 100, 110, 120, **average 110**. *Many short consumers are delayed by one heavyweight consumer* — OSTEP's grocery-store picture: you, with one item, stuck behind a family with three full carts.

### 3.3 SJF — shortest job first
Among available jobs, run the one with the shortest *total* length. Order C, B, A:
```
| C (2) | B (3) |        A (10)        |
0       2       5                     15
```
| Job | Completion | Turnaround |
|---|---|---|
| C | 2 | 2 |
| B | 5 | 5 |
| A | 15 | 15 |
| **Average** | | **7.33** |

**When all jobs arrive together and lengths are known, SJF is provably optimal for average turnaround** (OSTEP: "no proofs are allowed" in a systems class — but it's true). Compare 12.67 (FIFO) vs. 7.33 (SJF) on the *same jobs*.

SJF has two assumptions, both usually false in a real OS: **(1)** the scheduler knows job lengths; **(2)** a started job runs to completion.

### 3.4 Late arrivals break non-preemptive SJF
A arrives at t=0 needing 100; B and C arrive at t=10, needing 10 each.
```
|             A (100)             | B (10) | C (10) |
0                                100      110      120
```
Turnarounds: A = 100, B = 110 − 10 = 100, C = 120 − 10 = 110 → **average 103.33**. B and C are short but can't run until A finishes — the convoy problem again, *even under SJF*. We need **preemption**.

### 3.5 Preemption — what it needs
> A preemptive scheduler may stop a process even if it did not voluntarily block or exit.

```
P in user mode → timer interrupt → kernel trap handler → scheduler decision
```
Modern time-sharing depends on **periodic timer interrupts**. (This is exactly the interrupt path from your Syscall guide, now used for a different purpose: not a syscall, but the kernel regaining control from a process that never asked to give it up.) OSTEP's aside: virtually all modern schedulers are preemptive.

### 3.6 STCF / SRTF — preemptive SJF
**Shortest Time-to-Completion First** always runs whichever job has the least *remaining* time, re-deciding whenever a job arrives. Same workload as 3.4:
```
| A (10) | B (10) | C (10) |          A (90)           |
0       10       20       30                          120
```
Turnarounds: A = 120, B = 20 − 10 = 10, C = 30 − 10 = 20 → **average 50** (vs. 103.33 without preemption). STCF is provably optimal for average turnaround **given known lengths and preemption**.

### 3.7 But turnaround-optimal is not interactive
Three jobs of 5 s each arrive together. SJF/STCF runs them back-to-back:
| Job | First run | Response |
|---|---|---|
| A | 0 | 0 |
| B | 5 | 5 |
| C | 10 | 10 |
| **Average** | | **5** |

The third job waits 10 s for its *first* sign of progress. Great turnaround, poor response.

### 3.8 Round Robin — time slicing
Run each runnable job for one **time slice (quantum)**, then rotate to the next. With 1 s slices on the same three 5 s jobs: `A B C A B C …`
| Job | First run | Response |
|---|---|---|
| A | 0 | 0 |
| B | 1 | 1 |
| C | 2 | 2 |
| **Average** | | **1** |

**RR's price is turnaround.** The three jobs finish at 13, 14, 15 → average **14**, versus 10 for FIFO/SJF on the same jobs. OSTEP: RR is "nearly pessimal" for turnaround, even worse than FIFO in many cases, because it deliberately *stretches out* every job. In general:

> **Any policy that is fair on a small time scale (divides the CPU evenly) will do poorly on turnaround. You can have short jobs finish early (unfair, bad response) or good response (fair, bad turnaround) — not both.**

### 3.9 The quantum is a design tradeoff
| Very large quantum | Reasonable quantum | Very small quantum |
|---|---|---|
| RR degenerates toward FIFO; poor response | Good response; acceptable overhead | Too many switches; high overhead |

**Amortization (OSTEP tip):** if a context switch costs 1 ms and the slice is 10 ms, ~10% of time is wasted; at a 100 ms slice, < 1%. Pay a fixed cost less often. The slice must be **much larger than the switch cost** — and note OSTEP also requires the slice to be a **multiple of the timer-interrupt period** (10 ms ticks → 10, 20, … ms slices).

### 3.10 Context-switch cost is more than saving registers
A switch can disturb useful hardware state:
| State | Effect |
|---|---|
| Registers | saved/restored by the kernel (the obvious cost) |
| **Caches** | the new job's working set is cold |
| **TLB** | translations may need refreshing or replacement (recall `satp`/`sfence.vma` from the VM guide when the address space changes) |
| Branch predictor | learned history becomes less useful |

This is why a too-small quantum hurts *throughput*, not just "bookkeeping."

### 3.11 Policy summary
| Policy | Preemptive? | Strength | Weakness |
|---|---|---|---|
| FIFO / FCFS | No | Simple | Convoy effect |
| SJF | No | Low average turnaround | Needs job length |
| STCF / SRTF | Yes | Excellent turnaround | Needs *remaining* time |
| Round Robin | Yes | Good response, fairness | Hurts turnaround |

## PART 4 — Incorporating I/O

Relaxing assumption 4: real programs block for I/O. When a job issues an I/O request it will not use the CPU, so **the scheduler should run something else**; when the I/O completes, an interrupt moves the job from blocked back to **ready** (RUNNABLE).

```
RUNNING ──(I/O request)──► SLEEPING/BLOCKED ──(I/O completion interrupt)──► RUNNABLE
```

**The standard trick:** treat each **CPU burst** as a separate small job. Example (OSTEP): A uses 10 ms of CPU, then does a 10 ms I/O, repeated 5 times; B is a pure 50 ms CPU job.
- **Poor:** run A to completion (CPU sits idle during each of A's I/Os), then B → the CPU idles ~40 ms while A waits on the disk; total ≈ 140 ms.
- **Better:** whenever A blocks on I/O, run B; when A's I/O finishes, A's next 10 ms burst (shorter than B's remainder, so STCF prefers it) preempts B → `A B A B A B A B A B`; the CPU is never idle and everything finishes at ≈ 100 ms.

> **Tip (OSTEP): overlap enables higher utilization.** Start an operation, then switch to other work — useful for disk I/O, network messages, and more.

Treating bursts as jobs also means interactive jobs (short bursts) naturally get run frequently, while CPU hogs fill the gaps.

## PART 5 — No More Oracle: Multi-Level Feedback Queue (OSTEP Ch. 8)

### 5.1 The crux
> **How can we schedule without perfect knowledge?** Minimize response time for interactive jobs *and* turnaround for others, without knowing job lengths in advance.

| SJF / STCF | Round Robin | **MLFQ** |
|---|---|---|
| Needs job length | No oracle needed | Uses *observed behavior* |
| Excellent turnaround | Good response | Adapts priorities |

**Tip: learn from history.** MLFQ uses the recent past to predict the near future. This works when jobs have *phases* of behavior; it can be wrong, and a wrong prediction can be worse than none.

### 5.2 Structure and Rules 1–2
Multiple **queues**, each at a different **priority** level; every runnable job sits in **exactly one** queue.
```
Q2  [high]   A  B
Q1           C
Q0  [low]    D
```
- **Rule 1:** If Priority(A) > Priority(B), A runs (B doesn't).
- **Rule 2:** If Priority(A) = Priority(B), they run in **Round Robin** (using that queue's time slice).

In the picture, A and B alternate; C and D wait as long as Q2 has runnable jobs.

The key design question is *how priorities change* — MLFQ sets them from behavior: a job that keeps relinquishing the CPU (waiting on the keyboard) looks interactive → stay high; a job that burns long CPU stretches looks CPU-bound → move down.

### 5.3 Attempt #1: changing priority (Rules 3–4)
New concept: **allotment** — the total CPU time a job may spend at one priority level before being demoted (initially assume allotment = one time slice).
- **Rule 3:** A new job enters at the **highest** priority (topmost queue).
- **Rule 4 (first version, 4a/4b):** use up the allotment → move **down**; give up the CPU *before* the allotment is used (e.g., blocking for I/O) → **stay** at the same level.

### 5.4 Worked behaviors
**One long CPU-bound job** (3 queues, slice = allotment = 10 ms): A starts in Q2, uses its slice → Q1, uses its slice → Q0, and stays at the bottom. *It proves itself CPU-bound.*

**A short job arrives later** (A long and already in Q0; B arrives at t=100, needs 20 ms): B enters at Q2, preempts A, runs 10 ms, drops to Q1, runs 10 more, finishes. **MLFQ approximates SJF**: every new job is *assumed possibly short* until it proves otherwise — if it's short it finishes quickly at high priority; if not, it sinks.

**An interactive job** (runs ~briefly, blocks for I/O, repeat): it keeps yielding before its allotment expires, so it stays in Q2. Meanwhile CPU-bound A fills the idle CPU from Q0. Giving up the CPU early is treated as interactive behavior.

### 5.5 Problem 1: starvation
If interactive, high-priority jobs keep arriving, a low-priority CPU-bound job may get **no CPU at all**, forever. A correct scheduler must balance responsiveness with *eventual progress*.

### 5.6 Rule 5: priority boost
- **Rule 5:** After some period **S**, move **all** jobs to the topmost queue.

Solves two problems at once: **(1) no starvation** — a job sitting in the top queue shares the CPU round-robin with the other top jobs, so it *will* be served; **(2) behavior change** — a job that was CPU-bound but has become interactive gets reconsidered and treated correctly after the boost.

### 5.7 Problem 2: gaming the scheduler
Under rule 4a/4b, a process can issue a (cheap) I/O just *before* its allotment expires (say after running 99% of it) — it never gets demoted and **nearly monopolizes the CPU**.

> **Tip (OSTEP): scheduling must be secure from attack.** A scheduling policy is a *security* concern: in shared systems, a single user able to game the policy gains advantage and harms others.

### 5.8 Attempt #3: better accounting (the final Rule 4)
Stop forgetting partial CPU use when a job blocks. Instead **accumulate** CPU usage at each level:
- **Rule 4 (final):** Once a job uses up its time allotment at a given level — **regardless of how many times it has given up the CPU** — it moves down one queue.

One long burst and many small bursts are **charged consistently**.

### 5.9 The refined rule set (memorize this)
1. Higher-priority jobs run before lower-priority jobs.
2. Jobs at the same priority run in Round Robin (using that queue's time slice).
3. New jobs enter at the highest priority.
4. After using its allotment at a level (cumulatively), a job moves down.
5. Periodically boost all jobs back to the top queue.

### 5.10 Tuning MLFQ
| Parameter | Design effect |
|---|---|
| Number of queues | priority granularity |
| Quantum per queue | high queues usually **short** (≈10 ms or less); low queues usually **longer** (100s of ms) |
| Allotment per queue | how quickly CPU-bound jobs move down |
| Boost period S | **too high → starvation; too low → weak priority separation** |
| Accounting rule | must prevent gaming and preserve fairness |

**No universally correct constants.** OSTEP's **Ousterhout's Law**: avoid "voo-doo constants" when possible — but it's hard, and defaults are usually left unmodified in the field.

**Real systems:** Solaris's Time-Sharing (TS) class is table-driven — by default ~60 queues, slices growing from ~20 ms at the top to a few hundred ms at the bottom, boosts about every second. FreeBSD uses a **formula** over decayed CPU usage (decay plays the role of the boost). Many schedulers also reserve top levels for OS work and accept user **advice** (e.g., `nice`). Windows NT and descendants, BSD derivatives, and Solaris all use some form of MLFQ.

## PART 6 — Mapping to Luit: Policy Concept → Implementation

| Concept from the policy lectures | Luit implementation idea |
|---|---|
| Runnable set | Processes with state `RUNNABLE` |
| Preemption | Timer interrupt may lead to `yield()` |
| Blocking | `sleep()` changes `RUNNING → SLEEPING` |
| I/O completion / event | `wakeup()` changes `SLEEPING → RUNNABLE` |
| Context switch | `swtch()` transfers between scheduler and process context |
| Policy choice | **Simple process-table scan / RR-like behavior** in the teaching OS |

> **Luit is intentionally simple; MLFQ is a policy students can later implement or compare against.**

### 6.1 The conceptual scheduler loop
```c
for (;;) {
    intr_on();
    for each process p {
        acquire(&p->lock);
        if (p->state == RUNNABLE) {
            p->state = RUNNING;
            cpu->proc = p;
            swtch(&cpu->context, &p->context);
            cpu->proc = 0;
        }
        release(&p->lock);
    }
}
```
This is a **teaching-level view** — the lecture itself says to match exact names and order to the Luit source when tracing code. Reading it:
- **One scheduler loop per hart** (Part 6.6): each hart runs its own copy of this loop.
- `intr_on()` — interrupts must be able to arrive, otherwise a hart with nothing runnable could never learn that something became runnable.
- `acquire(&p->lock)` — process state is shared kernel data touched by many harts; `p->lock` is one of the locks from the Locks guide's Part 11.1 table ("scheduling and state transitions must be consistent").
- The scan picks the **first RUNNABLE** process it finds → effectively round-robin over the process table: a policy, but a trivial one.

### 6.2 `swtch()`: mechanism, not policy
```
 Process P kernel ctx ──swtch(&P,&cpu)──► Scheduler ctx ──swtch(&cpu,&Q)──► Process Q kernel ctx
```
**`scheduler()` decides who should run; `swtch()` performs the low-level context transfer.** A process never switches *directly* to another process — it switches **to the scheduler's own context**, which then picks and switches to the next. The scheduler has its own context precisely so it can *resume* after a process yields or sleeps.

### 6.3 Trapframe ≠ `swtch` context (a favorite confusion)
| Trapframe | `swtch` context |
|---|---|
| **User** ↔ kernel trap state | **Kernel** context-switch state |
| Used for syscall, exception, interrupt **return** | Used to resume scheduler/process **kernel execution** |
| Holds user-visible registers needed for `sret` (recall the 31 registers `uservec` saves, from the Syscall guide) | Holds **callee-saved** kernel registers and a return point |
| Tied to **trap handling** | Tied to **scheduling mechanism** |

Keep them conceptually separate: a trapframe says "how to get back to *user mode*"; a `swtch` context says "how to get back to *this kernel thread of execution*."

### 6.4 Timer interrupt → scheduler: the full story
```
 1. P runs in user mode          5. yield()
 2. timer interrupt              6. P: RUNNING → RUNNABLE
 3. trap entry (uservec)         7. swtch to scheduler
 4. usertrap()                   8. scheduler chooses Q  (→ swtch to Q)
```
**A CPU-bound process cannot run forever, because timer interrupts return control to the kernel.** Steps 1–4 are exactly the trap path from the Syscall guide (this time `scause` indicates a *timer interrupt* rather than `ecall`); steps 5–8 are the new scheduling half.

> **A trap becomes a scheduling event only when the kernel actually yields/sleeps and dispatches another process.**

### 6.5 `yield`, `sleep`, `wakeup` — the three state transitions
| Operation | Transition | Meaning |
|---|---|---|
| `yield()` | `RUNNING → RUNNABLE` | "I can run again later" |
| `sleep(chan, lock)` | `RUNNING → SLEEPING` | "Don't run me until the event occurs" |
| `wakeup(chan)` | `SLEEPING → RUNNABLE` | "The event occurred; you *may* run later" |

`sleep`/`wakeup` are exactly the Condition Variables guide's Part 11 mechanism, here seen as scheduler state changes. **`wakeup()` doesn't run the process — it only makes it eligible.** The scheduler still decides when a RUNNABLE process becomes RUNNING.

### 6.6 A syscall trap is not automatically a context switch
| Ordinary syscall | Scheduler switch |
|---|---|
| `P user → P kernel → P user` | `P → scheduler → Q` |
| Same process remains current | **Running process changes** |

In the Luit design discussed in class, an **ordinary syscall does not by itself imply a `satp` change to another process** (recall the Syscall guide's Part 3: Luit's whole point is *not* switching page tables on trap entry). A real **P → Q** switch changes the active process and address-space context (and so does involve `satp`, and the `sfence.vma` discipline from the VM guide).

### 6.7 Multiple harts: real parallelism
```
Hart 0: scheduler loop → P1
Hart 1: scheduler loop → P2
Hart 2: scheduler loop → P3
Hart 3: scheduler loop → idle / P4
```
Several processes run **truly in parallel**, and several harts can make scheduling decisions *concurrently*. Open questions the lecture raises (understand the questions, not a single answer):
- One **global run queue** or **per-hart queues**?
- Should a process prefer the same hart (**cache affinity**)?
- How to avoid **load imbalance** (one hart overloaded while another idles)?
- How do **locks** protect process state while multiple harts schedule at once? (This is why the loop above takes `p->lock` — your Harts/Threads guide's Part 9 point that the kernel is *already* concurrent.)

## PART 7 — Worked Exercises

### 7.1 Exercise 1: FIFO vs. SJF vs. RR (quantum = 2)
Jobs (all arrive at 0): **A = 8, B = 4, C = 2**. Arrival order A, B, C.

**FIFO** — `A(0–8) B(8–12) C(12–14)`
| Job | Completion | Turnaround | First run | Response |
|---|---|---|---|---|
| A | 8 | 8 | 0 | 0 |
| B | 12 | 12 | 8 | 8 |
| C | 14 | 14 | 12 | 12 |
| **Avg** | | **11.33** | | **6.67** |

**SJF** — `C(0–2) B(2–6) A(6–14)`
| Job | Completion | Turnaround | First run | Response |
|---|---|---|---|---|
| C | 2 | 2 | 0 | 0 |
| B | 6 | 6 | 2 | 2 |
| A | 14 | 14 | 6 | 6 |
| **Avg** | | **7.33** | | **2.67** |

**RR, quantum 2** — `A(0–2) B(2–4) C(4–6) A(6–8) B(8–10) A(10–12) A(12–14)`
- A has 6 left after its first slice; B has 2 left after its first; C finishes at 6 (its only slice needed). Then A, B alternate; B finishes at 10; A runs alone to 14.
| Job | Completion | Turnaround | First run | Response |
|---|---|---|---|---|
| A | 14 | 14 | 0 | 0 |
| B | 10 | 10 | 2 | 2 |
| C | 6 | 6 | 4 | 4 |
| **Avg** | | **10.00** | | **2.00** |

**What the exercise is testing:** SJF wins on turnaround (7.33), RR wins on response among the *fair* options (2.00 vs. FIFO's 6.67) while landing in the middle on turnaround (10.00). Different policies optimize different metrics — and don't confuse the two formulas: turnaround uses **completion** time, response uses **first-run** time.

### 7.2 Exercise 2: predict MLFQ behavior
Setup: 3 queues (Q2 high → Q0 low), quantum = allotment = 10 ms at every level, boost period S = 100 ms. **A**: CPU-bound, arrives t=0. **B**: interactive, arrives t=30, runs 2 ms then sleeps 18 ms, repeatedly. **C**: short job, arrives t=50, needs 12 ms.

**Trace (my working of the exercise, under the stated assumptions):**
| Time | Event |
|---|---|
| 0–10 | A runs in Q2, uses its allotment → demoted to Q1 |
| 10–20 | A runs in Q1 (alone), uses its allotment → demoted to Q0 |
| 20–30 | A runs in Q0 |
| 30 | B arrives → enters **Q2** (Rule 3), outranks A (Q0) → **B preempts A** |
| 30–32 | B runs 2 ms, then sleeps (I/O) until t=50 |
| 32–50 | A runs in Q0 whenever nothing higher is runnable |
| 50 | B wakes (still Q2) **and** C arrives → Q2. Both outrank A → they round-robin; either starts within about one slice |
| ~50–64 | C runs one 10 ms slice, uses its allotment, drops to Q1, then finishes its last 2 ms in Q1 |
| 70, 90, … | B's wake-ups each preempt A for 2 ms |
| **100** | **Priority boost (Rule 5):** A is lifted from Q0 back to Q2 |

**Discussion answers:**
- **Best response:** **B and C** — both enter at the top queue and preempt the low-priority A almost immediately (response ≈ 0 to about one slice).
- **Which job moves down:** **A** (clearly, to Q0 by t=20). **C** also moves to Q1 after one full slice, since it needs 12 ms > 10 ms. B is kept high because it gives up the CPU after 2 ms.
- **Why the boost matters:** A sits at the bottom; if interactive jobs like B keep arriving, A could starve. The boost at t=100 guarantees A progress and lets the scheduler reconsider whether its behavior changed.
- **A subtle extra point (worth noticing, my observation):** under the *final* Rule 4, B's 2 ms bursts **accumulate** (2 ms × 5 = 10 ms = the allotment). B's bursts start at t = 30, 50, 70, 90 (≈8 ms by t=92), so the t=100 boost arrives before a fifth burst — assuming the boost also resets usage accounting, B isn't demoted here. Without a boost, an interactive job that runs a lot *cumulatively* would eventually sink too — another reason the boost matters.

### 7.3 Exercise 3: trace Luit scheduling
Control flow when CPU-bound P is preempted by a timer interrupt and Q runs next:
1. timer interrupt → 2. trap entry → 3. `usertrap()` → 4. `yield()` → 5. P becomes `RUNNABLE` → 6. `swtch` to scheduler → 7. scheduler selects Q → 8. `swtch` to Q.

**Key answer point:** *a trap becomes a scheduling event only when the kernel actually yields/sleeps and dispatches another process.*

## PART 8 — Common Misconceptions (High-Value Viva/Exam Points)
| Misconception | Correction |
|---|---|
| Every trap is a context switch | A syscall trap may return to the **same** process |
| `wakeup` runs the process immediately | `wakeup` makes it **RUNNABLE**; the scheduler decides when it runs |
| RR is always better than SJF | Depends on the metric: **response** (RR) vs. **turnaround** (SJF/STCF) |
| MLFQ magically knows job length | MLFQ **estimates from observed behavior** |
| `swtch` chooses the process | `scheduler()` chooses; **`swtch` only transfers context** |
| Trapframe and `swtch` context are the same thing | Trapframe = user/trap state; `swtch` context = kernel switch state |
| Giving up the CPU early always keeps you high-priority | Only under the *naive* Rule 4a/4b; the final Rule 4 accumulates usage |

## Quick-Reference: Formulas and Rules
```
T_turnaround = T_completion − T_arrival
T_response   = T_first-run  − T_arrival
average      = sum over jobs / number of jobs
```
**Solving a numerical schedule — procedure:**
1. Draw the timeline (Gantt chart) for the given policy, noting arrivals and preemptions.
2. For each job, read off **completion** and **first-run** times.
3. Apply the two formulas (watch arrival ≠ 0).
4. Average. Then state which metric the policy favors and why.

## Quick-Reference: Vocabulary
| Term | One-line meaning |
|---|---|
| **Turnaround time** | completion − arrival |
| **Response time** | first run − arrival |
| **Convoy effect** | short jobs stuck behind a long one |
| **Preemption** | OS stops a running job (via timer interrupt) without its consent |
| **Quantum / time slice** | how long RR (or an MLFQ level) runs a job before rotating |
| **Amortization** | pay a fixed cost (context switch) less often by using longer slices |
| **STCF / SRTF** | preemptive SJF — run the job with the least *remaining* time |
| **MLFQ** | several priority queues; priority adapts from observed behavior |
| **Allotment** | CPU time allowed at one level before demotion |
| **Priority boost** | periodically move all jobs to the top queue (prevents starvation) |
| **Gaming** | yielding just before the allotment ends to stay high-priority |
| **`swtch()`** | low-level context transfer between kernel contexts |
| **`scheduler()`** | per-hart loop that picks a RUNNABLE process |
