## PART 1 — Proportional Share: The Central Idea

Earlier schedulers optimized *metrics*:

| Earlier metrics | New metric |
|---|---|
| Turnaround time | **Configured CPU share** |
| Response time | Fairness over time |
| Waiting time | Resource ownership |
| Interactive feel | Useful in clouds / VMs |

> **Example goal: A should receive 75% of the CPU, B should receive 25%.**

Instead of minimizing turnaround or response, the scheduler **guarantees each job a configured fraction of CPU time**. This matters wherever resources are *owned or sold in proportion* — e.g., VMs in a cloud, where one tenant pays for a larger share than another.

Compare with MLFQ (earlier guide): MLFQ *guesses* who deserves priority from observed behavior and offers no explicit share. Proportional share lets you **state the intended share directly**.

## PART 2 — Tickets Represent Shares

| Process | Tickets | Fraction of total | Desired CPU share |
|---|---|---|---|
| A | 75 | 75/100 | 75% |
| B | 25 | 25/100 | 25% |

> A ticket is an **abstract claim on a fraction of a resource**.

Three consequences worth remembering:
- More tickets → higher probability (lottery) or higher deterministic share (stride).
- **Shares are relative:** doubling *everyone's* tickets changes nothing, because only the ratios matter.
- The mechanism **generalizes beyond the CPU** — to memory, I/O, and virtual machines.

## PART 3 — Lottery Scheduling: Randomized Proportional Share

### 3.1 The algorithm
Every quantum, hold a lottery:
1. Count all **runnable** tickets.
2. Pick a random **winning ticket**.
3. Find the process that owns that ticket.
4. Run that process for the next time slice.

### 3.2 Worked example: 100 tickets
A owns tickets 0–74; B owns 75–99.

| Winning ticket | Winner | Reason |
|---|---|---|
| 63 | A | in A's range |
| 85 | B | in B's range |
| 10 | A | in A's range |
| 99 | B | in B's range |

Over many lotteries, A should win about 75% and B about 25%.

### 3.3 The implementation is tiny
```c
winner  = random(0, total_tickets - 1);
counter = 0;
for each runnable job p:
    counter += p.tickets;
    if (counter > winner) {
        run p;
        break;
    }
```
What you need: a runnable list, the total ticket count, a random number, and a walk until the **cumulative** ticket count exceeds the winner. Ticket ranges are never stored — they are *implicit* in the running sum.

### 3.4 Trace: A = 100, B = 50, C = 250 (total 400), winner = 300
| Step | Counter | Decision |
|---|---|---|
| A | 100 | 100 ≤ 300 → continue |
| B | 150 | 150 ≤ 300 → continue |
| C | 400 | 400 > 300 → **C wins** |

Implicit ranges: A owns 0–99, B owns 100–149, C owns 150–399. Ticket 300 is in C's range, so C gets the next quantum. Long-run expected shares: A 25%, B 12.5%, C 62.5%.

> Watch the comparison: it is `counter > winner` (strictly greater), because winning tickets are numbered from 0.

### 3.5 Why randomness is attractive — and its price
**Attractive:** simple (just ticket counts and a random number), lightweight (no continuously-maintained fairness state), and robust (avoids some deterministic corner-case behavior).
**Price:** randomness gives **approximate fairness, not exact short-term guarantees**.

| Short time window | Long time window |
|---|---|
| Outcome can deviate from the exact share | Observed share tends toward the desired share |
| A small-ticket job may get unlucky | Random variation averages out |
| Fairness is approximate | Better with many lotteries |

### 3.6 Ticket mechanisms: currency, transfer, inflation
| Mechanism | Meaning | Why useful |
|---|---|---|
| **Currency** | Users allocate *their own local* tickets; the OS converts them to global tickets | Hierarchical sharing |
| **Transfer** | A client temporarily gives tickets to a server | Speeds up work done *on the client's behalf* |
| **Inflation** | A process temporarily changes its own ticket count | Only safe in **trusted** environments (otherwise a greedy process just "prints" tickets) |

**Currency worked example:**
| Owner | Local allocation | Global conversion |
|---|---|---|
| User A | A1 = 500, A2 = 500 (out of 1000) | A1 = 50, A2 = 50 |
| User B | B1 = 10 (out of 10) | B1 = 100 |
| Global lottery | — | Total = 200 tickets |

User A owns half the system share, split equally between A1 and A2; User B owns the other half, all to B1. **Each user can express local choices without breaking the global share.**

### 3.7 The open problem: assigning tickets
The *mechanism* is easy; the *policy* is hard. How many tickets should the browser get? A compiler? Should tickets be per process, per user, per group, per service? If users choose tickets, how do we prevent unfairness? **Ticket assignment is part of the scheduler's policy — tickets alone don't solve it.**

## PART 4 — Stride Scheduling: Deterministic Proportional Share

### 4.1 The idea
Remove the randomness:
- Each process gets a **stride inversely proportional to its tickets**.
- Each process also has a **pass** value measuring accumulated progress.
- At each scheduling point, **run the process with the lowest pass**.
- After it runs, **pass += stride**.

> More tickets → smaller stride → runs more often.

### 4.2 Stride values (stride = 10000 / tickets)
| Process | Tickets | Stride |
|---|---|---|
| A | 100 | 100 |
| B | 50 | 200 |
| C | 250 | 40 |

### 4.3 Full trace (ties broken A, then B, then C)
| Pass(A) | Pass(B) | Pass(C) | Run |
|---|---|---|---|
| 0 | 0 | 0 | A |
| 100 | 0 | 0 | B |
| 100 | 200 | 0 | C |
| 100 | 200 | 40 | C |
| 100 | 200 | 80 | C |
| 100 | 200 | 120 | A |
| 200 | 200 | 120 | C |
| 200 | 200 | 160 | C |
| 200 | 200 | **200** | *(all equal — the cycle restarts)* |

Over one **8-quantum cycle**: **C runs 5, A runs 2, B runs 1 → exactly 250 : 100 : 50.** (I re-ran this trace by script while preparing the guide; the order is `A B C C C A C C` and all three pass values land on 200, i.e., one clean cycle — 200 is the least common multiple of the strides 100, 200 and 40.)

### 4.4 Lottery vs. stride
| Aspect | Lottery | Stride |
|---|---|---|
| Decision | Random winning ticket | Minimum pass value |
| Fairness | Probabilistic over time | **Deterministic over cycles** |
| Per-process state | Minimal (tickets) | Needs **pass** and **stride** |
| New arrivals | Easy to insert | Need a **sensible initial pass** |
| Strength | Simple and robust | Precise proportionality |

**Why "new arrivals" is a real problem for stride:** if a new process started with pass = 0 while everyone else's pass is large, it would have the lowest pass for a long time and **monopolize the CPU while catching up**. The initial pass must be set sensibly (e.g., near the current minimum). The same "late joiner catches up and starves everyone" shape reappears in CFS for waking sleepers (Part 5.7).

## PART 5 — CFS: Fair Sharing in a Real Scheduler

### 5.1 The idea
CFS (the Completely Fair Scheduler) approximates an **ideal fair CPU** where every runnable process progresses equally.
- Each process has **virtual runtime (vruntime)**; it grows as the process runs.
- At each decision, CFS picks the **runnable process with the lowest vruntime** — the one that has received the *least* service.

> **Key idea: fairness is converted into an ordering by vruntime.**

Notice the structural kinship with stride: "pick the minimum, then advance it" — vruntime is CFS's pass, but derived from *actual runtime* rather than a fixed per-run stride.

### 5.2 Dynamic time slice (no fixed RR quantum)
| Parameter | Meaning |
|---|---|
| `sched_latency` | Target period over which all runnable processes should get fair service |
| `n` | Number of runnable processes on this CPU |
| Basic slice | `sched_latency / n` |
| `min_granularity` | Lower bound on the slice, to avoid too many context switches |

**Example, `sched_latency` = 48 ms:**
| Runnable processes | Basic slice | Interpretation |
|---|---|---|
| 4 | 48/4 = **12 ms** | each runs 12 ms in the 48 ms window |
| 2 | 48/2 = **24 ms** | longer slices |
| 10 | 48/10 = **4.8 ms** | too small → `min_granularity` may apply |

(The OSTEP chapter's example uses a 6 ms floor for this last case, so each of the ten gets 6 ms instead of 4.8 — the slide doesn't state the value, so treat that number as a reminder from the chapter rather than from the slide.)

This reuses the quantum tradeoff from the previous guide's Part 3.9: slices that are too short waste time on context switches (and cold caches/TLB); CFS bounds that with `min_granularity`.

### 5.3 Niceness and weights
CFS adjusts shares through **weights derived from nice values**:
| Nice | Meaning | Weight |
|---|---|---|
| negative | higher priority | larger |
| 0 | default | **1024** |
| positive | lower priority | smaller |

> Being "nice" means **accepting less CPU share.**

### 5.4 Weighted time slice
```
time_slice_k = ( weight_k / Σ weight_i ) × sched_latency
```
| Process | Nice | Weight | Share if only A and B |
|---|---|---|---|
| A | −5 | 3121 | 3121/(3121+1024) ≈ **75%** |
| B | 0 | 1024 | 1024/(3121+1024) ≈ **25%** |

With `sched_latency` = 48 ms: **A ≈ 36 ms, B ≈ 12 ms** (precisely 36.1 and 11.9).

### 5.5 Weighted vruntime: higher weight accumulates *slower*
```
vruntime_i += ( weight_0 / weight_i ) × runtime_i        (weight_0 = 1024)
```
| Process | Weight | Same real runtime → vruntime |
|---|---|---|
| High-weight A | 3121 | grows **slowly** → stays eligible more often |
| Default B | 1024 | grows normally → gets a smaller share |

**Check it with the numbers above** (my worked verification): in one 48 ms window, A runs 36.1 ms real → vruntime += (1024/3121) × 36.1 ≈ **11.9**; B runs 11.9 ms real → vruntime += (1024/1024) × 11.9 ≈ **11.9**. **Both advance by the same amount** — which is exactly why picking the lowest vruntime yields the 75/25 split. Equal vruntime *means* fair-share-weighted equality. CFS gives high-priority processes more real CPU without letting their vruntime race ahead.

### 5.6 The data structure matters
| Naïve list | Red-black tree |
|---|---|
| Finding minimum vruntime may be expensive | Ordered by vruntime |
| Sorted insertion O(n) | Insert/delete **O(log n)** |
| Bad with thousands of processes | **Leftmost node = next candidate** |

> A scheduler runs very frequently; its data structure must be engineered carefully. (OSTEP adds that only *runnable* processes live in the tree — a sleeping process is removed and re-inserted on wakeup.)

### 5.7 Sleeping and I/O processes
**Problem:** a process that sleeps a long time wakes up with a **very small vruntime** compared to everyone else, so it could monopolize the CPU while "catching up".
**Fix:** CFS adjusts a waking process's vruntime — a common idea is to place it **near the minimum vruntime of the runnable jobs**. This prevents starvation of others, but *exact* fair sharing with I/O sleepers remains subtle (you've deliberately forgotten some of the service it was "owed" while asleep). *Fair-share scheduling is elegant, but its interaction with I/O is not trivial.*

(Same family of problem as stride's new-arrival initial pass, Part 4.4.)

## PART 6 — Proportional-Share Summary

| Scheduler | Main idea | Strength | Weakness |
|---|---|---|---|
| **Lottery** | Tickets + random winner | Simple and flexible | Short-term randomness |
| **Stride** | Tickets → strides; run min pass | Deterministic share | Global pass-state issues (initial pass, shared state) |
| **CFS** | Run lowest vruntime | Practical, scalable fairness | Complex details; I/O subtleties |

**Common goal:** allocate CPU in *configured proportions*, not merely minimize turnaround or response time.

## PART 7 — Multiprocessor Scheduling: A Placement Problem

> Once a machine has multiple CPUs/harts, scheduling becomes a **placement** problem as well as a **choice** problem:
> - Which runnable job should run?
> - On *which* CPU/hart should it run?
> - Should it stay there next time?
> - How do we balance load without destroying cache locality?

The lecture notes this topic is best understood *after concurrency*, because **locks and shared state now become scheduler issues too** (your Locks and Harts/Threads guides).

### 7.1 More CPUs don't automatically speed up one program
| Single-threaded program | Multithreaded program |
|---|---|
| One execution stream → uses one CPU at a time | Work split into threads that can run on different CPUs |
| More CPUs don't directly help | Needs synchronization and careful design |

**Hardware parallelism is useful only if software exposes enough parallel work.**

### 7.2 Architecture: caches matter
```
CPU 0       CPU 1       CPU 2
Cache       Cache       Cache
        Shared Main Memory
```
Each CPU/hart may have **local cache and TLB state**. Moving a process between CPUs can lose useful locality (recall the previous guide's Part 3.10: caches, TLB and branch-predictor state are part of context-switch cost). Shared-memory correctness needs **cache coherence** plus **synchronization**.

### 7.3 Cache coherence: correctness vs. performance
1. CPU 0 reads address A and caches value D.
2. CPU 0 writes A, producing D′ in *its* cache.
3. The process later runs on CPU 1.
4. CPU 1 must **not** incorrectly read the stale D from memory.

Hardware **cache-coherence protocols** preserve the single shared-memory view. **But coherence does not remove the need for locks** on shared OS data structures.

### 7.4 Don't forget synchronization
```c
tmp   = head;
value = head->value;
head  = head->next;
free(tmp);
```
Two CPUs can run this list-pop concurrently: both read the same old `head`, both pop the same node, both `free(tmp)` → **double free / lost node**. *Coherence guarantees both CPUs see the same memory; it does not make the multi-step update atomic.* This is exactly the free-list race from your Locks guide (Part 11.2, `kmem.lock`) — now with scheduler queues and process lists as the victims. **Shared scheduler queues and process lists need mutual exclusion.**

### 7.5 Cache affinity
A process builds useful state in the cache/TLB of the CPU where it last ran.
| Run again on the same CPU | Move to another CPU |
|---|---|
| Cache contents may still be useful | Correct (thanks to coherence) |
| TLB and predictor state may help | But the cache may be **cold** |
| Better performance | Working set must be reloaded |

> **Scheduler goal: preserve affinity when possible, but still balance load.** Two goals in tension — the theme of the rest of this lecture.

## PART 8 — Single-Queue Multiprocessor Scheduling (SQMS)

**One global runnable queue shared by all CPUs.**
```
Global queue:  A  B  C  D  E
```
- A simple extension of a single-CPU scheduler: with four CPUs, pick the next four runnable jobs.
- **Naturally balances load**, since every CPU draws from the same queue.

### 8.1 Problem 1 — scalability
| What is shared | What goes wrong |
|---|---|
| Global run queue | All CPUs contend for the **same lock** |
| Queue lock | Queue operations become a bottleneck |
| Scheduling metadata | More CPUs can mean *more* scheduling overhead |
| Runnable state | |

A simple design becomes slow when many CPUs make scheduling decisions concurrently.

### 8.2 Problem 2 — poor cache affinity
| CPU | Slice 1 | Slice 2 | Slice 3 | Slice 4 |
|---|---|---|---|---|
| CPU 0 | A | E | D | C |
| CPU 1 | B | A | E | D |
| CPU 2 | C | B | A | E |
| CPU 3 | D | C | B | A |

Jobs **bounce across CPUs** because every CPU takes whatever is next in the queue. Execution is still *correct* (coherence), but each job keeps **re-warming a different cache**.

### 8.3 SQMS with affinity: a possible improvement
| CPU | Mostly stays with | Occasional migrant |
|---|---|---|
| CPU 0 | A | E |
| CPU 1 | B | E |
| CPU 2 | C | E |
| CPU 3 | D | E |

Most jobs keep cache affinity; **only some** (here E) migrate, to keep load balanced. It works, but the implementation is more complex than a pure global queue — you've added per-job placement bookkeeping to a design whose appeal was simplicity.

## PART 9 — Multi-Queue Multiprocessor Scheduling (MQMS)

**Each CPU has its own scheduling queue.**
```
Q0: A  C          Q1: B  D
```
- Each CPU schedules mostly from *its own* queue.
- Each queue can use RR, MLFQ, CFS-like, or any local discipline.
- Less sharing → less lock contention.

| Property | Why MQMS helps |
|---|---|
| Scalability | Each CPU mostly touches its own queue → less global lock contention |
| Cache affinity | Jobs tend to return to the same CPU → reuse cache/TLB |
| Modularity | Each queue can run its own local policy |

> **But the price is a new problem: load imbalance.**

### 9.1 The imbalance problem
```
Q0: A            Q1: B  D
```
| CPU | Observed effect |
|---|---|
| CPU 0 | Only A runs → A gets a **large share** |
| CPU 1 | B and D alternate → each gets *less* CPU than A |

If Q0 becomes empty while Q1 still has work, **CPU 0 can go idle** — wasted hardware while jobs wait. So MQMS must sometimes **move work between queues**.

### 9.2 Migration
**Migration** = moving a job from one CPU's queue to another's.
| Why migrate | Why not migrate too much |
|---|---|
| Avoid idle CPUs | Breaks cache affinity |
| Give jobs fair CPU access | Adds scheduler overhead |
| Balance queue lengths/load | Requires synchronization |

> Migration is useful, but it **fights locality**. The scheduler must compromise.

### 9.3 Work stealing
1. A CPU notices its local queue is **empty or lightly loaded**.
2. It occasionally **peeks** at another CPU's queue.
3. If that queue is much fuller, it **steals** one or more jobs.
4. Those jobs migrate to the underloaded CPU.

**Tuning:** *steal too often* → high overhead and poor scalability (you've rebuilt the shared-queue contention you were avoiding); *steal too rarely* → severe load imbalance. Another "no universally correct constant" parameter, like MLFQ's boost period.

## PART 10 — SQMS vs. MQMS, and Real Linux Schedulers

| Aspect | Single queue (SQMS) | Multi queue (MQMS) |
|---|---|---|
| Design | One global queue | One queue per CPU/hart |
| Load balance | Naturally good | Needs migration / work stealing |
| Scalability | Can suffer lock contention | Usually better |
| Cache affinity | Can be poor | Naturally good |
| Complexity | Simple core idea | More balancing logic |

> **There is no universally perfect multiprocessor scheduler.**

**Linux examples (as presented from OSTEP):**
| Scheduler | Queue style | Main idea |
|---|---|---|
| O(1) | Multiple queues | Priority-based, MLFQ-like, focused on interactivity |
| CFS | Multiple queues | Deterministic proportional share using vruntime |
| BFS | Single queue | Proportional-share style with the EEVDF idea |

Both single-queue and multi-queue approaches can be made to work in real systems; **details matter greatly**. (This table reflects the lecture/OSTEP presentation — real Linux scheduling has kept evolving, so treat it as course material rather than current kernel documentation.)

## PART 11 — Connecting to Luit: Harts and Runnable Work

- A **hart** is an execution engine that runs kernel/user code (Harts/Threads guide, Part 1).
- With multiple harts, multiple processes/threads run **at the same time**.
- **Scheduler state must be protected**, because harts inspect and update it concurrently.
- Running the same process again on the same hart **may preserve cache/TLB state**.

Luit supplies the concrete setting: `RUNNABLE` processes, harts, locks, timer interrupts, context switches.

**My interpretation, not stated on the slides — flagged as such:** the teaching-level Luit loop from your previous guide (every hart scans the process table, taking `p->lock` and running the first `RUNNABLE` process it finds) looks *conceptually* closer to the **SQMS** side of the spectrum — one shared pool of runnable work, contention on shared process state, and no per-hart placement logic — than to MQMS with per-hart queues. That would explain why, in the lecture's framing, "harts, queues, locks" and "cache-affinity intuition" are the next topics. The lecture itself says to match exact names and structure to the real Luit source when tracing code, so verify this reading against the source before relying on it.

## PART 12 — Worked Exercises

### 12.1 Lottery
Tickets: A = 100, B = 50, C = 250 (total 400).
- **Expected shares:** A 25%, B 12.5%, C 62.5%.
- **Winner = 120?** counter: A 100 (≤120) → B 150 (>120) → **B wins** (ticket 120 is in B's range 100–149).
- **Winner = 399?** A 100, B 150, C 400 (>399) → **C wins** (the last ticket).
- **Winner = 99?** A 100 (>99) → **A wins** (the last of A's tickets).

### 12.2 Stride
Same tickets, stride = 10000/tickets → A 100, B 200, C 40. Run lowest pass, ties A→B→C. Sequence for one cycle: **A B C C C A C C** (pass values end at 200, 200, 200). Counts: C 5, A 2, B 1 = 250:100:50.
*Self-check:* what if we gave everyone **double** the tickets? Strides halve for all, ratios unchanged, the *same* schedule results — shares are relative (Part 2).

### 12.3 CFS slices
`sched_latency` = 48 ms.
- 6 equal-weight runnable processes → 8 ms each.
- 3 processes with weights 2048, 1024, 1024 (total 4096) → 24 ms, 12 ms, 12 ms.
- 12 processes → 4 ms basic slice, likely clamped up by `min_granularity`.

### 12.4 Board trace: two CPUs, four jobs
Initial queues: **Q0: A, C — Q1: B, D** (MQMS).
1. **What if C finishes?** Q0 = {A}, Q1 = {B, D}. A runs alone on CPU 0 and gets a full CPU; B and D each get half of CPU 1 → **imbalance** (A gets twice the share).
2. **What if A and C both finish?** Q0 is empty → **CPU 0 goes idle** while CPU 1 time-slices B and D. Wasted hardware; this is the case for migration/work stealing.
3. **Which job should migrate, and how often?** Move one of B/D to Q0 so each CPU runs one job. *How often* is the tradeoff: migrate too eagerly and you lose cache affinity and pay lock/overhead costs; too rarely and one CPU idles or is underloaded. With an odd job count (e.g., 3 jobs on 2 CPUs) a single static placement can't be fair, so a scheduler may *keep rotating* which job gets moved — accepting some migration cost in exchange for fairness. (This last point is the standard OSTEP-style observation, not a specific number from the slide.)

**What this exercise exposes: the core MQMS tradeoff — load balance versus affinity.**

## PART 13 — Decision Map and Common Mix-Ups

```
Need a configured CPU share?   → Lottery / Stride / CFS
Multiple CPUs/harts?           → SQMS or MQMS
Need scalability + affinity?   → MQMS + migration
```
- Fair-share scheduling asks **"how much CPU should each job receive?"**
- Multiprocessor scheduling asks **"where should each runnable job run?"**

| Mix-up | Correction |
|---|---|
| "Lottery guarantees exact shares" | Only **probabilistically**, and better over long windows |
| "Stride is just lottery without randomness" | It also needs **pass/stride state** and a sensible **initial pass** for newcomers |
| "More tickets = more CPU in absolute terms" | Shares are **relative** to total tickets |
| "CFS has a fixed quantum" | The slice is **dynamic** (`sched_latency / n`, weighted, floored by `min_granularity`) |
| "Higher weight → vruntime grows faster" | **Slower** — that's what keeps the process eligible more often |
| "Cache coherence makes shared scheduler data safe" | Coherence ≠ atomicity; you still need **locks** |
| "SQMS is always worse because of the lock" | It balances load perfectly; the issue is **scalability and affinity** |
| "MQMS solves everything" | It trades contention for **load imbalance**, needing migration/stealing |

## Quick-Reference Vocabulary
| Term | One-line meaning |
|---|---|
| **Proportional share** | Guarantee each job a configured fraction of the CPU |
| **Ticket** | Abstract claim on a fraction of a resource; shares are relative |
| **Lottery scheduling** | Random winning ticket each quantum |
| **Ticket currency / transfer / inflation** | Local→global ticket conversion / lend tickets to a server / self-adjust tickets (trusted only) |
| **Stride / pass** | Inverse-of-tickets increment / accumulated progress; run the lowest pass |
| **vruntime** | CFS's weighted virtual runtime; run the lowest |
| **`sched_latency` / `min_granularity`** | CFS target period / lower bound on slice length |
| **Nice value / weight** | User-facing priority knob / the number CFS actually uses (default 1024) |
| **Cache coherence** | Hardware keeping all CPUs' view of memory consistent |
| **Cache affinity** | Preference to rerun a process on the CPU holding its warm cache/TLB state |
| **SQMS / MQMS** | One global run queue / one run queue per CPU |
| **Migration / work stealing** | Moving jobs between CPU queues / underloaded CPU pulls from a fuller one |

## How This Lecture Connects to Earlier Guides
- **CPU Scheduling guide:** same turnaround/response/fairness trilemma, now with *fairness as an explicit goal*; CFS's dynamic slice reuses the quantum-vs-switch-cost tradeoff (Part 3.9–3.10 there), and Luit's scheduler loop is the single-hart baseline that Part II here generalizes.
- **Locks guide:** the list-pop race (Part 7.4) is the free-list race again; SQMS's global-queue contention is a *spinlock scalability* problem, and MQMS exists largely to dodge it.
- **Harts/Threads guide:** "multiple harts make scheduling decisions concurrently" is the same fact as "the kernel is already concurrent" — now applied to the scheduler itself.
- **VM guide:** cache affinity includes **TLB** state; migrating a process loses TLB warmth just as a context switch can, which is why locality matters even when execution stays correct.
- **Condition Variables guide (sleep/wakeup):** CFS's treatment of *sleepers* (Part 5.7) is the scheduler-side consequence of `sleep`/`wakeup`: a process that blocks and returns must be re-inserted into the fairness ordering without being unfairly advantaged.
